# Vertical Pod Autoscaler (VPA) — Domain 3: Services and Networking

---

## 1. What is the Vertical Pod Autoscaler?

> The **Vertical Pod Autoscaler (VPA)** is a Kubernetes component that **automatically adjusts the CPU and memory `requests`** (and optionally `limits`) for containers running inside your pods.

- "Vertical" scaling = **giving each pod more or less CPU/memory**. (This is different from HPA, which adds or removes pods — that is "horizontal" scaling.)
- VPA looks at the actual CPU and memory consumption of a pod over time, and then either **recommends** better values, or **automatically updates** them by recreating the pod with the new request values.

```
        ┌────────────────────────────────────┐
        │       Vertical Pod Autoscaler       │
        │   (watches CPU/memory of pods)      │
        └─────────────────┬──────────────────┘
                          │
                          ▼
                ┌──────────────────┐
                │   Deployment      │
                │   (nginx)         │
                └──────────────────┘
                          │
              Old pod: requests cpu=50m, mem=50Mi
                          │  (VPA recreates pod)
                          ▼
              New pod: requests cpu=25m, mem=262Mi
                       (adjusted based on actual usage)
```

---

## 2. Why VPA — What Challenges Does It Solve?

### Challenge 1: Requests and Limits Set Too Low

If a developer sets CPU/memory requests **too low**, the application does not get enough resources and may **crash** or run slowly.

**VPA solves this** by detecting low requests and recommending higher values that match actual usage.

---

### Challenge 2: Requests and Limits Set Too High

If requests are set **too high**, the pod **reserves** more resources than it actually needs. Even if the pod is idle and using almost nothing, that reserved amount is **blocked off** and cannot be used to schedule other pods on the node.

> Example from the slides:
> A worker node has **3 cores / 3 GB RAM**. A pod requests **3 cores / 3 GB RAM** even though it only uses a fraction of that. The scheduler cannot place any other pod on this node — all resources are reserved for one pod that does not need them.

**VPA solves this** by lowering the request to a realistic value, freeing up the node to schedule more pods.

---

### Challenge 3: Manually Right-Sizing Pods is Tedious

In production, applications have many containers with very different workloads. Hand-tuning CPU and memory requests for each one is slow, error-prone, and quickly goes out of date.

**VPA solves this** by continuously observing real usage and automatically suggesting (or applying) optimal request values.

---

## 3. How VPA Works (in Simple Kubernetes Terms)

1. You create a **Deployment** (or other workload) that has pods with `resources.requests` set.
2. You create a **VPA** object and point it at that workload using `targetRef`.
3. VPA uses the **Metrics Server** to observe how much CPU and memory the pods actually use.
4. VPA produces a **recommendation** with these values:
   - **Lower Bound** — minimum safe value
   - **Target** — best value to use
   - **Upper Bound** — maximum safe value
   - **Uncapped Target** — best value ignoring resource policy limits
5. Depending on the **update mode**, VPA either just reports the recommendation, or actively applies it by **evicting and recreating** the pods with the new requests.

---

## 4. VPA Update Modes

This is the most important concept to understand for VPA.

| `updateMode` | What it does |
|---|---|
| **Off** | VPA only provides **recommendations**. No changes are applied to the pods. Use this when starting out, to study the recommendation before trusting VPA to act. |
| **Initial** | VPA **assigns the request values only when the pod is created**. Once the pod is running, VPA never changes them. |
| **Auto** | VPA **actively applies** recommendations by **evicting and restarting** pods with the new requests. Pods will get terminated and recreated automatically. |

> In `Auto` mode, you will see existing pods being terminated and new pods being created with updated CPU/memory requests. This is normal — it is VPA doing its job.

---

## 5. Important Points to Remember

- **VPA is NOT installed by default** in Kubernetes. You must install it manually (it is a separate project, part of the official `kubernetes/autoscaler` repository).
- After installation, `kubectl get vpa` works. Before installation, it returns `the server does not have resource type "vpa"`.
- **VPA needs the Metrics Server** to collect CPU/memory data — same as HPA.
- **VPA recreates pods** to apply new requests (in `Auto` mode). This means brief disruption — be careful with stateful or single-replica workloads.
- **VPA may push requests up beyond what the node can fit.** If a pod's new request is larger than free CPU/memory on every node, the new pod stays in **Pending** state with `Insufficient memory` or `Insufficient cpu`. This is a real risk to plan for.
- **Do NOT use VPA and HPA on the same metric** (e.g., both targeting CPU) for the same workload — they will conflict. VPA on CPU/memory + HPA on custom metrics is okay.

## 6. Syntax

### VPA Manifest (Declarative)

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: nginx-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx-deployment      # the workload to scale
  updatePolicy:
    updateMode: "Off"            # Off | Initial | Auto
```

### Inspect VPA

```bash
kubectl get vpa
kubectl describe vpa <vpa-name>
```

### Edit an Existing VPA (e.g., change update mode)

```bash
kubectl edit vpa <vpa-name>
# change updateMode value, save and exit
```

### Delete VPA

```bash
kubectl delete vpa <vpa-name>
```

### Install / Uninstall VPA (the component itself)

```bash
# Install (from the official kubernetes/autoscaler repo)
git clone https://github.com/kubernetes/autoscaler.git
cd autoscaler/vertical-pod-autoscaler/
./hack/vpa-up.sh

# Uninstall
./hack/vpa-down.sh
```

## 7. Examples

### Example 1: Sample Deployment with Requests

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx
        resources:
          requests:
            cpu: "50m"
            memory: "50Mi"
```

Apply it:

```bash
kubectl create -f nginx-deployment.yaml
kubectl get pods
```

Look at one pod:

```bash
kubectl describe pod <pod-name>
# Requests:
#   cpu:     50m
#   memory:  50Mi
```

---

### Example 2: VPA in `Off` Mode (Recommendation Only)

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: nginx-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx-deployment
  updatePolicy:
    updateMode: "Off"
```

```bash
kubectl apply -f vpa.yaml
kubectl get vpa
# CPU and memory columns are empty initially — wait a few minutes
```

Once data is collected:

```bash
kubectl describe vpa nginx-vpa
```

Sample recommendation block:

```
Recommendation:
  Container Recommendations:
    Container Name: nginx
    Lower Bound:
      Cpu:     25m
      Memory:  262144k
    Target:
      Cpu:     25m
      Memory:  262144k
    Uncapped Target:
      Cpu:     25m
      Memory:  262144k
    Upper Bound:
      Cpu:     25m
      Memory:  262144k
```

No pods are restarted — VPA only suggests values.

---

### Example 3: Switch VPA to `Auto` Mode

```bash
kubectl edit vpa nginx-vpa
# change:   updateMode: Off
# to:       updateMode: Auto
```

Watch what happens:

```bash
kubectl get pods --watch
```

You will see existing pods being **Terminating** and new pods being **Created**:

```bash
kubectl describe pod <new-pod-name>
# Requests:
#   cpu:     25m
#   memory:  262144k
```

The request values have been **automatically adjusted** based on the VPA's recommendation.

---

### Example 4: VPA Risk — Pending Pods Due to Insufficient Resources

After VPA bumps up memory requests, the new pod may not fit on any worker node:

```bash
kubectl get pods
# NAME                READY   STATUS    AGE
# nginx-xxx-new       0/1     Pending   30s
```

```bash
kubectl describe pod nginx-xxx-new
# Events:
#   0/1 nodes are available: Insufficient memory.
```

This is **not a bug** — the node simply does not have enough free memory to satisfy the new (larger) request. You must either add a worker node or lower the recommendation.

## 8. Exercises to Practice for the CKAD Exam

### Imperative (CLI-based) Exercises

**Exercise 1 — Confirm VPA is Installed**
1. Run `kubectl get vpa`. If the response says `the server does not have a resource type "vpa"`, install VPA from the official `kubernetes/autoscaler` repo.
2. Re-run `kubectl get vpa` and confirm no errors.

**Exercise 2 — Inspect VPA Recommendation**
1. Create any deployment (e.g., `nginx-deployment`) with explicit CPU and memory requests.
2. Apply a VPA in `Off` mode targeting that deployment.
3. After 2–3 minutes, run `kubectl describe vpa <name>` and read the `Lower Bound`, `Target`, and `Upper Bound` values.

**Exercise 3 — Edit the Update Mode**
1. Use `kubectl edit vpa <name>` to change `updateMode` from `Off` to `Auto`.
2. Watch the pods: `kubectl get pods --watch` — confirm old pods are terminated and new ones come up with adjusted requests.

**Exercise 4 — Verify Adjusted Requests**
1. After VPA recreates the pods in `Auto` mode, run `kubectl describe pod <new-pod>`.
2. Confirm the `Requests:` values now match VPA's recommendation (and are different from the original deployment manifest).

**Exercise 5 — Cleanup**
1. Delete the VPA: `kubectl delete vpa <name>`.
2. Delete the deployment.
3. Optionally uninstall VPA itself by running `./hack/vpa-down.sh` from the cloned `kubernetes/autoscaler` repo.

---

### Declarative (YAML-based) Exercises

**Exercise 6 — Deployment with Low Requests**
1. Write a Deployment manifest for `nginx-deployment` with **2 replicas** of `nginx`.
2. Set `requests.cpu: 50m` and `requests.memory: 50Mi`.
3. Apply and confirm both pods are running.

**Exercise 7 — VPA in `Off` Mode**
1. Write a VPA manifest (`apiVersion: autoscaling.k8s.io/v1`, `kind: VerticalPodAutoscaler`).
2. Target the `nginx-deployment` from Exercise 6.
3. Set `updateMode: "Off"`.
4. Apply and verify the VPA exists with `kubectl get vpa`.

**Exercise 8 — Switch to `Auto` Mode**
1. Edit the VPA YAML and change `updateMode` from `"Off"` to `"Auto"`.
2. Re-apply with `kubectl apply -f vpa.yaml`.
3. Confirm pods are evicted and recreated with new requests.

**Exercise 9 — VPA in `Initial` Mode**
1. Modify the VPA manifest to use `updateMode: "Initial"`.
2. Apply and verify that **already-running** pods are **NOT** touched.
3. Create a brand new pod (scale the deployment up) and verify the **new pod** uses the recommended requests.

**Exercise 10 — Simulating the Pending Risk**
1. Write a Deployment manifest with very low requests (`cpu: 10m`, `memory: 10Mi`) but a memory-hungry workload.
2. Apply a VPA in `Auto` mode targeting it.
3. Observe whether the new pod becomes `Pending` due to `Insufficient memory`. Explain *why* this happens.

**Exercise 11 — Read the Recommendation Block via YAML**
1. Run `kubectl get vpa <name> -o yaml`.
2. Locate the `status.recommendation.containerRecommendations` block.
3. Identify the four values: `lowerBound`, `target`, `uncappedTarget`, `upperBound`.

## 9. Summary

| Concept | Detail |
|---|---|
| **What it is** | A Kubernetes component that auto-adjusts CPU and memory **requests** for pods |
| **Why it exists** | Requests set too low → app crashes; set too high → wasted resources blocked on nodes |
| **Works with** | Deployment, StatefulSet, ReplicaSet, etc. (anything with a pod template) |
| **Requires** | Metrics Server installed + VPA component installed (not built-in) |
| **API group** | `autoscaling.k8s.io/v1`, `kind: VerticalPodAutoscaler` |
| **Update modes** | `Off` (recommend only), `Initial` (set on pod creation only), `Auto` (evict + recreate) |
| **Recommendation fields** | `lowerBound`, `target`, `uncappedTarget`, `upperBound` |
| **Inspect** | `kubectl get vpa`, `kubectl describe vpa <name>` |
| **Edit mode** | `kubectl edit vpa <name>` |
| **Risk** | In `Auto` mode, a higher request can leave the new pod `Pending` with `Insufficient memory/cpu` if no node has space |
| **Conflict warning** | Do **not** run VPA and HPA on the same metric for the same workload |
| **Install** | Clone `kubernetes/autoscaler`, run `./hack/vpa-up.sh` from `vertical-pod-autoscaler/` |
| **Uninstall** | `./hack/vpa-down.sh` |
