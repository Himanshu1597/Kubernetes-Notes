# Persistent Volume (PV) and Persistent Volume Claim (PVC) Notes

## 1. What is it, Why is it Used, and What Challenges Does it Solve?

### The Problem (Challenge)

When you attach a volume to a Pod, the volume can be of many types — `emptyDir`, `hostPath`, `local`, `NFS`, `EBS`, `GlusterFS`, and many others. Each volume type needs its own specific configuration inside the Pod manifest:

- **NFS** needs a `server` IP and a `path`.
- **EBS** needs AWS-specific settings.
- **GlusterFS** needs endpoints and paths.

This creates two big problems:

1. **Developers get overloaded**: A developer knows how to write a Pod manifest but may not know (or want to know) the details of NFS, EBS, or GlusterFS. Forcing them to add storage-specific fields into the Pod YAML makes the manifest complex and error-prone.
2. **No clear separation of duties**: The person creating the Pod (developer) is also forced to manage storage backend details, which should ideally be handled by a storage expert.

### The Solution

Kubernetes introduces **Persistent Volume (PV)** and **Persistent Volume Claim (PVC)** to separate these concerns:

- **Storage Administrator** creates and manages the actual storage pieces (PVs).
- **Developer** simply requests storage by creating a claim (PVC) and references that claim in the Pod.
- **Pod** uses the claim, and Kubernetes automatically wires it to the right backend storage.

> In short: PV and PVC let developers say *"I need 2 GB of storage"* without ever caring whether that storage is on NFS, EBS, or a local disk.

## 2. Define and Explain in Simple Plain English

### Persistent Volume (PV)

> A **Persistent Volume** is a piece of storage inside the Kubernetes cluster that has already been set up by an administrator (or created automatically by a StorageClass). It is a cluster-level resource that represents the actual disk space — like a hard drive partition or a network share — ready to be used by applications.

Think of a PV as a **pre-built parking spot** in a parking lot. The parking spot already exists. It has a size (capacity), a surface type (EBS, NFS, etc.), and a label (storage class). Someone (the storage admin) built it beforehand.

### Persistent Volume Claim (PVC)

> A **Persistent Volume Claim** is a request made by a user (usually a developer) for a piece of storage. It describes what the user needs — for example, *"I need 2 GB of storage with read-write access"* — and Kubernetes finds a suitable Persistent Volume that matches those needs and binds them together.

Think of a PVC as a **parking ticket request**. You go to the parking lot and say, *"I need a spot for a small car"*. The system finds an available spot that fits your request and assigns it to you.

### How They Work Together

```
Physical Storage (EBS / NFS / GlusterFS / Local Disk)
         |
         |  (Storage Admin creates)
         v
   Persistent Volume (PV)  <-- cluster-level storage object
         |
         |  (Kubernetes binds based on request)
         v
   Persistent Volume Claim (PVC)  <-- user's request
         |
         |  (Developer references in Pod)
         v
        App Pod
```

## 3. Explanation in Simple Kubernetes Terms

### The Three Layers

| Layer | What it is | Who manages it |
|---|---|---|
| **Physical Storage** | The real disk or network share (EBS volume, NFS server path, etc.) | Infrastructure / Cloud |
| **Persistent Volume (PV)** | A Kubernetes object that wraps the physical storage and makes it available in the cluster | Storage Administrator |
| **Persistent Volume Claim (PVC)** | A Kubernetes object that requests storage from the pool of PVs | Developer / User |

### Lifecycle in Kubernetes Terms

1. **Provisioning**: A PV is created. It can be:
   - **Static**: Admin manually creates PVs ahead of time.
   - **Dynamic**: Kubernetes creates PVs automatically when a PVC is made (using a StorageClass).

2. **Binding**: When a PVC is created, Kubernetes looks at all available PVs and picks one that satisfies the PVC's requirements (size, access mode, storage class). The PV status changes from `Available` to `Bound`.

3. **Using**: The developer adds the PVC name inside the Pod's `volumes` section. The Pod then gets the actual storage mounted at the specified `mountPath`.

4. **Releasing**: When the Pod is deleted, the PVC still holds the PV. Data remains.

5. **Recycling / Deleting**: When the PVC is deleted, the PV can be either retained, recycled, or deleted based on its `persistentVolumeReclaimPolicy`.

### Key Matching Rules for Binding

Kubernetes matches a PVC to a PV based on:

- **Storage Class Name**: Both must match (if specified).
- **Access Modes**: Both must be compatible (e.g., `ReadWriteOnce`).
- **Capacity**: The PV must have **at least** the capacity requested by the PVC. If you request 2 GB and the only available PV is 3 GB, Kubernetes will bind the 3 GB PV to your PVC. This does not break anything — your app simply gets more space than asked.

### Important Kubernetes Behaviors

- A PV is a **cluster-scoped** resource (not tied to a namespace).
- A PVC is a **namespace-scoped** resource (lives inside a namespace).
- One PV can be bound to **only one** PVC at a time.
- A Pod's volume section no longer points directly to storage. It points to a PVC by name.
- Once a PVC is bound to a PV, no other PVC can use that same PV until it is released.

## 4. Syntax

### Imperative (CLI)

> Note: PVs and PVCs are usually created via YAML in real environments. The CLI has limited direct support for creating them imperatively with all fields, but you can generate templates.

**Generate a PV YAML template**
```bash
kubectl run tmp --image=nginx --dry-run=client -o yaml  # not directly useful for PV
```

For PV and PVC, **declarative YAML is the standard approach**. Use `kubectl apply -f` with YAML files.

**List PVs and PVCs**
```bash
kubectl get pv
kubectl get pvc
kubectl get pvc -n <namespace>
```

**Describe to see binding details**
```bash
kubectl describe pv <pv-name>
kubectl describe pvc <pvc-name> -n <namespace>
```

**Delete in correct order**
```bash
kubectl delete pod <pod-name>
kubectl delete pvc <pvc-name>
kubectl delete pv <pv-name>
```

### Declarative (YAML)

#### Persistent Volume (PV)

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: manual-pv-1gb
spec:
  capacity:
    storage: 1Gi
  volumeMode: Filesystem
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  hostPath:
    path: /tmp/k8s-pv-1
```

| Field | Meaning |
|---|---|
| `capacity.storage` | Total size of this PV (e.g., `1Gi`, `3Gi`, `10Gi`). |
| `accessModes` | How the volume can be mounted. `ReadWriteOnce` = read-write by a single node. |
| `storageClassName` | A label/category for this PV. PVCs can request a specific class. |
| `persistentVolumeReclaimPolicy` | What happens to the PV when the PVC is deleted: `Retain`, `Recycle`, or `Delete`. |
| `hostPath` / `nfs` / `awsElasticBlockStore` | The actual backend storage type and its specific config. |

#### Persistent Volume Claim (PVC)

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: manual-pvc-2gb
  namespace: default
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: manual
  resources:
    requests:
      storage: 2Gi
```

| Field | Meaning |
|---|---|
| `resources.requests.storage` | How much storage the user is asking for. |
| `accessModes` | Must match the PV's access mode. |
| `storageClassName` | Must match the PV's storage class (if used). |

#### Pod Referencing the PVC

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: test-pod
spec:
  containers:
  - name: app-container
    image: nginx
    volumeMounts:
    - name: mydata
      mountPath: /data
  volumes:
  - name: mydata
    persistentVolumeClaim:
      claimName: manual-pvc-2gb
```

| Field | Meaning |
|---|---|
| `volumes[].persistentVolumeClaim.claimName` | The name of the PVC to use. |
| `volumeMounts[].name` | Must match the volume name defined above. |
| `volumeMounts[].mountPath` | The path inside the container where the storage appears. |

## 5. Examples

### Example 1 — Storage Admin Creates Two PVs

**PV 1 — 1 GB**
```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-1gb
spec:
  capacity:
    storage: 1Gi
  accessModes:
    - ReadWriteOnce
  storageClassName: manual
  hostPath:
    path: /tmp/pv-1
```

**PV 2 — 3 GB**
```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-3gb
spec:
  capacity:
    storage: 3Gi
  accessModes:
    - ReadWriteOnce
  storageClassName: manual
  hostPath:
    path: /tmp/pv-2
```

Apply them:
```bash
kubectl apply -f pv-1gb.yaml
kubectl apply -f pv-3gb.yaml
kubectl get pv
# STATUS: Available for both
```

### Example 2 — Developer Creates a PVC Requesting 2 GB

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: manual-pvc-2gb
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: manual
  resources:
    requests:
      storage: 2Gi
```

Apply it:
```bash
kubectl apply -f pvc.yaml
kubectl get pv
# pv-3gb is now STATUS: Bound
# pv-1gb remains STATUS: Available
```

> Kubernetes bound the 3 GB PV because no exact 2 GB PV existed. A larger PV is acceptable.

### Example 3 — Developer Creates a Pod Using the PVC

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: test-pod
spec:
  containers:
  - name: app-container
    image: nginx
    volumeMounts:
    - name: mydata
      mountPath: /data
  volumes:
  - name: mydata
    persistentVolumeClaim:
      claimName: manual-pvc-2gb
```

Apply it:
```bash
kubectl apply -f pod.yaml
kubectl describe pod test-pod
# Under Volumes: Type = PersistentVolumeClaim, ClaimName = manual-pvc-2gb
```

### Example 4 — Verify the Mount Inside the Pod

```bash
kubectl exec -it test-pod -- /bin/sh
ls /
# You will see a /data directory

cd /data
touch hello.txt
ls
# hello.txt is created inside the mounted storage
exit
```

### Example 5 — Cleanup (Correct Order)

```bash
# Step 1: Delete the Pod
kubectl delete pod test-pod

# Step 2: Delete the PVC (this releases the PV)
kubectl delete pvc manual-pvc-2gb

# Step 3: Delete the PVs (if needed)
kubectl delete pv pv-1gb
kubectl delete pv pv-3gb
```

### Example 6 — NFS-Based PV (More Real-World)

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: nfs-pv
spec:
  capacity:
    storage: 5Gi
  accessModes:
    - ReadWriteMany
  storageClassName: nfs
  nfs:
    server: 192.168.1.100
    path: /exported/path
```

> The developer never sees the NFS server IP or path. They only create a PVC with `storageClassName: nfs` and Kubernetes handles the rest.

## 6. Exercises to Practice for the CKAD Exam

### Imperative / Quick CLI Exercises

**Exercise 1 — Check Existing PVs**
1. Run `kubectl get pv`.
2. Note the `CAPACITY`, `ACCESS MODES`, `STATUS`, and `STORAGECLASS` columns.
3. Run `kubectl describe pv <any-pv-name>` and locate the `Source` section to see the backend type.

**Exercise 2 — Create a Static PV**
1. Write a PV manifest named `pv-exercise` with:
   - `capacity`: `2Gi`
   - `accessModes`: `ReadWriteOnce`
   - `storageClassName`: `manual`
   - `hostPath`: `/tmp/exercise`
2. Apply it and confirm `STATUS: Available` with `kubectl get pv`.

**Exercise 3 — Create a PVC and Watch Binding**
1. Write a PVC manifest named `pvc-exercise` requesting `1Gi` with `storageClassName: manual`.
2. Apply it.
3. Run `kubectl get pv` and confirm the PV from Exercise 2 changed to `STATUS: Bound`.
4. Run `kubectl get pvc` and confirm it shows `STATUS: Bound` and the correct `VOLUME` name.

**Exercise 4 — Create a Pod That Uses the PVC**
1. Write a Pod manifest named `pod-exercise` running `nginx`.
2. Mount a volume named `storage` at `/usr/share/nginx/html`.
3. In `volumes`, reference `pvc-exercise`.
4. Apply and verify with `kubectl describe pod pod-exercise`.

**Exercise 5 — Write Data and Verify Persistence**
1. Exec into the Pod: `kubectl exec -it pod-exercise -- /bin/sh`.
2. Create a file: `echo "CKAD Practice" > /usr/share/nginx/html/index.html`.
3. Delete the Pod: `kubectl delete pod pod-exercise`.
4. Recreate the exact same Pod (same YAML).
5. Exec again and check if `/usr/share/nginx/html/index.html` still exists.
6. It should still exist because the PVC + PV kept the data.

**Exercise 6 — Test Capacity Matching**
1. Create a PV of `5Gi` with `storageClassName: fast`.
2. Create a PVC requesting `3Gi` with `storageClassName: fast`.
3. Confirm the `5Gi` PV gets bound to the `3Gi` PVC.
4. Understand that Kubernetes prefers a larger PV over no PV at all.

**Exercise 7 — Generate YAML from Dry-Run**
1. Although `kubectl create` does not fully support PV/PVC creation via CLI flags, practice generating Pod YAML that references a PVC:
   ```bash
   kubectl run test --image=nginx --dry-run=client -o yaml > pod-template.yaml
   ```
2. Manually edit the generated YAML to add the `volumes` and `volumeMounts` sections pointing to a PVC.

### Declarative (YAML-Based) Exercises

**Exercise 8 — Multi-PV Pool**
1. Create three PVs:
   - `pv-small`: `1Gi`, `storageClassName: standard`
   - `pv-medium`: `2Gi`, `storageClassName: standard`
   - `pv-fast`: `1Gi`, `storageClassName: premium`
2. Create a PVC `pvc-standard` requesting `1Gi` with `storageClassName: standard`.
3. Confirm it binds to either `pv-small` or `pv-medium` (whichever matches best).
4. Create a PVC `pvc-premium` requesting `1Gi` with `storageClassName: premium`.
5. Confirm it binds to `pv-fast`.

**Exercise 9 — ReadWriteMany vs ReadWriteOnce**
1. Create a PV with `accessModes: ["ReadWriteMany"]` and `hostPath`.
2. Create a PVC with the same access mode.
3. Try creating two Pods in different nodes referencing the same PVC.
4. Observe that `ReadWriteMany` allows multiple nodes, while `ReadWriteOnce` restricts to one node.

**Exercise 10 — Cleanup Drill**
1. Delete the Pod.
2. Delete the PVC.
3. Check `kubectl get pv` and note whether the PV is `Released` or `Available` depending on `persistentVolumeReclaimPolicy`.
4. If policy is `Retain`, manually clean up the data on the host or cloud console.
5. Delete the PV.

**Exercise 11 — Troubleshooting a Pending PVC**
1. Create a PVC requesting `10Gi` with `storageClassName: manual`.
2. Do NOT create any PV.
3. Run `kubectl get pvc` and confirm `STATUS: Pending`.
4. Run `kubectl describe pvc <name>` and read the events to understand why it is pending (no matching PV found).
5. Now create a PV of `10Gi` with the same storage class.
6. Confirm the PVC automatically moves to `Bound`.

**Exercise 12 — Describe and Inspect**
1. With a bound Pod running, run:
   ```bash
   kubectl get pod <pod-name> -o yaml
   ```
2. Trace the `spec.volumes` section to see the PVC name.
3. Run `kubectl get pvc <pvc-name> -o yaml` and trace the `spec.volumeName` to find the bound PV.
4. Run `kubectl get pv <pv-name> -o yaml` and trace the `spec` to find the actual backend (e.g., `hostPath.path`).

## Important Notes from Q&A

> **Q: In which storage type (EBS, NFS, etc.) is the PV and PVC actually created?**
>
> **A:** The `storageClassName` field is **just a label/tag** used for matching PVC to PV. It is **NOT** the actual storage type.
>
> The real storage type and its backend-specific configuration are defined inside the PV manifest itself:
> - `hostPath` → `spec.hostPath.path`
> - `NFS` → `spec.nfs.server` + `spec.nfs.path`
> - `EBS` → `spec.awsElasticBlockStore.volumeID`
> - `GCE PD` → `spec.gcePersistentDisk.pdName`
>
> Two PVs can have the same `storageClassName` (e.g., `manual`) but use completely different backends (one hostPath, one NFS). The PVC only sees the label and has no idea what the actual backend is.

---

> **Q: Whose responsibility is it to create the PV manifest file?**
>
> **A:** The **Storage Administrator** (or Cluster Administrator).
>
> The admin is the expert who knows the backend details — NFS server IPs, EBS volume IDs, node paths, cloud credentials, etc. They create the pool of PVs so developers don't have to deal with any storage-specific configuration.
>
> The **Developer** only creates:
> 1. The **PVC** — to request storage (size, access mode, storage class label)
> 2. The **Pod** — to reference the PVC by name
>
> The developer never touches the PV manifest and never needs to know whether the storage is EBS, NFS, or hostPath.

## 7. Summary

| Concept | Detail |
|---|---|
| **Persistent Volume (PV)** | Cluster-level storage object provisioned by an admin. Represents actual disk space. |
| **Persistent Volume Claim (PVC)** | Namespace-level request for storage. Binds to a matching PV. |
| **Who creates PV** | Storage Administrator (static) or StorageClass + Provisioner (dynamic). |
| **Who creates PVC** | Developer / User who needs storage for their application. |
| **Binding rules** | Matches on `storageClassName`, `accessModes`, and capacity (PV >= PVC request). |
| **Pod usage** | Pod references the PVC by name in `volumes` and mounts it via `volumeMounts`. |
| **Scope** | PV is cluster-scoped; PVC is namespace-scoped. |
| **Capacity behavior** | A PVC requesting 2 GB can bind to a 3 GB PV if no exact match exists. |
| **Reclaim Policy** | `Retain` (keep data), `Delete` (remove data), or `Recycle` (wipe and reuse). |
| **Access Modes** | `ReadWriteOnce`, `ReadOnlyMany`, `ReadWriteMany`. |
| **Cleanup order** | Delete Pod first, then PVC, then PV. |
| **CKAD tip** | Always remember the three-step workflow: **Create PV → Create PVC → Reference PVC in Pod**. |
