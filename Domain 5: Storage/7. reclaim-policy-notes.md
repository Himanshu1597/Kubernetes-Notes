# Reclaim Policy — Domain 4: Storage

---

## 1. Recap: Where Reclaim Policy Fits

| Concept | What it does |
|---|---|
| **PersistentVolume (PV)** | The actual piece of storage in the cluster. |
| **PersistentVolumeClaim (PVC)** | A user's request for storage; binds to a PV. |
| **StorageClass** | Defines how PVs are dynamically provisioned. |
| **Reclaim Policy** | Decides **what happens to the PV and its underlying storage** after the bound PVC is deleted. |

This note focuses on **Reclaim Policy**. For related topics, see [pv-provisioning-notes.md](pv-provisioning-notes.md), [storage-class-notes.md](storage-class-notes.md), and [access-modes-notes.md](access-modes-notes.md).

---

## 2. What is a Reclaim Policy?

> The **Reclaim Policy** is a setting on a PersistentVolume that specifies what happens to **the PV object and its underlying storage** after the **PVC** that was bound to it is **deleted**.

In plain English: *"When the user is done with this storage, do I delete it, or keep it for later?"*

```
   ┌─────────┐ Claimed ┌─────────┐
   │   PVC    │ ◄─────► │   PV     │ ───► underlying storage
   └─────────┘         └─────────┘
        │
        │ user deletes PVC
        ▼
        ✗
        ?  what should happen to the PV?
           → "Delete" → remove the PV + storage
           → "Retain" → keep the PV + storage
```

---

## 3. Why Reclaim Policy — What Challenges Does It Solve?

### Challenge 1: Critical Data Should Not Be Auto-Deleted

If a database's PVC is accidentally deleted, you do **not** want the underlying volume (and all its data) to vanish. That would be catastrophic.

**Reclaim Policy `Retain` solves this** by keeping the PV and its data even after the PVC is gone — the admin can recover it.

---

### Challenge 2: Temporary Workloads Should Not Leak Storage

For short-lived workloads (CI jobs, scratch work), you do not want orphaned volumes lingering in your cloud account, burning money.

**Reclaim Policy `Delete` solves this** by automatically removing the PV and the underlying storage when the PVC is deleted. Clean, automatic.

---

### Challenge 3: Different Workloads Need Different Behaviour

You might want `fast-ssd` storage to auto-clean and `db-storage` to retain. Both can exist in the same cluster.

**Reclaim Policy solves this** by being configurable per-StorageClass (for dynamic provisioning) and per-PV (for static provisioning).

---

## 4. The Two Reclaim Policies

| Policy | What happens when PVC is deleted |
|---|---|
| **Delete** (default) | The PV object in Kubernetes **and** the underlying storage volume in the infrastructure are **both deleted**. Data is lost. |
| **Retain** | The PV object **remains** in Kubernetes with status `Released`. The underlying storage and its data are **preserved**. Admin must clean up manually. |

> There used to be a third policy called **`Recycle`** — it has been **deprecated** and removed. Do not use it.

---

## 5. Default Behaviour

> If you create a StorageClass and do **not** specify `reclaimPolicy`, the default is **`Delete`**.

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: standard
provisioner: kubernetes.io/aws-ebs
# no reclaimPolicy specified → defaults to Delete
```

---

## 6. Where Can Reclaim Policy Be Set?

It can be set in **two places**:

### A. On a PersistentVolume (used for **static** provisioning)

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv0003
spec:
  capacity:
    storage: 5Gi
  volumeMode: Filesystem
  accessModes:
  - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain         # ◄── set here
  nfs:
    path: /tmp
    server: 172.17.0.2
```

### B. On a StorageClass (used for **dynamic** provisioning)

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: standard
provisioner: kubernetes.io/aws-ebs
reclaimPolicy: Retain                            # ◄── set here
```

> When dynamic provisioning is used, the PV inherits its reclaim policy from the StorageClass. So in practice, you almost always set it on the StorageClass.

---

## 7. Side-by-Side Behaviour

| Aspect | Retain | Delete |
|---|---|---|
| **Data Retention After PVC Deletion** | ✓ Data is preserved | ✗ Underlying storage is deleted |
| **Underlying Storage Reused Automatically** | ✗ No — requires manual intervention | ✓ Storage is deleted and cleaned up |
| **Manual Admin Cleanup Needed** | ✓ Admin must delete or reuse the volume | ✗ Handled automatically |
| **Use Case** | Critical data, backups, manual recovery | Temporary or dynamically provisioned data |
| **Common Storage Backend Support** | All backends | Dynamic provisioners (AWS EBS, GCE PD, etc.) |
| **Recommended For** | Long-term storage, compliance, audits | Short-lived workloads, automation |

## 8. Demo Walkthrough

### Demo 1 — Delete Policy

```bash
# StorageClass: do-block-storage  (reclaimPolicy: Delete)

# 1. No PVs yet
kubectl get pv
# (empty)

# 2. Create a PVC
kubectl apply -f pvc-delete.yaml
kubectl get pv
# pvc-...   1Gi   RWO   Delete   Bound   default/demo-pvc

# 3. Verify in cloud console — a DigitalOcean Volume was created

# 4. Delete the PVC
kubectl delete pvc demo-pvc

# 5. Check PV — it is gone
kubectl get pv
# (empty)

# 6. Verify in cloud console — the Volume is also deleted. Data lost.
```

### Demo 2 — Retain Policy

```bash
# StorageClass: do-block-storage-retain  (reclaimPolicy: Retain)

# 1. Create a PVC referencing the retain class
kubectl apply -f pvc-retain.yaml
kubectl get pv
# pvc-...   1Gi   RWO   Retain   Bound   default/demo-pvc

# 2. Delete the PVC
kubectl delete pvc demo-pvc

# 3. Check PV — it is still there
kubectl get pv
# pvc-...   1Gi   RWO   Retain   Released   default/demo-pvc

# 4. The status is now Released — bound PVC is gone, but PV and data are intact.

# 5. The cloud Volume still exists; admin must decide to keep, reuse, or delete it.
```

> **`Released` status** = the PV is no longer bound to a PVC but its data is preserved. A new PVC cannot bind to it directly until an admin manually cleans the PV (or recreates it).

## 9. Syntax — Quick Reference

### On a StorageClass

```yaml
reclaimPolicy: Retain    # or Delete
```

### On a PersistentVolume

```yaml
spec:
  persistentVolumeReclaimPolicy: Retain    # or Delete
```

### Inspect

```bash
kubectl get pv
# look at the RECLAIM POLICY column

kubectl get sc
# look at the RECLAIMPOLICY column

kubectl describe pv <name>
kubectl describe sc <name>
```

### Patch an Existing PV

```bash
kubectl patch pv <pv-name> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'
```

> Useful when you realise a PV is using `Delete` but actually holds critical data — you can switch it to `Retain` to prevent accidental loss.

## 10. Examples

### Example 1 — StorageClass with Retain

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: db-storage
provisioner: kubernetes.io/aws-ebs
parameters:
  type: gp3
reclaimPolicy: Retain
allowVolumeExpansion: true
```

Any PVC using `storageClassName: db-storage` gets a PV with reclaim policy `Retain`.

### Example 2 — Static PV with Retain

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: critical-data-pv
spec:
  capacity:
    storage: 10Gi
  accessModes:
  - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  hostPath:
    path: /mnt/critical
```

### Example 3 — Two StorageClasses, Different Policies

```yaml
# Auto-clean storage for scratch data
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: scratch
provisioner: kubernetes.io/aws-ebs
reclaimPolicy: Delete
---
# Retained storage for important data
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: important
provisioner: kubernetes.io/aws-ebs
reclaimPolicy: Retain
```

## 11. Exercises to Practice for the CKAD Exam

### Imperative (CLI-based) Exercises

**Exercise 1 — Inspect Existing Reclaim Policies**
1. Run `kubectl get sc` and identify the `RECLAIMPOLICY` of each StorageClass.
2. Run `kubectl get pv` and confirm each PV's reclaim policy matches its StorageClass.

**Exercise 2 — Test Delete Policy**
1. Find a StorageClass with `reclaimPolicy: Delete`.
2. Create a PVC referencing it.
3. Confirm a PV was created.
4. Delete the PVC.
5. Confirm the PV is also gone (`kubectl get pv` shows nothing).

**Exercise 3 — Test Retain Policy**
1. Find a StorageClass with `reclaimPolicy: Retain`.
2. Create a PVC referencing it.
3. Confirm a PV was created.
4. Delete the PVC.
5. Confirm the PV is **still there**, with status `Released`.
6. Clean it up: `kubectl delete pv <name>`.

**Exercise 4 — Patch a PV's Reclaim Policy**
1. Find any PV with `Delete` policy.
2. Patch it to `Retain`:
   `kubectl patch pv <name> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'`
3. Verify with `kubectl get pv`.

---

### Declarative (YAML-based) Exercises

**Exercise 5 — Write a Retain StorageClass**
1. Write a StorageClass manifest with `reclaimPolicy: Retain`.
2. Apply.
3. Create a PVC referencing it. Confirm the resulting PV inherits `Retain`.

**Exercise 6 — Write a Static PV with Retain**
1. Write a `PersistentVolume` manifest with `persistentVolumeReclaimPolicy: Retain`, `storageClassName: manual`, `hostPath`, `1Gi`, `RWO`.
2. Apply.
3. Create a matching PVC and observe the binding.
4. Delete the PVC. Confirm the PV stays with status `Released`.

**Exercise 7 — Two StorageClasses Side-by-Side**
1. Write two StorageClasses: one `Delete`, one `Retain`, both with the same provisioner.
2. Apply both.
3. Create one PVC against each.
4. Delete both PVCs — observe one PV disappear, one stay `Released`.

**Exercise 8 — Default Policy When Unspecified**
1. Write a StorageClass manifest **without** `reclaimPolicy`.
2. Apply.
3. Inspect with `kubectl describe sc <name>` and confirm the policy defaults to **`Delete`**.

**Exercise 9 — Convert Released PV to Available (Advanced)**
1. Create a PVC against a Retain StorageClass, then delete the PVC. The PV is now `Released`.
2. Edit the PV manifest (`kubectl edit pv <name>`) and **remove the `spec.claimRef` field**.
3. Confirm the PV's status returns to `Available` and can be bound by a new PVC.

## 12. Summary

| Concept | Detail |
|---|---|
| **What it is** | Decides what happens to a PV (and its storage) when the bound PVC is deleted |
| **Two values** | `Delete` (default) and `Retain` |
| **Delete** | Removes PV + underlying storage; data is lost |
| **Retain** | Keeps PV + storage; status becomes `Released`; admin must clean up |
| **Default when omitted** | `Delete` |
| **Deprecated** | `Recycle` policy is removed — do not use |
| **Set on StorageClass (dynamic)** | `reclaimPolicy: Retain` |
| **Set on PV (static)** | `spec.persistentVolumeReclaimPolicy: Retain` |
| **Patch an existing PV** | `kubectl patch pv <name> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'` |
| **Released status** | PV no longer bound but data preserved; cannot be re-bound until admin clears `claimRef` |
| **Recommended for** | Critical data → `Retain` ; ephemeral data → `Delete` |
