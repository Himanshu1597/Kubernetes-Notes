# Kubernetes Volumes — Domain 4: Storage

---

## 1. What is a Volume?

> A **Volume** in Kubernetes is a piece of storage that is attached to a Pod, so containers can **read and write files that survive container restarts** and can be **shared across containers** in the same Pod.

By default, every container has its own private file system that is **wiped clean** when the container restarts. A Volume is the way to keep data alive beyond that.

```
   ┌──────────────────────────────────┐
   │                Pod                │
   │   ┌──────────┐    ┌──────────┐    │
   │   │ Container│    │ Container│    │
   │   │    1     │    │    2     │    │
   │   └────┬─────┘    └────┬─────┘    │
   │        │ /data         │ /data    │
   │        ▼               ▼          │
   │        ┌────────────────┐          │
   │        │     Volume     │          │
   │        └────────────────┘          │
   └──────────────────────────────────┘
```

---

## 2. Why Volumes — What Challenges Do They Solve?

### Challenge 1: State Persistence (Data Loss on Restart)

When a container **crashes** or a pod **restarts**, the container state is **NOT saved**. The kubelet restarts the container from the **base image** — every file created after launch (logs, user data, generated files) is **lost**.

> Example from the transcript: A BusyBox pod creates `/tmp/important-file.txt`. After the 100s `sleep` finishes and the container restarts, the file is gone.

**Volumes solve this** by storing data in a Volume that lives outside the container's file system. When the container restarts, the data is still there.

```
   Pod Before Restart            Pod After Restart
   ┌──────────────────┐          ┌──────────────────┐
   │ Running Container│          │  New Container   │
   │ ┌──────┐ ┌──────┐│   ──►    │ ┌──────┐ ┌──────┐│
   │ │Config│ │App   ││  crash   │ │Config│ │App   ││
   │ │      │ │Data  ││  & restart│ │      │ │Data  ││
   │ └──────┘ └──────┘│          │ └──────┘ └──────┘│
   │ ┌──────┐ ┌──────┐│          │  ✗ Generated     │
   │ │Gen.  │ │User  ││          │  ✗ User Data     │
   │ │Files │ │Data  ││          │     LOST         │
   │ └──────┘ └──────┘│          └──────────────────┘
   └──────────────────┘
```

---

### Challenge 2: Shared Storage Between Containers / Pods

In a **multi-container pod**, each container has its own file system. Container-1 cannot see files written by Container-2.

> Example from the transcript: BusyBox container-1 creates `/tmp/container1.txt`, but BusyBox container-2 cannot see it.

**Volumes solve this** by giving one shared storage area that **all containers** in the pod mount. The same volume can also be attached to **multiple pods**, so different pods can share files.

```
            ┌──────────────────────┐
            │    Multi-Pod Setup    │
            │                       │
            │   ┌─────────────┐     │
            │   │ Database Pod│ ──┐  │
            │   └─────────────┘   │  │            ┌────────┐
            │                     ├──┼──────────► │ Volume │
            │   ┌─────────────┐   │  │            └────────┘
            │   │ Analytic Pod│ ──┘  │
            │   └─────────────┘     │
            └──────────────────────┘
```

## 3. How Volumes Work in Kubernetes (Simple Terms)

1. You declare a **Volume** in the pod's `spec.volumes`. This says: *"There is a volume named X of this type."*
2. Inside each container's `spec.containers[].volumeMounts`, you say: *"Mount the volume named X at this path inside me."*
3. When the pod starts, that path inside the container is **backed by the volume** instead of the container's own filesystem.
4. Reads/writes at that path go to the volume — and depending on the volume **type**, data may persist beyond the pod.

> **Volume = storage definition (pod-level).**
> **volumeMount = how a container uses that storage (container-level).**

---

## 4. Types of Volumes

Kubernetes offers many volume types. Pick the type based on the use case.

| Type | What it is | Common Use | Covered In |
|---|---|---|---|
| **emptyDir** | A temporary directory created when the pod starts; deleted when the pod is removed. | Sharing files between containers in the same pod. | [emptydir-volume-notes.md](emptydir-volume-notes.md) |
| **hostPath** | Mounts a file or directory from the **worker node's** filesystem into the pod. | Reading node logs, node config, or writing persistent data on the node. | [hostpath-volume-notes.md](hostpath-volume-notes.md) |
| **configMap** | Mounts a ConfigMap as files. | Injecting config files into a container. | — |
| **secret** | Mounts a Secret as files. | Injecting credentials into a container. | — |
| **nfs** | Mounts an NFS share. | Network shared storage across pods. | — |
| **persistentVolumeClaim (PVC)** | Mounts a cluster-managed persistent volume. | Production storage that outlives pods. | — |
| **local** | A locally-attached storage device on a node. | Specific node-bound persistent storage. | — |

> Some older volume types are **deprecated or removed** in newer Kubernetes versions — always check the docs before using one in production.

## 5. Ephemeral vs Persistent Volumes

| | Ephemeral Volume | Persistent Volume |
|---|---|---|
| **Lifetime** | Tied to the Pod — destroyed when the pod is removed | Lives independently of any Pod |
| **Examples** | `emptyDir`, `configMap`, `secret` | `persistentVolumeClaim`, `nfs`, cloud disks |
| **Use case** | Short-term shared data between containers | Long-lived data (databases, user uploads) that must survive pod restarts |

```
   Ephemeral:                  Persistent:
                                 ┌─────────────┐
   Pod 1 ── EphVol               │  Pod 1      │ ──┐
   ✗ When pod ends, vol gone     └─────────────┘   │
                                                    ├── PersistentVolume
                                  ┌─────────────┐   │     (still here!)
                                  │  Pod 2      │ ──┘
                                  └─────────────┘
```

## 6. Volume and VolumeMounts (The Two Key Fields)

To use a volume in a Pod, you always need **both**:

- **`.spec.volumes[]`** — defines what volumes exist for this Pod (name + type).
- **`.spec.containers[].volumeMounts[]`** — tells each container where to mount each named volume.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: test-pd
spec:
  containers:
  - image: nginx:latest
    name: test-container
    volumeMounts:                # WHERE to mount (per-container)
    - mountPath: /my-data
      name: data-volume
  volumes:                       # WHAT volumes exist (pod-level)
  - name: data-volume
    emptyDir:
      sizeLimit: 500Mi
```

> The **name** in `volumeMounts.name` must exactly match a **name** in `volumes`.

## 7. Syntax Cheat Sheet (Generic)

### Define a Volume (Pod-Level)

```yaml
spec:
  volumes:
  - name: <volume-name>
    <volume-type>:
      ...type-specific options...
```

### Mount a Volume Inside a Container

```yaml
spec:
  containers:
  - name: <container-name>
    volumeMounts:
    - name: <volume-name>      # must match a volume name above
      mountPath: <path-in-container>
      readOnly: false           # optional
```

### Inspect Volumes in a Pod

```bash
kubectl describe pod <pod-name>
# Look for the "Volumes:" and "Mounts:" sections.
```

### Useful Commands

```bash
kubectl exec -it <pod> -c <container> -- sh   # connect to a specific container in a multi-container pod
kubectl get pods -w                            # watch pod restarts/events
kubectl delete pod <pod>                       # remove pod (ephemeral volumes go with it)
```

## 8. Examples

### Example 1 — Demonstrating Data Loss Without a Volume

```bash
kubectl run busybox --image=busybox --command -- sleep 100
kubectl exec -it busybox -- sh
cd /tmp
touch important-file.txt
exit

# After 100s, pod restarts
kubectl get pods -w
# busybox  1/1  Running   0  0s
# busybox  0/1  Completed 0  100s
# busybox  1/1  Running   1  103s   <- RESTART

# File is gone
kubectl exec -it busybox -- ls /tmp
# (empty)
```

This is the core problem volumes solve.

---

### Example 2 — A Minimal Pod with a Volume

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: volume-demo
spec:
  containers:
  - name: app
    image: busybox
    command: ["sleep", "3600"]
    volumeMounts:
    - name: my-data
      mountPath: /data
  volumes:
  - name: my-data
    emptyDir: {}
```

`/data` inside the container is now backed by the `my-data` volume.

## 9. Exercises to Practice for the CKAD Exam

> These are general volume-concept exercises. Type-specific exercises are in [emptydir-volume-notes.md](emptydir-volume-notes.md) and [hostpath-volume-notes.md](hostpath-volume-notes.md).

### Imperative (CLI-based) Exercises

**Exercise 1 — Observe Data Loss**
1. Create a BusyBox pod that sleeps for 60 seconds (`kubectl run busybox --image=busybox --command -- sleep 60`).
2. Exec into it and create `/tmp/data.txt`.
3. Wait for the pod to restart and confirm the file is gone.

**Exercise 2 — Inspect a Pod's Volumes**
1. Apply any pod manifest that uses a volume.
2. Run `kubectl describe pod <name>` and identify the `Volumes:` section and each container's `Mounts:` section.

**Exercise 3 — Connect to a Specific Container**
1. Apply a multi-container pod with a shared volume.
2. `kubectl exec -it <pod> -c <container-name> -- sh` to access each container individually.

---

### Declarative (YAML-based) Exercises

**Exercise 4 — Single-Container Pod with a Volume**
1. Write a Pod manifest where one container mounts an `emptyDir` at `/cache`.
2. Apply and verify by `kubectl describe pod`.

**Exercise 5 — Wrong Volume Name (Negative Test)**
1. Write a Pod where the `volumeMounts.name` does NOT match the `volumes.name`.
2. Apply and observe the validation/error.
3. Fix the name and re-apply.

**Exercise 6 — Ephemeral Lifetime Behaviour**
1. Apply a Pod with an `emptyDir`.
2. Exec in, write a file, delete the pod.
3. Re-create the pod with the same manifest and confirm the file is gone (because `emptyDir` is ephemeral).

## 10. Summary

| Concept | Detail |
|---|---|
| **What a Volume is** | Storage attached to a Pod that survives container restarts and can be shared between containers |
| **Why use Volumes** | (1) Persist data across container crashes/restarts, (2) Share files between containers in a pod |
| **Volume vs volumeMount** | `volumes` (pod-level) declares storage; `volumeMounts` (container-level) places it at a path |
| **Ephemeral types** | `emptyDir`, `configMap`, `secret` — live only as long as the pod does |
| **Persistent types** | `persistentVolumeClaim`, `nfs`, cloud disks — live independently of any Pod |
| **Naming rule** | `volumeMounts.name` must match a name in `volumes` |
| **Default container FS behaviour** | Wiped on every container restart — that is the reason volumes exist |
| **Deprecation note** | Some volume types are deprecated/removed in newer Kubernetes versions — check docs before production use |
