# Kubernetes Volumes — Simplified Notes

---

## 1. What is a Volume?

> A **Volume** in Kubernetes is a piece of storage that is attached to a **Pod**. Containers inside that Pod can read and write files to it.

```
   ┌──────────────────────────────────┐
   │                Pod                │
   │   ┌──────────┐    ┌──────────┐    │
   │   │ Container│    │ Container│    │
   │   │    1     │    │    2     │    │
   │   └────┬─────┘    └────┬─────┘    │
   │        │ /data         │ /data    │
   │        ▼               ▼          │
   │        ┌────────────────┐          │
   │        │     Volume     │          │
   │        └────────────────┘          │
   └──────────────────────────────────┘
```

By default, every container has its own private file system. When a container crashes or a Pod restarts, the container's file system is **wiped clean** and the container starts fresh from the image.

A Volume solves this by providing storage that:
- **Survives container restarts** within the same Pod
- **Can be shared** between multiple containers in the same Pod

---

## 2. What Problem Does It Solve? (Real Scenario)

### The Problem: Data Disappears When a Container Restarts

Imagine you have a simple application running in a Pod. The app writes logs to a file:

```
/var/log/app/access.log
```

One day, the app crashes. Kubernetes automatically restarts the container. But when the new container starts:

- **The log file is gone.**
- The new container started fresh from the Docker image.
- Everything that was written after the image was built is lost.

**This is the default behavior of every container in Kubernetes.**

```
   Pod Before Restart            Pod After Restart
   ┌──────────────────┐          ┌──────────────────┐
   │ Running Container│          │  New Container   │
   │ ┌──────┐ ┌──────┐│   ──►    │ ┌──────┐ ┌──────┐│
   │ │Config│ │App   ││  crash   │ │Config│ │App   ││
   │ │      │ │Data  ││  & restart│ │      │ │Data  ││
   │ └──────┘ └──────┘│          │ └──────┘ └──────┘│
   │ ┌──────┐ ┌──────┐│          │  ✗ Generated     │
   │ │Gen.  │ │User  ││          │  ✗ User Data     │
   │ │Files │ │Data  ││          │     LOST         │
   │ └──────┘ └──────┘│          └──────────────────┘
   └──────────────────┘
```

### The Solution: Attach a Volume

You attach a Volume to the Pod and tell the container:
> *"When you write to `/var/log/app`, actually write to the Volume instead of your own file system."*

Now when the container crashes and restarts:
- The new container mounts the same Volume.
- The log file is still there.
- Nothing is lost.

## 3. How Volumes Work in Kubernetes

To use a Volume in a Pod, you always need **two things**:

### Part 1: `spec.volumes` (Pod-level)
This declares what volumes exist for this Pod. You give each volume a **name** and a **type**.

```yaml
volumes:
- name: my-data
  emptyDir: {}
```

### Part 2: `spec.containers[].volumeMounts` (Container-level)
This tells each container **where** to mount each named volume inside its own file system.

```yaml
volumeMounts:
- name: my-data
  mountPath: /data
```

> **Rule:** The `name` in `volumeMounts` must exactly match a `name` in `volumes`.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: volume-demo
spec:
  containers:
  - name: app
    image: busybox
    command: ["sleep", "3600"]
    volumeMounts:              # WHERE to mount (per container)
    - name: my-data
      mountPath: /data
  volumes:                     # WHAT volumes exist (pod-level)
  - name: my-data
    emptyDir: {}
```

In this example:
- The Pod declares a volume called `my-data` of type `emptyDir`
- The container `app` mounts that volume at the path `/data`
- Any file written to `/data` inside the container is actually stored in the Volume

## 4. Types of Volumes

Kubernetes supports many volume types. You choose based on what you need.

| Type | What It Is | Common Use | Covered In |
|------|-----------|------------|------------|
| **emptyDir** | A temporary directory created when the Pod starts; deleted when the Pod is removed. | Sharing files between containers in the same pod. | emptydir-volume-notes.md |
| **hostPath** | Mounts a file or directory from the **worker node's** file system into the Pod. | Reading node logs, node config, or writing persistent data on the node. | hostpath-volume-notes.md |
| **configMap** | Mounts a ConfigMap as files. | Injecting config files into a container. | — |
| **secret** | Mounts a Secret as files. | Injecting credentials into a container. | — |
| **nfs** | Mounts an NFS share. | Network shared storage across pods. | — |
| **persistentVolumeClaim (PVC)** | Mounts a cluster-managed persistent volume. | Production storage that outlives pods. | — |
| **local** | A locally-attached storage device on a node. | Specific node-bound persistent storage. | — |

> Some older volume types are deprecated or removed in newer Kubernetes versions — always check the docs before using one in production.

## 5. Ephemeral vs Persistent Volumes

| | Ephemeral Volume | Persistent Volume |
|---|---|---|
| **Lifetime** | Tied to the Pod — destroyed when the pod is removed | Lives independently of any Pod |
| **Examples** | `emptyDir`, `configMap`, `secret` | `persistentVolumeClaim`, `nfs`, cloud disks |
| **Use case** | Short-term shared data between containers | Long-lived data (databases, user uploads) that must survive pod restarts |

**Key difference:**
- **Ephemeral:** Pod dies → Volume dies → Data is gone
- **Persistent:** Pod dies → Volume stays → New Pod can reattach and see the old data

```
   Ephemeral:                  Persistent:
                                 ┌─────────────┐
   Pod 1 ── EphVol               │  Pod 1      │ ──┐
   ✗ When pod ends, vol gone     └─────────────┘   │
                                                    ├── PersistentVolume
                                  ┌─────────────┐   │     (still here!)
                                  │  Pod 2      │ ──┘
                                  └─────────────┘
```

## 6. Volume and VolumeMounts (The Two Key Fields)

To use a volume in a Pod, you always need **both**:

- **`.spec.volumes[]`** — defines what volumes exist for this Pod (name + type).
- **`.spec.containers[].volumeMounts[]`** — tells each container where to mount each named volume.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: test-pd
spec:
  containers:
  - image: nginx:latest
    name: test-container
    volumeMounts:                # WHERE to mount (per-container)
    - mountPath: /my-data
      name: data-volume
  volumes:                       # WHAT volumes exist (pod-level)
  - name: data-volume
    emptyDir:
      sizeLimit: 500Mi
```

> The **name** in `volumeMounts.name` must exactly match a **name** in `volumes`.

## 7. Syntax Cheat Sheet (Generic)

### Define a Volume (Pod-Level)
```yaml
spec:
  volumes:
  - name: <volume-name>
    <volume-type>:
      ...type-specific options...
```

### Mount a Volume Inside a Container
```yaml
spec:
  containers:
  - name: <container-name>
    volumeMounts:
    - name: <volume-name>        # must match a volume name above
      mountPath: <path-in-container>
      readOnly: false             # optional
```

### Inspect Volumes in a Pod
```bash
kubectl describe pod <pod-name>
# Look for the "Volumes:" and "Mounts:" sections.
```

### Useful Commands
```bash
kubectl exec -it <pod> -c <container> -- sh   # connect to a specific container in a multi-container pod
kubectl get pods -w                            # watch pod restarts/events
kubectl delete pod <pod>                       # remove pod (ephemeral volumes go with it)
```

## 8. Examples

### Example 1 — Demonstrating Data Loss Without a Volume

```bash
kubectl run busybox --image=busybox --command -- sleep 100
kubectl exec -it busybox -- sh
cd /tmp
touch important-file.txt
exit

# After 100s, pod restarts
kubectl get pods -w
# busybox  1/1  Running   0  0s
# busybox  0/1  Completed 0  100s
# busybox  1/1  Running   1  103s   <- RESTART

# File is gone
kubectl exec -it busybox -- ls /tmp
# (empty)
```

This is the core problem volumes solve.

---

### Understanding: Why Does the Pod Restart Instead of Getting Deleted?

When you run:
```bash
kubectl run busybox --image=busybox --command -- sleep 60
```

You might expect: *"After 60 seconds, the command finishes, so the Pod should be deleted."*

**But that is NOT what happens.** The Pod restarts the container and keeps running forever.

#### Why? Because of `restartPolicy: Always`

By default, `kubectl run` creates a Pod with `restartPolicy: Always`. This means:
- When the container exits, Kubernetes **automatically restarts it**
- The Pod itself **never deletes itself**
- It just loops: run → exit → restart → run → exit → restart...

#### What actually happens (step by step)

| Time | What Happens |
|------|-------------|
| `0s` | Pod created, container starts, runs `sleep 60` |
| `60s` | `sleep` finishes, container **exits** |
| `60s` | Kubernetes sees exit, **restarts** the container (RESTART count = 1) |
| `120s` | `sleep` finishes again, container exits |
| `120s` | Kubernetes **restarts again** (RESTART count = 2) |
| ... | Loop continues forever until **you manually delete the Pod** |

#### The three restart policies

| Policy | What Happens When Container Exits |
|--------|-----------------------------------|
| **`Always`** (default for `kubectl run`) | Container is **restarted** forever. Pod stays. |
| **`OnFailure`** | Restarted only if exit code is non-zero (failure). Pod stays. |
| **`Never`** | **Not restarted**. Pod stays in `Completed` state. |

#### How to see it happening
```bash
kubectl run busybox --image=busybox --command -- sleep 60
kubectl get pods -w
```

Output:
```
busybox   1/1   Running     0   5s
busybox   0/1   Completed   0   60s
busybox   1/1   Running     1   61s     ← RESTARTED (count = 1)
busybox   0/1   Completed   1   120s
busybox   1/1   Running     2   121s    ← RESTARTED again (count = 2)
```

#### How to make the Pod NOT restart (run once and stay Completed)

You must write a YAML file with `restartPolicy: Never`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: busybox-once
spec:
  restartPolicy: Never
  containers:
  - name: busybox
    image: busybox
    command: ["sleep", "60"]
```

Apply it:
```bash
kubectl apply -f busybox-once.yaml
```

Now when `sleep 60` finishes:
- The container exits
- Kubernetes sees `restartPolicy: Never`
- **It does NOT restart**
- The Pod stays in `Completed` state
- It never gets deleted unless you run `kubectl delete pod busybox-once`

> **Key Point:** A standalone Pod created by `kubectl run` does NOT delete itself. It restarts forever by default. You must manually delete it with `kubectl delete pod <name>`.

---

### Example 2 — A Minimal Pod with a Volume

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: volume-demo
spec:
  containers:
  - name: app
    image: busybox
    command: ["sleep", "3600"]
    volumeMounts:
    - name: my-data
      mountPath: /data
  volumes:
  - name: my-data
    emptyDir: {}
```

`/data` inside the container is now backed by the `my-data` volume.

Apply and verify:
```bash
kubectl apply -f volume-demo.yaml
kubectl describe pod volume-demo
```

## 9. Exercises to Practice for the CKAD Exam

> These are general volume-concept exercises. Type-specific exercises are in emptydir-volume-notes.md and hostpath-volume-notes.md.

### Imperative (CLI-based) Exercises

**Exercise 1 — Observe Data Loss**

1. Create a BusyBox pod that sleeps for 60 seconds:
   ```bash
   kubectl run busybox --image=busybox --command -- sleep 60
   ```
2. Exec into it and create `/tmp/data.txt`:
   ```bash
   kubectl exec -it busybox -- sh
   cd /tmp
   touch data.txt
   echo "important data" > data.txt
   exit
   ```
3. Wait for the pod to finish and restart. Watch it:
   ```bash
   kubectl get pods -w
   ```
4. Once it restarts, check if the file is still there:
   ```bash
   kubectl exec -it busybox -- ls /tmp
   ```
5. **Expected result:** The file is gone. This proves why volumes are needed.

---

**Exercise 2 — Inspect a Pod's Volumes**

1. Apply any pod manifest that uses a volume (use Example 2 above).
2. Run:
   ```bash
   kubectl describe pod <pod-name>
   ```
3. Identify these sections in the output:
   - `Volumes:` — shows what volumes exist and their types
   - `Mounts:` under each container — shows where each volume is mounted
4. Confirm that every `volumeMounts.name` has a matching entry in `Volumes:`.

---

**Exercise 3 — Connect to a Specific Container**

1. Apply a multi-container pod with a shared volume.
2. `kubectl exec -it <pod> -c <container-name> -- sh` to access each container individually.
3. From one container, write a file to the shared mount path.
4. From the other container, read that same file.
5. **Expected result:** Both containers see the same file because they share the same Volume.

---

### Declarative (YAML-based) Exercises

**Exercise 4 — Single-Container Pod with a Volume**

1. Write a Pod manifest where one container mounts an `emptyDir` at `/cache`:
   ```yaml
   apiVersion: v1
   kind: Pod
   metadata:
     name: cache-pod
   spec:
     containers:
     - name: app
       image: busybox
       command: ["sleep", "3600"]
       volumeMounts:
       - name: cache-vol
         mountPath: /cache
     volumes:
     - name: cache-vol
       emptyDir:
         sizeLimit: 100Mi
   ```
2. Apply it:
   ```bash
   kubectl apply -f cache-pod.yaml
   ```
3. Verify with:
   ```bash
   kubectl describe pod cache-pod
   ```
4. Exec into the pod and write a file to `/cache`:
   ```bash
   kubectl exec -it cache-pod -- sh
   echo "cached data" > /cache/file.txt
   exit
   ```
5. Delete the pod and recreate it:
   ```bash
   kubectl delete pod cache-pod
   kubectl apply -f cache-pod.yaml
   ```
6. Check if the file is still there:
   ```bash
   kubectl exec -it cache-pod -- ls /cache
   ```
7. **Expected result:** The file is gone because `emptyDir` is ephemeral.

---

**Exercise 5 — Wrong Volume Name (Negative Test)**

1. Write a Pod where the `volumeMounts.name` does **NOT** match the `volumes.name`:
   ```yaml
   apiVersion: v1
   kind: Pod
   metadata:
     name: broken-pod
   spec:
     containers:
     - name: app
       image: busybox
       command: ["sleep", "3600"]
       volumeMounts:
       - name: wrong-name          # <-- This does not match
         mountPath: /data
     volumes:
     - name: correct-name
       emptyDir: {}
   ```
2. Apply it:
   ```bash
   kubectl apply -f broken-pod.yaml
   ```
3. Check the status:
   ```bash
   kubectl get pod broken-pod
   kubectl describe pod broken-pod
   ```
4. **Expected result:** The Pod will fail to start. You will see an error because Kubernetes cannot find a volume named `wrong-name`.
5. Fix the name so both match, re-apply, and confirm the Pod runs.

---

**Exercise 6 — Ephemeral Lifetime Behaviour**

1. Apply a Pod with an `emptyDir`:
   ```yaml
   apiVersion: v1
   kind: Pod
   metadata:
     name: ephemeral-pod
   spec:
     containers:
     - name: app
       image: busybox
       command: ["sleep", "3600"]
       volumeMounts:
       - name: temp-data
         mountPath: /data
     volumes:
     - name: temp-data
       emptyDir: {}
   ```
2. Exec in and write a file:
   ```bash
   kubectl exec -it ephemeral-pod -- sh
   echo "test data" > /data/file.txt
   exit
   ```
3. Verify the file exists:
   ```bash
   kubectl exec -it ephemeral-pod -- cat /data/file.txt
   ```
4. Delete the Pod:
   ```bash
   kubectl delete pod ephemeral-pod
   ```
5. Recreate the Pod with the exact same manifest:
   ```bash
   kubectl apply -f ephemeral-pod.yaml
   ```
6. Check if the file exists:
   ```bash
   kubectl exec -it ephemeral-pod -- ls /data
   ```
7. **Expected result:** The directory is empty. The `emptyDir` was destroyed when the original Pod was deleted, and a brand new empty directory was created for the new Pod.

## 10. Summary

| Concept | Detail |
|---------|--------|
| **What a Volume is** | Storage attached to a Pod that survives container restarts and can be shared between containers |
| **Why use Volumes** | (1) Persist data across container crashes/restarts, (2) Share files between containers in a pod |
| **Volume vs volumeMount** | `volumes` (pod-level) declares storage; `volumeMounts` (container-level) places it at a path |
| **Ephemeral types** | `emptyDir`, `configMap`, `secret` — live only as long as the pod does |
| **Persistent types** | `persistentVolumeClaim`, `nfs`, cloud disks — live independently of any Pod |
| **Naming rule** | `volumeMounts.name` must match a name in `volumes` |
| **Default container FS behaviour** | Wiped on every container restart — that is the reason volumes exist |
| **Deprecation note** | Some volume types are deprecated/removed in newer Kubernetes versions — check docs before production use |

---

## 11. Key Takeaways

1. **Without a Volume, every container restart wipes your data.** The container starts fresh from the image.

2. **A Volume lives at the Pod level.** All containers in the Pod can mount it and share files.

3. **You always need both `volumes` and `volumeMounts`.** One defines the storage, the other uses it.

4. **If `volumeMounts.name` does not match `volumes.name`, the Pod will fail.**

5. **Ephemeral volumes** (`emptyDir`, `configMap`, `secret`) die with the Pod.

6. **Persistent volumes** (`PVC`, `nfs`, cloud disks) survive beyond any Pod.

7. **Type-specific details** for `emptyDir` and `hostPath` are covered in their own separate notes.
