# Persistent Volume Provisioning — Static vs Dynamic — Domain 4: Storage

---

## 1. What is Persistent Volume Provisioning?

> **Provisioning** is the process of actually **creating the storage** behind a PersistentVolume (PV) so a Pod can use it.

In Kubernetes there are **two ways** to do this:

| Type | Who creates the PV | When | Used for |
|---|---|---|---|
| **Static** | An admin creates the PV **manually**, ahead of time | Before any PVC exists | Special / pre-existing storage that the admin already manages |
| **Dynamic** | Kubernetes creates the PV **automatically** when a PVC asks for it | At the time the PVC (or Pod) is created | Most production scenarios; uses a StorageClass + Provisioner |

```
   Static:                            Dynamic:
   ┌──────────┐                        ┌──────────┐
   │  Admin   │── creates PV ──┐       │   User    │── creates PVC ──┐
   └──────────┘                ▼       └──────────┘                  ▼
                       ┌──────────┐                          ┌──────────────┐
                       │   PV     │                          │ StorageClass │
                       └──────────┘                          └──────┬───────┘
                            ▲                                       │
   ┌──────────┐             │                                       ▼
   │   User   │── creates ──┘                                ┌──────────┐
   │   PVC    │  (matches)                                   │    PV    │ ◄── auto-created
   └──────────┘                                              └──────────┘
```

---

## 2. Why Provisioning — What Challenges Does It Solve?

### Challenge 1: Pods Need Persistent Storage, But Managing It Manually is Painful

In the static approach, an admin must manually create every PV ahead of time. In a large cluster with many namespaces and apps, this becomes a bottleneck.

**Dynamic provisioning solves this** by letting users just ask for storage (via a PVC); Kubernetes calls the provisioner and creates the PV automatically.

---

### Challenge 2: Cluster Admin and Developer Have Different Responsibilities

The admin knows what storage backends are available (AWS EBS, NFS, local disks). The developer just wants a 10 GB volume — they should not have to care about the backend.

**Provisioning solves this** by separating the two roles:
- Admin sets up the **StorageClass** (which backend + how to provision).
- Developer creates a **PVC** referencing that StorageClass.

---

### Challenge 3: Same Workflow Across Different Cloud Providers

Each cloud provider has different storage (AWS EBS, GCP Persistent Disk, DigitalOcean Volumes). Apps should not care.

**Dynamic provisioning solves this** by hiding the backend behind a StorageClass — the developer's PVC stays the same regardless of provider.

---

## 3. Static Provisioning — How It Works

> The admin creates PV objects **before** any PVC exists. Users create PVCs that **match** an available PV; Kubernetes binds them.

```
1. Admin creates PV  manual-pv-1gb  (1Gi, RWO, Retain)
2. Admin creates PV  manual-pv-3gb  (3Gi, RWO, Retain)
3. User creates PVC asking for 1Gi → bound to manual-pv-1gb
4. If no matching PV exists, the PVC stays unbound (Pending).
```

Output of `kubectl get pv`:

```
NAME            CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM   STORAGECLASS
manual-pv-1gb   1Gi        RWO            Retain           Available           manual
manual-pv-3gb   3Gi        RWO            Retain           Available           manual
```

> Static is rarely used in production because it requires manual admin work for every workload.

---

## 4. Dynamic Provisioning — How It Works

> The user simply creates a PVC. The StorageClass referenced in the PVC tells Kubernetes which **provisioner** to call. The provisioner creates the actual storage and a matching PV — automatically.

```
1. Admin sets up StorageClass + Provisioner    (one-time setup)
2. User looks at available StorageClasses
3. User creates a PVC referencing a StorageClass
4. Provisioner creates the underlying storage
5. Provisioner creates the PV
6. Kubernetes binds the PVC to the new PV
7. The Pod that mounts the PVC starts using the storage
```

Output of `kubectl get pvc` after dynamic provisioning:

```
NAME       STATUS  VOLUME                                     CAPACITY  ACCESS MODES  STORAGECLASS
do-pvc-1gb Bound   pvc-86690381-df9a-4966-be5b-db45c61971c8   1Gi       RWO           do-block-storage
```

> Managed Kubernetes clusters (EKS, GKE, AKS, DOKS) ship with **default StorageClasses** so dynamic provisioning works out of the box.

---

## 5. Static vs Dynamic — Side-by-Side

| | Static | Dynamic |
|---|---|---|
| **Who creates the PV** | Admin manually | Kubernetes (via provisioner) automatically |
| **When the PV is created** | Before the PVC | When the PVC asks for it |
| **Requires StorageClass** | Optional (often `manual` or `""`) | Yes — drives the provisioning |
| **Effort per workload** | High — admin must pre-create | Zero — user just creates the PVC |
| **Common use** | Pre-existing/special storage | Most production scenarios |

## 6. The Dynamic Provisioning Workflow (Roles)

```
                  ┌─────────────────────┐
                  │ Cluster Administrator│
                  │  ① sets up Storage  │
                  │     Class + Provis. │
                  └──────────┬──────────┘
                             │
        ┌────────────────────┼──────────────────────┐
        │                    │                      │
        ▼                    ▼                      ▼
  ┌──────────┐         ┌──────────┐          ┌────────────┐
  │ Storage  │         │   PV     │          │ Provisioner│
  │  Class   │         │  (auto)  │ ◄────────┤ creates    │
  └────┬─────┘         └──────────┘          │ actual     │
       │                    ▲                │ storage    │
       │                    │ ⑥ bind         └────────────┘
       │ ③ developer        │
       │   sees classes     │
       ▼                    │
  ┌──────────┐    ④ PVC     │
  │   PVC    │──────────────┘
  └────┬─────┘
       │ ② mount in pod
       ▼
  ┌──────────┐
  │   Pod    │
  └──────────┘
```

1. Admin sets up the **StorageClass** + provisioner.
2. Application developer writes a **Pod** that needs storage.
3. Developer checks which StorageClasses are available: `kubectl get storageclass`.
4. Developer creates a **PVC** that references a StorageClass.
5. The provisioner provisions the **actual storage** and creates the **PV**.
6. Kubernetes **binds** the PVC to the newly-created PV. The Pod can now mount it.

## 7. Practical Example — Local Path Provisioner (Rancher)

> The **Local Path Provisioner** by Rancher is a lightweight, simple dynamic storage provisioner that uses local storage on a node to provide PersistentVolumes. Useful when you do not have a cloud-managed StorageClass to practice on (e.g., kubeadm or local clusters).

### Install

```bash
# One-line install (creates a StorageClass + a provisioner Pod)
kubectl apply -f https://raw.githubusercontent.com/rancher/local-path-provisioner/master/deploy/local-path-storage.yaml
```

After install:

```bash
kubectl get storageclass
# NAME         PROVISIONER             RECLAIMPOLICY  VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION
# local-path   rancher.io/local-path   Delete         WaitForFirstConsumer   false
```

A separate namespace is also created:

```bash
kubectl get namespace
# NAME                  STATUS
# local-path-storage    Active     <-- holds the provisioner Pod

kubectl get pods -n local-path-storage
# local-path-provisioner-xxxxxxx-yyyy   1/1   Running
```

This provisioner pod **contains the logic** that creates PVs when PVCs ask for them.

---

### Step 1 — Create a PVC

`pvc.yaml`:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: local-path-pvc
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: local-path        # references the StorageClass
  resources:
    requests:
      storage: 128Mi
```

```bash
kubectl apply -f pvc.yaml
kubectl get pvc
# NAME             STATUS    VOLUME   CAPACITY   STORAGECLASS
# local-path-pvc   Pending                       local-path
```

> The PVC is **Pending** at this point — the StorageClass has `WaitForFirstConsumer`, so no PV is created until a Pod actually uses the PVC.

### Step 2 — Create a Pod That Uses the PVC

`pod.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: lp-pod
spec:
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - mountPath: /data
      name: storage
  volumes:
  - name: storage
    persistentVolumeClaim:
      claimName: local-path-pvc
```

```bash
kubectl apply -f pod.yaml
kubectl get pv
# NAME                                       CAPACITY  STATUS  CLAIM
# pvc-86690381-df9a-4966-be5b-db45c61971c8   128Mi     Bound   default/local-path-pvc

kubectl get pvc
# NAME             STATUS   CAPACITY   STORAGECLASS
# local-path-pvc   Bound    128Mi      local-path
```

Now the PV was **dynamically created** the moment the Pod was scheduled.

### Cleanup

```bash
kubectl delete pod lp-pod
kubectl delete pvc local-path-pvc
```

## 8. Syntax — Quick Reference

### Inspect Storage

```bash
kubectl get storageclass         # available classes
kubectl get pv                   # cluster PVs
kubectl get pvc -A               # claims in all namespaces
kubectl describe pvc <name>      # check binding, events
```

### Minimal PVC

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
  storageClassName: <storage-class-name>    # omit to use the default class
```

### Minimal Pod Using a PVC

```yaml
spec:
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - mountPath: /data
      name: vol
  volumes:
  - name: vol
    persistentVolumeClaim:
      claimName: my-pvc
```

## 9. Examples

### Example 1 — Dynamic on a Managed Cluster (DigitalOcean)

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: do-pvc-1gb
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: do-block-storage    # default DO StorageClass
  resources:
    requests:
      storage: 1Gi
```

```bash
kubectl apply -f do-pvc-1gb.yaml
kubectl get pvc
# do-pvc-1gb   Bound   pvc-...   1Gi   RWO   do-block-storage
kubectl get pv
# pvc-86690381-...   1Gi   RWO   Delete   Bound
```

A real **DigitalOcean Volume** is created in the DO account automatically.

### Example 2 — Static Provisioning

```yaml
# admin creates a PV first
apiVersion: v1
kind: PersistentVolume
metadata:
  name: manual-pv-1gb
spec:
  capacity:
    storage: 1Gi
  accessModes: ["ReadWriteOnce"]
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  hostPath:
    path: /mnt/data
```

```yaml
# user creates a matching PVC
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: manual-pvc
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: manual
  resources:
    requests:
      storage: 1Gi
```

Once both exist, Kubernetes binds them automatically.

## 10. Exercises to Practice for the CKAD Exam

### Imperative (CLI-based) Exercises

**Exercise 1 — List Available StorageClasses**
1. Run `kubectl get storageclass`.
2. Identify which (if any) is the **default** (look for `(default)` next to the name).
3. Look at the `PROVISIONER` and `VOLUMEBINDINGMODE` columns.

**Exercise 2 — Dynamic Provisioning Test**
1. Find the default StorageClass.
2. Create a PVC via CLI: `kubectl create -f <pvc.yaml>` (use a minimal manifest).
3. Run `kubectl get pv` and confirm a PV was created automatically.

**Exercise 3 — Watch the Binding**
1. Apply a PVC and immediately run `kubectl get pvc --watch`.
2. Observe the status change from `Pending` to `Bound`.

**Exercise 4 — Local Path Provisioner Setup**
1. Install the local-path-provisioner using the one-line apply command.
2. Wait for the pod in `local-path-storage` namespace to be `Running`.
3. Confirm a new StorageClass `local-path` is available.

---

### Declarative (YAML-based) Exercises

**Exercise 5 — Static PV + PVC**
1. Write a `PersistentVolume` manifest with `capacity: 1Gi`, `accessModes: [ReadWriteOnce]`, `hostPath: /mnt/data`, `storageClassName: manual`.
2. Write a matching `PersistentVolumeClaim` requesting `1Gi`, `RWO`, `storageClassName: manual`.
3. Apply both and confirm the PVC binds to the PV.

**Exercise 6 — Dynamic PVC with WaitForFirstConsumer**
1. Write a PVC referencing the `local-path` StorageClass.
2. Apply and confirm the PVC is `Pending` (no PV yet).
3. Write a Pod that mounts the PVC.
4. Apply the Pod and confirm a PV is now created and bound.

**Exercise 7 — Pod Using a PVC**
1. Write a Pod manifest that:
   - Has a `volumes:` block with `persistentVolumeClaim.claimName: my-pvc`.
   - Mounts that volume at `/data` in the container.
2. Apply and confirm the Pod runs.
3. Exec in and write a file in `/data`.
4. Delete the Pod, recreate it — the file should still be there (because the PV persists).

**Exercise 8 — Default StorageClass Behaviour**
1. Write a PVC manifest **without** `storageClassName`.
2. Apply it and verify the default StorageClass was used.
3. (Repeat after temporarily removing the default-class annotation — verify the PVC now stays Pending.)

## 11. Summary

| Concept | Detail |
|---|---|
| **Static provisioning** | Admin creates PV manually; PVC binds to a matching pre-existing PV |
| **Dynamic provisioning** | PVC + StorageClass → Kubernetes auto-creates the PV via a provisioner |
| **Provisioner** | The plugin/driver that talks to the underlying storage (AWS EBS, NFS, local disks, etc.) |
| **Managed clusters** | Ship with default StorageClasses — dynamic just works |
| **Local Path Provisioner** | Rancher's lightweight provisioner; great for kubeadm/local clusters; uses node-local disk |
| **WaitForFirstConsumer** | PV creation is delayed until a Pod actually mounts the PVC |
| **Immediate** | PV is created the moment the PVC is created |
| **Inspect** | `kubectl get storageclass`, `kubectl get pv`, `kubectl get pvc`, `kubectl describe pvc <name>` |
