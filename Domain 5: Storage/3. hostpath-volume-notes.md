# HostPath Volume — Domain 4: Storage

---

## 1. Recap: Types of Volumes

| Type | Key Features | Use Case |
|---|---|---|
| **emptyDir** | Temporary directory created with the Pod; deleted with the Pod. | Sharing files between containers in the same Pod. |
| **hostPath** | Mounts a path from the worker node's filesystem. | Access node logs, configs, or write node-bound data. |
| **configMap / secret** | Mounts config or secret data as files. | Inject config or credentials into containers. |
| **persistentVolumeClaim** | Cluster-managed persistent storage. | Long-lived data (databases, user uploads). |

This note focuses on **hostPath**.

---

## 2. What is a hostPath Volume?

> A **hostPath** volume mounts a **file or directory from the worker node's filesystem** directly into the Pod.

The worker node is the machine where the Pod is running. It has its own filesystem (`/var/log`, `/etc`, `/`, etc.). A hostPath volume lets a container inside the Pod reach into those node paths.

```
   ┌────────────── Pod ──────────────┐
   │       ┌──────────────┐           │
   │       │  Container    │           │
   │       │  /worker-node-│           │
   │       │   data        │           │
   │       └──────┬───────┘           │
   │              │                    │
   └──────────────┼────────────────────┘
                  │ (mount)
                  ▼
         ┌────────────────────────┐
         │  Host (Worker Node)    │
         │   /                     │
         │   /var/log              │
         │   /etc                  │
         └────────────────────────┘
```

---

## 3. Why hostPath — What Challenges Does It Solve?

### Challenge 1: A Container Needs to Read Node Logs or Configs

Sometimes a container's job is to analyze logs that live on the **node** (like `/var/log` on a Linux worker node). The container's own filesystem does not have those files.

**hostPath solves this** by mounting the node directory into the container so the container can read those files directly.

---

### Challenge 2: A Container Needs to Write Persistent Data to a Specific Node Path

If a container must write data that must survive Pod restarts and live on a specific node (e.g., a node-local cache, agent state file), the container's filesystem will not do.

**hostPath solves this** by writing into a directory on the node — data stays on the node even after the Pod is gone (until the node is gone).

---

### Challenge 3: No SSH Access to Worker Nodes (Managed Clusters)

In managed Kubernetes clusters (EKS, GKE, AKS, DOKS), you usually cannot SSH into the worker nodes. So inspecting node-level files is hard.

**hostPath solves this** by allowing you to create a Pod that mounts the node's root filesystem (`/`) and then `kubectl exec` into the Pod to look around — a common troubleshooting trick.

---

## 4. Important Points to Remember

- **hostPath ties the Pod to a specific node.** If the Pod gets rescheduled to a different node, the new node may not have the same files/paths.
- **Security-sensitive.** Mounting node paths (especially `/` or `/etc`) gives the Pod a lot of access to the host. Use carefully.
- **Not portable.** A Pod using hostPath is harder to move between environments.
- **Persistence is limited.** Data survives Pod restarts only if the Pod stays on the same node. If the node dies, the data is gone.
- The optional **`type`** field lets you assert what the path should be (e.g., `Directory`, `File`, `DirectoryOrCreate`) — useful as a safety check.

---

## 5. Syntax

### Basic hostPath Volume

```yaml
spec:
  volumes:
  - name: <volume-name>
    hostPath:
      path: <path-on-the-node>     # e.g., /var/log
      type: Directory               # optional: Directory | File | DirectoryOrCreate | etc.
```

### Mount Inside a Container

```yaml
spec:
  containers:
  - name: <container-name>
    volumeMounts:
    - name: <volume-name>      # must match the volumes name above
      mountPath: <path-in-container>
```

### Common `type` Values

| `type` | Meaning |
|---|---|
| *(empty)* | No check — path is used as-is. |
| `Directory` | Path must exist and be a directory. |
| `DirectoryOrCreate` | Path is created if it does not exist (as a directory). |
| `File` | Path must exist and be a file. |
| `FileOrCreate` | File is created if it does not exist. |

## 6. Examples

### Example 1 — Mount the Node's Root Filesystem into a Pod

Save as `hostpath-demo.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: hostpath-demo
spec:
  containers:
  - name: test-container
    image: busybox
    command: ["sleep", "36000"]
    volumeMounts:
    - name: host-volume
      mountPath: /worker-node-data
  volumes:
  - name: host-volume
    hostPath:
      path: /
      type: Directory
```

Apply and explore:

```bash
kubectl apply -f hostpath-demo.yaml
kubectl exec -it hostpath-demo -- sh
cd /worker-node-data
ls
# bin   boot   dev   etc   home   proc   root   var   ...   (this is the node's /)
```

The Pod is now looking directly at the worker node's root filesystem.

---

### Example 2 — Mount Just the Node's Log Directory

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: log-reader
spec:
  containers:
  - name: reader
    image: busybox
    command: ["sleep", "36000"]
    volumeMounts:
    - name: node-logs
      mountPath: /node-logs
      readOnly: true
  volumes:
  - name: node-logs
    hostPath:
      path: /var/log
      type: Directory
```

```bash
kubectl exec -it log-reader -- sh
cd /node-logs
ls            # shows /var/log of the worker node
```

> Using `readOnly: true` is a good safety practice when the container should not modify node files.

---

### Example 3 — Write Persistent Data to a Specific Node Path

```yaml
volumes:
- name: app-state
  hostPath:
    path: /opt/myapp/state
    type: DirectoryOrCreate
```

If `/opt/myapp/state` does not exist on the node, Kubernetes will create it. Whatever the container writes to `/opt/myapp/state` (via its `mountPath`) will live on the node and survive Pod restarts on that same node.

## 7. Exercises to Practice for the CKAD Exam

### Imperative (CLI-based) Exercises

**Exercise 1 — Inspect a hostPath Mount**
1. Apply `hostpath-demo.yaml` from Example 1.
2. Run `kubectl describe pod hostpath-demo`.
3. Find the `Volumes:` block and confirm `Type: HostPath`.

**Exercise 2 — Browse the Node's Root**
1. Exec into the pod and explore `/worker-node-data`.
2. Look at the contents of `/worker-node-data/etc` and `/worker-node-data/var/log` — these belong to the worker node.

**Exercise 3 — Use `kubectl get nodes -o wide`**
1. Find which node your hostPath pod is running on.
2. Delete the pod and recreate it — verify it is scheduled on a node (any node) and inspect again.

---

### Declarative (YAML-based) Exercises

**Exercise 4 — Read /var/log from the Node**
1. Write a Pod manifest that mounts `/var/log` from the node at `/node-logs` inside a busybox container.
2. Mark the mount as `readOnly: true`.
3. Apply and exec in — `tail` one of the log files.

**Exercise 5 — DirectoryOrCreate Behavior**
1. Write a Pod manifest that mounts a hostPath of `/opt/test-state` with `type: DirectoryOrCreate`.
2. Apply and confirm the directory now exists on the node (you can verify by running another pod or via the cluster).
3. Write a file into it from the container.

**Exercise 6 — File Type hostPath**
1. Write a Pod manifest that mounts a specific node file (e.g., `/etc/hostname`) with `type: File` at `/host-name` inside the container.
2. Apply and `cat /host-name` from inside.

**Exercise 7 — Negative Test: Wrong Type**
1. Set `type: File` but point `path:` to a directory.
2. Apply and observe the Pod fail to start.
3. Read the error in `kubectl describe pod`.

**Exercise 8 — Multiple hostPath Mounts**
1. Write a Pod that mounts two hostPath volumes — one read-only for `/var/log`, one writable for `/opt/myapp/state`.
2. Apply and verify both mounts via `kubectl describe pod`.

## 8. Summary

| Concept | Detail |
|---|---|
| **What it is** | Mounts a file or directory from the worker node's filesystem into the Pod |
| **Why use it** | Read node logs/configs, write node-bound data, troubleshoot managed clusters without SSH |
| **Lifetime of data** | Lives on the node — survives Pod restarts on the same node, lost if node dies |
| **Node binding** | Pod is effectively tied to whichever node has the data |
| **Security risk** | Can give the Pod broad access to the host filesystem; use with care |
| **`type` field** | Optional safety check (`Directory`, `File`, `DirectoryOrCreate`, etc.) |
| **Managed clusters** | Useful trick to inspect a worker node when SSH is not available |
| **Not portable** | A Pod with hostPath is hard to move across nodes/clusters |
