# Access Modes — Domain 4: Storage

---

## 1. Recap: Where Access Modes Fit

| Concept | What it does |
|---|---|
| **PersistentVolume (PV)** | The actual piece of storage in the cluster. |
| **PersistentVolumeClaim (PVC)** | A user's request for storage; binds to a PV. |
| **Access Modes** | Define **how** a PV can be mounted and accessed by Nodes and Pods. |

This note focuses on **Access Modes**. For related topics, see [pv-provisioning-notes.md](pv-provisioning-notes.md), [storage-class-notes.md](storage-class-notes.md), and [reclaim-policy-notes.md](reclaim-policy-notes.md).

---

## 2. What are Access Modes?

> **Access Modes** define **how a PersistentVolume can be mounted and accessed by Nodes and Pods** in the cluster.

In plain English: *"Can multiple Pods write to this volume? Can multiple Nodes read from it? Can only one Pod use it?"*

```
                  ┌─────────────────────┐
                  │  Persistent Volume  │
                  └─────────┬───────────┘
                            │
            ┌───────────────┴───────────────┐
            │                                │
            ▼                                ▼
      ┌──────────┐                     ┌──────────┐
      │   Pod-1   │                    │   Pod-2   │
      │  Node 1   │                    │  Node 2   │
      └──────────┘                     └──────────┘
```

The Access Mode decides who can mount this volume — and how.

---

## 3. Why Access Modes — What Challenges Do They Solve?

### Challenge 1: Not Every Storage Backend Supports Sharing

Some storage (like AWS EBS or DigitalOcean Block Storage) can only be attached to **one node at a time**. Other storage (like NFS) can be shared by **many nodes**. Pods need a way to say what they require.

**Access modes solve this** by letting the PVC declare what kind of sharing it needs.

---

### Challenge 2: Some Apps Need Exclusive Access

A database writing to disk usually needs **exclusive** access — multiple Pods writing to the same disk would corrupt the data.

**Access modes solve this** with `ReadWriteOnce` and (more strictly) `ReadWriteOncePod`.

---

### Challenge 3: Some Apps Need Shared Read or Read/Write Access

Many web apps want to share a read-only config volume, or share a writable upload directory across many Pods.

**Access modes solve this** with `ReadOnlyMany` and `ReadWriteMany`.

---

## 4. The Four Access Modes

| Access Mode | Abbreviation | Mounted By | Read | Write | Description |
|---|---|---|---|---|---|
| **ReadWriteOnce** | RWO | Single Node | ✓ | ✓ | The volume can be mounted as read-write by **Pods on a single Node**. Multiple Pods on the **same node** can share it. |
| **ReadOnlyMany** | ROX | Many Nodes | ✓ | ✗ | The volume can be mounted as read-only by **many Nodes simultaneously**. |
| **ReadWriteMany** | RWX | Many Nodes | ✓ | ✓ | The volume can be mounted as read-write by **many Nodes simultaneously**. Requires a backend that supports shared access (NFS, CephFS, AzureFile). |
| **ReadWriteOncePod** | RWOP | Single Pod (1 Node) | ✓ | ✓ | The most restrictive: only **one specific Pod** in the entire cluster can mount the volume as read-write. |

---

## 5. ReadWriteOnce (RWO) — Single Node

> The volume can be mounted as read-write by **a single Node** at a time. Multiple Pods on that same Node can all use the PVC and read/write the volume.

**Important nuance**: "single node" — not "single pod". Two Pods on the same node sharing the same PVC will both work in RWO. But a Pod on a different node cannot mount it simultaneously.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
  storageClassName: standard
```

> Typical backends: **AWS EBS, GCP Persistent Disk, Azure Disk, DigitalOcean Block Storage**.

---

## 6. ReadOnlyMany (ROX) — Many Nodes, Read-Only

> The volume can be mounted as **read-only by many nodes simultaneously**. Multiple Pods across multiple Nodes can mount and read from this volume concurrently. **No Pod can write to it.**

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: config-data
spec:
  accessModes:
    - ReadOnlyMany
  resources:
    requests:
      storage: 5Gi
  storageClassName: nfs-storage
```

> Typical use case: **shared read-only configuration or datasets**.

---

## 7. ReadWriteMany (RWX) — Many Nodes, Read-Write

> The volume can be mounted as **read-write by many nodes simultaneously**. Multiple Pods running on different worker Nodes can all read from and write to the same volume concurrently.

**Important**: this requires a storage backend that supports shared write access — common backends like AWS EBS do NOT.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: nfs-pvc
spec:
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 5Gi
  storageClassName: nfs-storage
```

> Typical backends: **NFS, CephFS, AzureFile** — shared writable file systems.

---

## 8. ReadWriteOncePod (RWOP) — Single Pod

> The volume can be mounted as **read-write by a single Pod only**. This is the **most restrictive** mode — only one specific Pod in the entire cluster can mount this volume as read-write.

Difference vs RWO: with RWO, multiple Pods on the **same node** can share the volume. With RWOP, **only one Pod**, anywhere, can mount it. If a second Pod tries, it stays `Pending` with an error.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: secure-pvc
spec:
  accessModes:
    - ReadWriteOncePod
  resources:
    requests:
      storage: 5Gi
  storageClassName: csi-storage
```

> Typical use case: **security-sensitive apps** needing strict single-Pod access.

> Error you will see when a second Pod tries to mount:
> *"0/1 nodes are available: 1 node has a Pod using the PersistentVolumeClaim with the same name and ReadWriteOncePod access mode."*

---

## 9. Side-by-Side Summary

| Access Mode | Abbreviation | Mounted By | Read | Write | Use Case Example |
|---|---|---|---|---|---|
| ReadWriteOnce | RWO | Single Node | ✓ | ✓ | AWS EBS, GCP PD, Azure Disk — standard volume for stateful apps |
| ReadWriteOncePod | RWOP | Single Pod (1 Node) | ✓ | ✓ | Security-sensitive apps needing strict single-Pod access |
| ReadOnlyMany | ROX | Multiple Nodes | ✓ | ✗ | Shared read-only config or datasets |
| ReadWriteMany | RWX | Multiple Nodes | ✓ | ✓ | NFS, CephFS — shared writable volume across pods/nodes |

---

## 10. Important Considerations

### Not All Volume Types Support All Access Modes

This is the **most important rule**. Always check the volume plugin or cloud provider documentation.

| Volume Plugin | RWO | ROX | RWX | RWOP |
|---|---|---|---|---|
| **AzureFile** | ✓ | ✓ | ✓ | – |
| **CephFS** | ✓ | ✓ | ✓ | – |
| **CSI** | depends on the driver | depends on the driver | depends on the driver | depends on the driver |
| **FC** | ✓ | ✓ | – | – |
| **FlexVolume** | ✓ | ✓ | depends on the driver | – |
| **HostPath** | ✓ | – | – | – |
| **iSCSI** | ✓ | ✓ | – | – |
| **NFS** | ✓ | ✓ | ✓ | – |

> Example: `HostPath` only supports `RWO`. NFS supports `RWO`, `ROX`, and `RWX`.

If you request an unsupported access mode, the PVC will stay **Pending** with an error like:
*"failed to provision volume … unsupported access mode multi node reader only."*

---

## 11. Syntax — Quick Reference

### Set Access Modes in a PVC

```yaml
spec:
  accessModes:
    - ReadWriteOnce          # or ReadOnlyMany, ReadWriteMany, ReadWriteOncePod
```

> `accessModes` is a **list** — you can request multiple modes; the PV must support **all** of them.

### Set Access Modes in a Static PV

```yaml
spec:
  accessModes:
    - ReadWriteOnce
```

### Inspect

```bash
kubectl get pvc                       # ACCESS MODES column shows abbreviation
kubectl get pv                        # same column on PVs
kubectl describe pvc <name>           # explains Pending/Bound reasons
```

## 12. Demo Walkthroughs

### Demo 1 — RWO Works Across Pods on the Same Node

```bash
# Create PVC with RWO
kubectl apply -f pvc-rwo.yaml

# Create test-pod-1 — schedules onto Node A
kubectl apply -f test-pod-1.yaml

# Create test-pod-2 (also forced to Node A) — both mount the same PVC
kubectl apply -f test-pod-2.yaml

# Both pods running
kubectl get pods

# Exec into pod 1, write a file
kubectl exec -it test-pod-1 -- sh
echo "from pod 1" > /data/pod-1-file.txt
exit

# Exec into pod 2, read it
kubectl exec -it test-pod-2 -- sh
ls /data        # pod-1-file.txt visible
cat /data/pod-1-file.txt
exit
```

> Both Pods read/write the same volume — because they are on the **same node**, RWO permits this.

### Demo 2 — RWOP Blocks the Second Pod

Change `accessModes` from `ReadWriteOnce` to `ReadWriteOncePod` in the PVC, then:

```bash
kubectl delete pvc demo-pvc
kubectl apply -f pvc-rwop.yaml

kubectl apply -f test-pod-1.yaml          # Runs
kubectl apply -f test-pod-2.yaml          # Pending

kubectl describe pod test-pod-2
# Events: 0/1 nodes are available: 1 node has a Pod using
# the persistent volume claim with the same name and ReadWriteOncePod access mode.
```

### Demo 3 — Unsupported Access Mode

Try requesting `ReadOnlyMany` on a backend (DigitalOcean Block Storage) that does not support it:

```bash
# PVC with accessModes: [ReadOnlyMany], storageClassName: do-block-storage
kubectl apply -f pvc-rox.yaml
kubectl get pvc
# STATUS: Pending

kubectl describe pvc demo-pvc
# Events: failed to provision volume with StorageClass "do-block-storage":
# rpc error: code = InvalidArgument desc = volume capabilities cannot be satisfied:
# unsupported access mode multi node reader only.
```

Lesson: always match the access mode to what the backend supports.

## 13. Exercises to Practice for the CKAD Exam

### Imperative (CLI-based) Exercises

**Exercise 1 — Inspect Access Modes**
1. Run `kubectl get pv` and note the `ACCESS MODES` column abbreviations (RWO, ROX, RWX, RWOP).
2. Run `kubectl get pvc` and confirm the same modes appear.

**Exercise 2 — Try an Unsupported Access Mode**
1. On a cluster with cloud block storage, create a PVC with `ReadOnlyMany`.
2. Confirm the PVC stays `Pending`.
3. Read the error from `kubectl describe pvc`.

**Exercise 3 — RWOP Restriction Demo**
1. Apply a PVC with `ReadWriteOncePod`.
2. Schedule a Pod that mounts it.
3. Schedule a second Pod with the same PVC.
4. Confirm the second Pod stays `Pending` with the RWOP error.

---

### Declarative (YAML-based) Exercises

**Exercise 4 — Write a RWO PVC**
1. Write a PVC manifest requesting `5Gi` with `ReadWriteOnce`.
2. Apply and confirm it binds.

**Exercise 5 — Write a RWX PVC**
1. Write a PVC manifest requesting `5Gi` with `ReadWriteMany`.
2. Apply against an NFS or AzureFile StorageClass.
3. Schedule two Pods on different Nodes that mount this PVC and write files; confirm both writes succeed.

**Exercise 6 — Write a ROX PVC**
1. Write a PVC requesting `ReadOnlyMany` for a shared config dataset.
2. Apply against an NFS class.
3. Verify multiple Pods on different Nodes can mount it.

**Exercise 7 — RWOP Strict Isolation**
1. Write a PVC with `ReadWriteOncePod`.
2. Apply.
3. Write **two** Pod manifests using the same PVC.
4. Confirm the second Pod stays `Pending`.

**Exercise 8 — Access Mode + Volume Plugin Mismatch**
1. Use a HostPath-backed PV.
2. Try a PVC requesting `ReadWriteMany`.
3. Confirm the binding fails because HostPath only supports RWO.

**Exercise 9 — Multiple Modes on a PV**
1. Write a PV manifest declaring `accessModes: [ReadWriteOnce, ReadOnlyMany]`.
2. Verify a PVC requesting either mode can bind.

## 14. Summary

| Concept | Detail |
|---|---|
| **What it is** | Declares how a PV/PVC can be mounted: single-node vs many-nodes, read vs read-write |
| **Four modes** | `ReadWriteOnce` (RWO), `ReadOnlyMany` (ROX), `ReadWriteMany` (RWX), `ReadWriteOncePod` (RWOP) |
| **RWO** | One node at a time — multiple Pods on the same node allowed |
| **ROX** | Many nodes, read-only |
| **RWX** | Many nodes, read-write (needs NFS/CephFS/AzureFile) |
| **RWOP** | One Pod only — strictest |
| **Set on** | Both PV and PVC (`accessModes` list) |
| **Backend support** | NOT all volume plugins support every mode — always check |
| **Common gotcha** | HostPath supports only RWO; cloud block storage supports only RWO |
| **PVC stays Pending if** | The backend cannot satisfy the requested access mode |
| **Related notes** | [pv-provisioning-notes.md](pv-provisioning-notes.md), [storage-class-notes.md](storage-class-notes.md), [reclaim-policy-notes.md](reclaim-policy-notes.md) |
