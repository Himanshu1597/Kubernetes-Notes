# EmptyDir Volume — Domain 4: Storage

---

## 1. Recap: Types of Volumes

| Type | Key Features | Use Case |
|---|---|---|
| **emptyDir** | Temporary directory created with the Pod; deleted with the Pod. | Sharing files between containers in the same Pod. |
| **hostPath** | Mounts a path from the worker node's filesystem. | Access node logs, configs, or write node-bound data. |
| **configMap / secret** | Mounts config or secret data as files. | Inject config or credentials into containers. |
| **persistentVolumeClaim** | Cluster-managed persistent storage. | Long-lived data (databases, user uploads). |

This note focuses on the first type — **emptyDir**.

---

## 2. What is an emptyDir Volume?

> An **emptyDir** volume is a **temporary storage directory** that is created when a Pod is assigned to a node, and **deleted when the Pod is removed**.

- It starts out **empty** (hence the name).
- All containers in the Pod can **read and write the same files** in the `emptyDir`.
- It can be stored on **disk** (default) or in **memory** (`medium: Memory`).

```
   ┌─────────────────── Pod ───────────────────┐
   │ ┌──────────────┐         ┌──────────────┐ │
   │ │ Writer       │         │ Reader       │ │
   │ │ Container    │         │ Container    │ │
   │ └──────┬───────┘         └──────┬───────┘ │
   │        │ /data                  │ /data    │
   │        └──────────┬─────────────┘         │
   │                   ▼                        │
   │           emptyDir Volume                  │
   └────────────────────────────────────────────┘
```

---

## 3. Why emptyDir — What Challenges Does It Solve?

### Challenge 1: Multi-Container Pods Need Shared Storage

In a multi-container Pod, each container has its own private filesystem. If a **writer** container produces files that a **reader** container must process, they cannot see each other's files by default.

**emptyDir solves this** by giving both containers a shared scratch directory. The writer writes to `/data`, the reader reads from `/data` — same volume.

---

### Challenge 2: Temporary Scratch Space Inside a Pod

Some apps need a temporary working directory (cache, intermediate processing files, sorting buffers). Storing that on the container's filesystem mixes it with application code and is wiped on container restart.

**emptyDir solves this** by giving the Pod a dedicated scratch area that lives until the Pod is removed — separate from the container image's filesystem.

---

### Challenge 3: Container Crashes Should Not Lose Temporary Work

If a container in a Pod crashes and restarts (but the Pod itself stays alive), data on the container's own filesystem is lost. For temporary work, that is wasteful.

**emptyDir solves this** by surviving container crashes. The Pod stays on the same node, so the `emptyDir` directory keeps its contents — only the failing container is replaced.

---

## 4. Key Features of emptyDir

| Feature | Detail |
|---|---|
| **Deleted with Pod** | The directory and all its files are removed when the Pod is removed from the node. |
| **Memory option** | Setting `medium: Memory` stores the directory in RAM — much faster than disk, but counts against the Pod's memory limit. |
| **Survives container crashes** | A container crash does not remove the Pod, so the emptyDir data is preserved across container restarts within the same Pod. |
| **Starts empty** | Always begins with no files; not for restoring previous state. |
| **Optional size limit** | You can set `sizeLimit` to cap the volume size. |

---

## 5. Syntax

### Disk-Backed emptyDir (Default)

```yaml
spec:
  volumes:
  - name: <volume-name>
    emptyDir: {}
```

### Memory-Backed emptyDir

```yaml
spec:
  volumes:
  - name: <volume-name>
    emptyDir:
      medium: Memory
      sizeLimit: 500Mi
```

### Mount Inside a Container

```yaml
spec:
  containers:
  - name: <container-name>
    volumeMounts:
    - name: <volume-name>     # must match the volumes name above
      mountPath: <path-in-container>
```

## 6. Examples

### Example 1 — Multi-Container Pod Sharing an emptyDir

Save as `emptydir-demo.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: emptydir-demo
spec:
  volumes:
  - name: shared-storage
    emptyDir: {}
  containers:
  - name: busybox-container-1
    image: busybox
    command: ["sleep", "36000"]
    volumeMounts:
    - name: shared-storage
      mountPath: /data
  - name: busybox-container-2
    image: busybox
    command: ["sleep", "36000"]
    volumeMounts:
    - name: shared-storage
      mountPath: /data
```

Apply and verify:

```bash
kubectl apply -f emptydir-demo.yaml
kubectl describe pod emptydir-demo
# Look for:
#   Mounts:    /data from shared-storage (rw)
#   Volumes:   shared-storage:  Type:  EmptyDir
```

---

### Example 2 — Write in One Container, Read in the Other

```bash
# Write a file from container 1
kubectl exec -it emptydir-demo -c busybox-container-1 -- sh
cd /data
touch container1-file.txt
exit

# Read it from container 2
kubectl exec -it emptydir-demo -c busybox-container-2 -- sh
ls /data
# container1-file.txt   <-- visible
```

Both containers see the same files — that is the emptyDir at work.

---

### Example 3 — Memory-Backed emptyDir for Performance

```yaml
volumes:
- name: cache-volume
  emptyDir:
    medium: Memory
    sizeLimit: 100Mi
```

Reads/writes happen in RAM, much faster than disk. The volume's size counts toward the container's memory usage.

---

### Example 4 — Confirm emptyDir is Ephemeral

```bash
# Write a file
kubectl exec -it emptydir-demo -c busybox-container-1 -- sh -c "echo hello > /data/file.txt"

# Delete the pod
kubectl delete pod emptydir-demo

# Recreate it
kubectl apply -f emptydir-demo.yaml

# The file is gone — emptyDir starts empty every time
kubectl exec -it emptydir-demo -c busybox-container-1 -- ls /data
# (empty)
```

## 7. Exercises to Practice for the CKAD Exam

### Imperative (CLI-based) Exercises

**Exercise 1 — Inspect an emptyDir Mount**
1. Apply the `emptydir-demo.yaml` from Example 1.
2. Run `kubectl describe pod emptydir-demo`.
3. Identify the `Volumes:` block and confirm `Type: EmptyDir`.

**Exercise 2 — Multi-Container Exec**
1. Use `kubectl exec -it emptydir-demo -c busybox-container-1 -- sh` to enter container 1.
2. Create a file in `/data`.
3. Use `kubectl exec -it emptydir-demo -c busybox-container-2 -- sh` to enter container 2 and read the same file.

**Exercise 3 — Survive a Container Crash**
1. With the pod running, kill the process in container 1 (e.g., `kubectl exec ... -- kill 1`).
2. Wait for the container to restart.
3. Confirm the file in `/data` is **still there** (because the Pod did not get deleted).

**Exercise 4 — Cleanup**
1. Delete the pod with `kubectl delete pod emptydir-demo`.
2. Re-create it and confirm `/data` is empty again — emptyDir does not persist across Pod deletion.

---

### Declarative (YAML-based) Exercises

**Exercise 5 — Writer / Reader Pattern**
1. Write a Pod manifest with two containers:
   - `writer` running `sh -c "while true; do date >> /data/log.txt; sleep 5; done"`.
   - `reader` running `sh -c "tail -f /data/log.txt"`.
2. Both should mount the same `emptyDir` at `/data`.
3. Apply and confirm the reader logs are live by running `kubectl logs <pod> -c reader`.

**Exercise 6 — Memory-Backed emptyDir**
1. Modify Exercise 5 to use `medium: Memory` with `sizeLimit: 100Mi`.
2. Apply and confirm the pod runs.

**Exercise 7 — Single-Container emptyDir Scratch Space**
1. Write a Pod manifest with a single container that mounts an `emptyDir` at `/cache`.
2. Apply.
3. Verify with `kubectl describe pod` that the mount exists.

**Exercise 8 — Negative Test: Mismatched Name**
1. Write a Pod where `volumeMounts.name` does NOT match `volumes.name`.
2. Apply and observe the validation error.
3. Fix the name and re-apply.

**Exercise 9 — Size Limit Behavior**
1. Add `sizeLimit: 10Mi` to a disk-backed `emptyDir`.
2. From inside the container, try to write a large file (e.g., 50MB).
3. Observe whether the write is allowed and what happens when the limit is exceeded.

## 8. Summary

| Concept | Detail |
|---|---|
| **What it is** | A temporary directory created with the Pod; deleted with the Pod |
| **Why use it** | Share files between containers in the same Pod; provide scratch space |
| **Starts** | Empty |
| **Deleted when** | The Pod is removed |
| **Survives** | Container restarts (within the same Pod) |
| **Medium options** | Default (disk) or `Memory` (RAM, faster) |
| **Optional `sizeLimit`** | Caps the volume size |
| **Naming rule** | `volumeMounts.name` must match a name in `volumes` |
| **Not for** | Long-lived data — use a PersistentVolume for that |
