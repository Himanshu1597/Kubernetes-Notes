# Kubernetes Node Selector — Domain 2: Workloads & Scheduling

---

## 1. Foundation: Nodes Are Not All Equal

Before understanding Node Selector, two things must be clear:

- In a real production cluster you rarely have identical worker nodes. Kubernetes **supports worker nodes with different hardware specifications** — different CPU, memory, and GPU.
- Every Pod you run has its **own resource requirements**. Some run heavy applications needing lots of CPU/memory; others need only bare-minimum compute.

```
+----------------------------------------------------------+
|                    Kubernetes Cluster                    |
|                                                          |
|   ┌──────────┐      ┌──────────┐      ┌──────────┐       |
|   │  Node-1  │      │  Node-2  │      │  Node-3  │       |
|   │  2 GB    │      │  8 GB    │      │  1 GB    │       |
|   │  (medium)│      │  (large) │      │  (micro) │       |
|   └──────────┘      └──────────┘      └──────────┘       |
+----------------------------------------------------------+
```

> Some applications require **more CPU and memory**, while some require only **minimum compute resources**. You want the right Pod on the right node.

---

## 2. The Challenge — Kubernetes Schedules Pods Anywhere

By default, when you create a Pod (or a Deployment), the Kubernetes scheduler is free to place it on **any** available worker node. It does not know your intent.

### The Resource-Mismatch Problem

```
Requirement: "AppA Pod needs high memory + CPU"

Without Node Selector, the scheduler might place it here:

   ┌──────────┐      ┌──────────┐      ┌──────────┐
   │  Node-1  │      │  Node-2  │      │  Node-3  │
   │  2 GB    │      │  8 GB    │      │  1 GB    │
   │          │      │          │      │ AppA ✗   │ ◄── landed on the SMALL node
   └──────────┘      └──────────┘      └──────────┘
                                        app crashes / runs poorly
```

If you create a 3-replica Deployment, Kubernetes typically spreads one Pod onto **each** worker node. That is fine when any node can run the Pod — but if the app needs 4–8 GB RAM and the nodes are undersized, the Pods will fail or perform badly.

**You need a way to say: "run this Pod only on a node big enough for it."** That mechanism is **Node Selector**.

---

## 3. What is a Node Selector?

> **Node Selector is a mechanism used to control the placement of Pods onto specific nodes within a cluster.**

Instead of letting the scheduler pick freely, you constrain a Pod to nodes that carry a specific **label**. If the requirement is *"AppA needs a big node"*, you label the big node and tell the Pod to only run where that label exists.

```
Requirement: "AppA Pod needs high memory + CPU → Run it on the Big Node"

   ┌──────────┐      ┌──────────┐      ┌──────────┐
   │  Node-1  │      │  Node-2  │      │  Node-3  │
   │  medium  │      │  LARGE   │      │  micro   │
   │          │      │ AppA ✓   │      │          │ ◄── scheduler forced here
   └──────────┘      └──────────┘      └──────────┘
                     size=large
```

Node Selector is the **simplest** way to influence scheduling in Kubernetes. It works exactly like the label/selector relationship you already know from ReplicaSets and Services — except the labels live on **nodes**, not Pods.

---

## 4. How It Works — Labels + nodeSelector

Node Selector is a **two-step** mechanism. Both steps are required.

| Step | What you do | Where |
|---|---|---|
| **1. Label the node** | Attach a key-value label (e.g. `size=large`) to the worker node | Node level |
| **2. Add `nodeSelector`** | Reference that same key-value pair in the Pod's `spec.nodeSelector` | Pod spec |

Once both are in place, the **Kubernetes scheduler places the Pod on a node that matches the specified label**.

```
Step 1 — Label the nodes:

   ┌──────────┐      ┌──────────┐      ┌──────────┐
   │  Node-1  │      │  Node-2  │      │  Node-3  │
   │size=medium│     │size=large│      │size=micro│
   └──────────┘      └──────────┘      └──────────┘

Step 2 — Pod spec says: nodeSelector: { size: large }

              scheduler matches label
                      │
                      ▼
   Pod is scheduled ONLY on Node-2 (size=large)
```

> 💡 This is the same idea as a ReplicaSet's `selector` matching Pod labels — but here the **selector is `nodeSelector`** and it matches **node labels**.

---

## 5. Step 1 — Labelling a Node

### Add a label to a node

```bash
# Syntax
kubectl label node <node-name> <key>=<value>

# Example
kubectl label node node-2 size=large
```

The label can be **anything** — `size=large`, `size=medium`, `size=micro`, `disktype=ssd`, `gpu=true`. The key/value is entirely your choice; it just has to match on both sides.

### Verify the label was applied

```bash
# Show all labels for every node
kubectl get nodes --show-labels

# Inspect one node's labels in detail
kubectl describe node <node-name>
# Look under the "Labels:" section — you should see size=large
```

> ⚠️ Managed clusters (DigitalOcean, EKS, GKE, minikube, etc.) come with **many pre-existing labels** added by the provider. Your custom label appears alongside them.

### Remove a label from a node

```bash
# Trailing dash (-) after the KEY removes the label
kubectl label node <node-name> size-
```

> ⚠️ **Common mistake:** removing a label uses the **node name** and the **label key** (not the value, not a pod name): `kubectl label node node-2 size-`.

---

## 6. Step 2 — The Pod Manifest with `nodeSelector`

`nodeSelector` goes inside the Pod's `spec`, at the same level as `containers`.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: memory-intensive-app
spec:
  containers:
    - name: app
      image: nginx
  nodeSelector:          # ◄── constrains scheduling
    size: large          # must match a node label size=large
```

```bash
kubectl create -f nodeSelector-pod.yaml
# or
kubectl apply -f nodeSelector-pod.yaml
```

### Using nodeSelector in a Deployment

`nodeSelector` lives in the **Pod template**, so it works for Deployments (and ReplicaSets, Jobs, etc.) too — every Pod created by the Deployment inherits the constraint:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: tmp-deploy
spec:
  replicas: 3
  selector:
    matchLabels:
      app: tmp
  template:
    metadata:
      labels:
        app: tmp
    spec:
      containers:
        - name: nginx
          image: nginx
      nodeSelector:        # ◄── all 3 replicas land on size=medium nodes
        size: medium
```

> With this Deployment, **all three replicas** are placed only on nodes labelled `size=medium` — even if other nodes are available and idle.

---

## 7. Verifying Placement

After creating the Pod/Deployment, confirm which node it landed on:

```bash
# -o wide adds the NODE column
kubectl get pods -o wide
# NAME                   READY   STATUS    NODE
# memory-intensive-app   1/1     Running   node-2   ◄── the size=large node
```

To prove *why* it landed there, inspect the node's labels and confirm they match the Pod's `nodeSelector`:

```bash
kubectl describe node node-2 | grep -i size
# size=large
```

The scheduler matched `nodeSelector: {size: large}` against the node's `size=large` label — placement confirmed. Recreating the Pod repeatedly always sends it to the **same** matching node.

---

## 8. Important Behaviour — Pod Waits (Doesn't Error) When No Node Matches

This is a key exam point. If **no node** matches the `nodeSelector`, the Pod is **not** rejected with an error — it simply stays in **`Pending`** until a matching node appears.

```bash
kubectl get pods
# NAME     READY   STATUS    RESTARTS   AGE
# pod      0/1     Pending   0          20s   ◄── stuck, not failed
```

Find out why with `describe`:

```bash
kubectl describe pod pod
# Events:
#   Warning  FailedScheduling  ...
#   0/1 nodes are available: 1 node(s) didn't match
#   Pod's node affinity/selector.
```

> 💡 The moment you add the matching label to a node, the scheduler picks up the pending Pod and places it — **no restart needed**. This also means: if a matching node goes down (network issue, etc.), Pods will wait in `Pending` for it to return rather than erroring out.

```
No matching label:   Pod → Pending (waits patiently)
        │
        │  kubectl label node <node> size=large
        ▼
Label now matches:   Pod → Running (scheduled automatically)
```

---

## 9. Why Use Node Selectors

| # | Reason | Example |
|---|---|---|
| **1** | Run workloads on nodes with **special hardware / configuration** | GPU nodes for ML, high-memory nodes for in-memory DBs, SSD nodes for I/O-heavy apps |
| **2** | **Segregate workloads** for compliance, performance, or isolation | Keep regulated/PCI workloads on dedicated nodes; isolate noisy neighbours |

In production you can have **hundreds or thousands** of worker nodes of varying sizes (high memory, high CPU, GPU-equipped). By labelling nodes by capability and using `nodeSelector`, you steer each application to the right hardware.

---

## 10. Limitations of Node Selector

`nodeSelector` is intentionally simple — and that simplicity is also its ceiling.

| Limitation | Meaning |
|---|---|
| **Single label matching only** | It's a plain AND of exact key=value pairs. You can list multiple labels, but all must match exactly. |
| **No OR logic** | You **cannot** say "run on `size=large` **OR** `size=medium`". |
| **No NOT logic** | You **cannot** say "run on any node that is **NOT** `size=micro`". |
| **No preferences** | It's binary — a node either matches or it doesn't. You can't express "**prefer** large, but medium is OK". |

```
Need: "schedule on size=large OR size=medium"
nodeSelector: ✗ cannot express this

Need: "prefer size=large, but tolerate anything"
nodeSelector: ✗ cannot express this
```

> 🎯 **The fix: Node Affinity.** When you need OR/NOT conditions or soft *preferences*, you use **Node Affinity** (`requiredDuringScheduling...` / `preferredDuringScheduling...`), which supports operators like `In`, `NotIn`, `Exists`, and `Gt/Lt`. Node Affinity is the more powerful successor covered in the next topic.

## 11. Hands-on Lab — Node Selector End to End

**Goal:** Force a Pod onto a specific node using a label, observe the `Pending` behaviour, then fix it. Works even on a **single-node** cluster.

### Step 1: Start With a Plain Pod (No nodeSelector)

Save as `node-selector-pod.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod
spec:
  containers:
    - name: nginx
      image: nginx
```

```bash
kubectl apply -f node-selector-pod.yaml
kubectl get pods -o wide      # scheduled to the only/any available node
kubectl delete pod pod        # clean up before the real test
```

### Step 2: Add a nodeSelector That Matches Nothing Yet

Edit the manifest to add a `nodeSelector` for a label no node has:

```yaml
spec:
  containers:
    - name: nginx
      image: nginx
  nodeSelector:
    size: large        # no node has this label yet
```

```bash
kubectl apply -f node-selector-pod.yaml
kubectl get pods
# STATUS = Pending  ◄── nothing matches
```

### Step 3: Confirm Why It's Pending

```bash
kubectl describe pod pod
# Events → "0/1 nodes are available: 1 node(s) didn't match
#           Pod's node affinity/selector."
```

### Step 4: Label the Node (Step 1 of the mechanism)

```bash
kubectl get nodes                       # get the node name
kubectl label node <node-name> size=large
```

### Step 5: Verify the Label and Watch the Pod Schedule

```bash
kubectl describe node <node-name> | grep -i size   # size=large present
kubectl get pods                                   # STATUS = Running now!
```

The scheduler found a matching node and placed the previously-pending Pod — **no restart required**.

### Step 6: Cleanup

```bash
kubectl delete pod pod

# Remove the label (node name + KEY + trailing dash)
kubectl label node <node-name> size-

# Verify the label is gone
kubectl describe node <node-name> | grep -i size   # no size=large anymore
```

## 12. Exercises to Practice for the CKA/CKAD Exam

### Imperative (CLI-based) Exercises

**Exercise 1 — Label and Inspect Nodes**
1. List all nodes with their labels using `kubectl get nodes --show-labels`.
2. Label any node with `disktype=ssd`.
3. Verify the label using `kubectl describe node <name>`.
4. Remove the label again with the trailing-dash syntax.

**Exercise 2 — Force a Pod Onto a Labelled Node**
1. Label a node `hardware=gpu`.
2. Create a pod `gpu-pod` (image `nginx`) that uses `nodeSelector: hardware=gpu`.
3. Verify with `kubectl get pods -o wide` that it landed on the labelled node.

**Exercise 3 — Observe the Pending Behaviour**
1. Create a pod with `nodeSelector: tier=frontend` when **no** node has that label.
2. Confirm the pod is `Pending` and read the scheduling event from `kubectl describe pod`.
3. Add `tier=frontend` to a node and confirm the pod moves to `Running` automatically.

---

### Declarative (YAML-based) Exercises

**Exercise 4 — Pod Manifest with nodeSelector**
1. Write a Pod manifest `memory-intensive-app` (image `nginx`) with `nodeSelector: size=large`.
2. Label a node `size=large`, apply the manifest, and verify placement.

**Exercise 5 — Deployment with nodeSelector**
1. Write a 3-replica Deployment whose Pod template includes `nodeSelector: size=medium`.
2. Label a node `size=medium`, apply, and confirm **all three** replicas run on that node.

**Exercise 6 — Prove the Limitation**
1. Try to design a `nodeSelector` that schedules on `size=large` **OR** `size=medium`.
2. Confirm it's impossible with `nodeSelector`, and write down that **Node Affinity** is required for OR/NOT/preference logic.

## 14. Summary

### The Full Picture

```
Without Node Selector:
  Pod ──► scheduler picks ANY node
  ✗ Heavy Pod may land on a tiny node → crashes / poor performance

With Node Selector:
  1. Label the node:      kubectl label node node-2 size=large
  2. Constrain the Pod:   nodeSelector: { size: large }
  Pod ──► scheduler ──► ONLY nodes with size=large
  ✓ Right workload on the right hardware

No matching node?
  Pod stays Pending (no error) → schedules the moment a match appears
```

### Key Points to Remember

- **Node Selector controls Pod placement** onto specific nodes using **node labels**.
- It's a **two-step** mechanism: (1) label the node, (2) add `nodeSelector` to the Pod spec.
- `nodeSelector` sits in `spec` (Pod) or `spec.template.spec` (Deployment), alongside `containers`.
- Label a node: `kubectl label node <node> key=value`; remove: `kubectl label node <node> key-`.
- Verify labels with `kubectl get nodes --show-labels` or `kubectl describe node <node>`.
- Verify placement with `kubectl get pods -o wide`.
- If **no node matches**, the Pod stays **`Pending`** (not errored) and schedules automatically once a matching node appears — **no restart needed**.
- **Use cases:** target special hardware (GPU / high-memory) and segregate workloads for compliance, performance, or isolation.
- **Limitations:** only exact `key=value` matching — **no OR, no NOT, no preferences**.
- For complex scheduling logic (OR/NOT/soft preferences), use **Node Affinity** instead.
