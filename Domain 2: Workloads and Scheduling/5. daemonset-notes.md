# Kubernetes DaemonSet — Domain 2: Workloads & Scheduling

---

## 1. What is a DaemonSet?

> **A DaemonSet ensures that every node in the cluster runs exactly one copy of a Pod.**

Where a ReplicaSet/Deployment thinks in terms of a **total replica count** ("run 3 Pods, anywhere"), a DaemonSet thinks in terms of **nodes** ("run one Pod on *each* node"). The number of Pods is not something you choose — it's automatically equal to the number of (eligible) nodes in the cluster.

```
                    DaemonSet: "antivirus"
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
 ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
 │ Worker Node 1│   │ Worker Node 2│   │ Worker Node 3│
 │              │   │              │   │              │
 │ ┌──────────┐ │   │ ┌──────────┐ │   │ ┌──────────┐ │
 │ │Anti-Virus│ │   │ │Anti-Virus│ │   │ │Anti-Virus│ │
 │ └──────────┘ │   │ └──────────┘ │   │ └──────────┘ │
 └──────────────┘   └──────────────┘   └──────────────┘

   one Pod            one Pod            one Pod
```

### The defining behaviour

- **Node added** → the DaemonSet **automatically creates** a copy of the Pod on that new node.
- **Node removed** → the Pod that lived on that node is **garbage-collected** (terminated), not rescheduled elsewhere.
- **One Pod per node** — you never get two copies of the same DaemonSet Pod on a single node.

> 💡 You don't "scale" a DaemonSet by setting a replica count. Its size tracks the cluster: **1 node = 1 Pod, 3 nodes = 3 Pods**, automatically.

## 2. Why Do We Need a DaemonSet?

Some workloads must run **on every single node** — not as a load-balanced pool, but as a per-node agent. Consider a security-compliance requirement: an **antivirus / malware-scanning agent** must run on each worker node to protect it.

```
Requirement: "Run an antivirus agent on EVERY worker node."

Without DaemonSet — you'd manually create one Pod per node:
  ✗ Add a node → remember to manually add the antivirus Pod
  ✗ Remove a node → manually clean up
  ✗ Easy to miss a node → compliance gap

With DaemonSet — Kubernetes guarantees coverage:
  ✓ Every current node has exactly one antivirus Pod
  ✓ New node joins → Pod appears automatically
  ✓ Node leaves → Pod is cleaned up automatically
```

The key insight from the antivirus example:

- You need the agent on **each** node → DaemonSet places one there.
- You **don't** need multiple copies on the same node → DaemonSet enforces exactly one.
- When a **new node** is added to the organisation's cluster → the same Pod is created there too, with no manual action.

## 3. How a DaemonSet Behaves — Demo Walkthrough

The concept is clearest when you watch the Pod count track the node count.

### Start: single-node cluster

```bash
kubectl get nodes
# NAME       STATUS   ROLES    AGE
# node-1     Ready    <none>   10d          ◄── only one node

kubectl get daemonset
# No resources found.                        ◄── none yet

# create the DaemonSet (manifest in Section 6)
kubectl apply -f daemonset-custom.yaml
# daemonset.apps/antivirus created

kubectl get daemonset
# NAME        DESIRED   CURRENT   READY   AGE
# antivirus   1         1         1       5s   ◄── DESIRED=1 (one node)

kubectl get pods
# NAME              READY   STATUS    NODE
# antivirus-abc12   1/1     Running   node-1
# → only ONE Pod, because there is only ONE node
```

### Add two more nodes → DaemonSet fans out automatically

```bash
kubectl get nodes
# now shows node-1, node-2, node-3            ◄── three nodes

kubectl get daemonset
# NAME        DESIRED   CURRENT   READY   AGE
# antivirus   3         3         3       4m   ◄── DESIRED auto-jumped to 3

kubectl get pods -o wide
# NAME              READY   STATUS    NODE
# antivirus-abc12   1/1     Running   node-1
# antivirus-def34   1/1     Running   node-2   ◄── created automatically
# antivirus-ghi56   1/1     Running   node-3   ◄── created automatically
# → one Pod per node, each on a UNIQUE node
```

> `kubectl get pods -o wide` shows the `NODE` column — use it to confirm each DaemonSet Pod is on a **different** node.

### Remove nodes → Pods are terminated (not rescheduled)

```bash
# scale the cluster back down to a single node (node-2, node-3 removed)
kubectl get nodes            # only node-1 remains
kubectl get pods             # only ONE antivirus Pod remains
kubectl get daemonset
# NAME        DESIRED   CURRENT   READY   AGE
# antivirus   1         1         1       20m  ◄── adjusted back down to 1
```

The DaemonSet **adjusts DESIRED/CURRENT automatically** as nodes come and go.

## 4. DaemonSet vs Deployment — The Node-Removal Difference

This is the single most important comparison, and a common exam trap. Suppose 3 nodes each run 1 Pod, and you remove node-2 and node-3.

```
DEPLOYMENT (replicas: 3) — count must stay at 3:
  Before:  node-1: ■   node-2: ■   node-3: ■     (3 pods total)
  Remove node-2, node-3:
  After:   node-1: ■ ■ ■                         (control plane RESCHEDULES
           node-2: —   node-3: —                  the 2 lost pods onto node-1)
  → Deployment keeps the REPLICA COUNT at 3, piling them onto surviving nodes.

DAEMONSET — one per node, no fixed count:
  Before:  node-1: ■   node-2: ■   node-3: ■
  Remove node-2, node-3:
  After:   node-1: ■   node-2: —   node-3: —     (the 2 pods are TERMINATED)
  → DaemonSet keeps ONE PER NODE. Fewer nodes = fewer pods.
```

| Behaviour | Deployment / ReplicaSet | DaemonSet |
|---|---|---|
| **Sizing model** | Fixed replica **count** you set | **One Pod per node** (auto) |
| **`replicas` field** | Required | **Not used** |
| **Node added** | Scheduler *may* place a Pod there (to balance) | **Always** adds a Pod there |
| **Node removed** | Lost Pods are **recreated on other nodes** (count preserved) | Pod is **terminated** (not moved) |
| **Typical use** | Scalable app workloads | Per-node agents (logging, monitoring, security) |

> 🎯 **Remember:** A Deployment preserves a **count**; a DaemonSet preserves **coverage** (one per node).

## 5. Common Use Cases

DaemonSets are for **node-level agents** — software that must observe or protect the node itself, so it belongs on every node.

| # | Agent type | What it does |
|---|---|---|
| **1** | **Anti-Virus / Malware scanning agents** | Protect each node against malware (common in regulated/compliance environments) |
| **2** | **Log collection agents** | Collect logs from every node (e.g. Fluentd, Filebeat) |
| **3** | **Monitoring & metrics collection agents** | Gather node-level metrics (e.g. Prometheus Node Exporter) |

Beyond these, core Kubernetes components themselves run as DaemonSets:

- **`kube-proxy`** — the networking component that must run on **every** node.
- **CNI network agents** like **`weave-net`**, Calico, Cilium — the overlay network needs an agent on each node.

```bash
# See the DaemonSets Kubernetes runs for itself:
kubectl get daemonsets -n kube-system
# NAME         DESIRED   CURRENT   READY   NODE SELECTOR   AGE
# kube-proxy   3         3         3       <none>          10d
# weave-net    3         3         3       <none>          10d
```

### Real-world example — PCI DSS compliance

PCI DSS (a payment-card security standard) has a requirement to *"protect all systems against malware and regularly update antivirus software."* In Kubernetes this maps directly to a DaemonSet: **deploy an anti-malware agent of your choice as a DaemonSet so it runs in a Pod on every node.** Cloud security docs (e.g. Azure) recommend exactly this pattern to *detect vulnerabilities of a regulated cluster*.

## 6. The DaemonSet Manifest (YAML)

The manifest is **almost identical** to a ReplicaSet/Deployment — with one telling difference: **there is no `replicas` field** (the count is node-determined).

```yaml
apiVersion: apps/v1        # same API group as Deployment
kind: DaemonSet
metadata:
  name: antivirus          # name of the DaemonSet
spec:
  selector:                # WHICH Pods this DaemonSet owns
    matchLabels:
      app: antivirus
  template:                # Pod blueprint — one is stamped onto every node
    metadata:
      labels:
        app: antivirus     # MUST match the selector above
    spec:
      containers:
        - name: antivirus
          image: nginx     # demo image; real use = an antivirus/agent image
# NOTE: no "replicas:" field — a DaemonSet runs one Pod per node.
```

### Field breakdown

| Field | Role |
|---|---|
| `apiVersion: apps/v1` | DaemonSet lives in the `apps/v1` API group (same as Deployment) |
| `kind: DaemonSet` | The object type |
| `metadata.name` | Name of the DaemonSet (here `antivirus`) |
| `spec.selector.matchLabels` | Tells the DaemonSet which Pods it manages |
| `spec.template` | The Pod definition replicated onto each node; its `labels` **must match** the selector |

> ⚠️ **Golden rule (same as ReplicaSet/Deployment):** `spec.selector.matchLabels` **must match** `spec.template.metadata.labels`, or the manifest is rejected.

> 💡 The image name doesn't have to match the DaemonSet name. Naming the DaemonSet `antivirus` while using the `nginx` image is fine for a demo — swap in the real agent image for production.

> 💡 **Tip from the lesson:** the official Kubernetes docs manifest ships with extras (`tolerations`, `volumes`, resource `limits`). None of these are required just to create a DaemonSet — trim down to the minimal fields above when learning.

## 7. How DaemonSet Pods Get Scheduled

How does a DaemonSet get a Pod onto *every* node?

| Kubernetes version | Mechanism |
|---|---|
| **v1.12 and later** (modern) | Uses the **default scheduler** together with **node affinity** rules. The DaemonSet controller creates Pods that are affinity-bound to each node, and the normal scheduler places them. |
| **Before v1.12** (legacy) | The DaemonSet controller set the Pod's **`nodeName`** field directly to bypass the scheduler. |

> For the exam, know that modern DaemonSets rely on the **default scheduler + node affinity** — this also means DaemonSet Pods respect taints/tolerations and node affinity like normal Pods.

## 8. Command Reference

| Task | Command |
|---|---|
| Create from manifest | `kubectl apply -f daemonset.yaml` (or `kubectl create -f ...`) |
| List DaemonSets | `kubectl get daemonset` (short: `kubectl get ds`) |
| List in all namespaces | `kubectl get ds -A` |
| Detailed view | `kubectl describe daemonset <name>` |
| See Pods + their nodes | `kubectl get pods -o wide` |
| Confirm node count | `kubectl get nodes` |
| System DaemonSets | `kubectl get ds -n kube-system` |
| Delete DaemonSet (+ its Pods) | `kubectl delete daemonset <name>` |

### Reading `kubectl get daemonset` output

```
NAME        DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR   AGE
antivirus   3         3         3       3            3           <none>          4m
```

| Column | Meaning |
|---|---|
| `DESIRED` | Number of nodes that should run the Pod (usually = node count) |
| `CURRENT` | Pods currently created |
| `READY` | Pods that passed readiness |
| `NODE SELECTOR` | If set, restricts the DaemonSet to a subset of nodes |

> 💡 **Restrict a DaemonSet to some nodes:** add a `nodeSelector` (or node affinity) to the Pod template so the DaemonSet runs only on matching nodes (e.g. only GPU nodes) instead of all of them.

## 9. Hands-on Lab — Create and Observe a DaemonSet

**Goal:** Create a DaemonSet and confirm it places exactly one Pod per node. Works on a single-node cluster (you'll see one Pod).

### Step 1: Confirm no DaemonSet exists

```bash
kubectl get nodes           # note how many nodes you have
kubectl get daemonset       # "No resources found." — good, clean start
```

### Step 2: Write the manifest

Save as `daemonset-custom.yaml` (use the manifest from Section 6).

### Step 3: Create it

```bash
kubectl apply -f daemonset-custom.yaml
# daemonset.apps/antivirus created
```

### Step 4: Verify one Pod per node

```bash
kubectl get daemonset
# DESIRED / CURRENT should equal your node count

kubectl get pods -o wide
# one Pod per node, each on a UNIQUE node (check the NODE column)
```

### Step 5 (multi-node clusters): Prove auto-scheduling

```bash
# Add a node to the cluster (cloud console / kubeadm join / etc.)
kubectl get nodes           # new node appears
kubectl get pods -o wide    # a new antivirus Pod appeared on it AUTOMATICALLY
```

### Step 6: Cleanup

```bash
kubectl delete daemonset antivirus
kubectl get pods            # all antivirus Pods are gone
```

**Expected outcome:** Pod count always equals eligible-node count, with no manual scaling.

## 11. Summary

### The Full Picture

```
ReplicaSet / Deployment:
  You declare replicas = N ──► scheduler places N pods ANYWHERE
  Node removed → lost pods RESCHEDULED onto surviving nodes (count stays N)

DaemonSet:
  You declare a Pod template (NO replicas) ──► ONE pod on EVERY node
  Node added   → pod created there automatically
  Node removed → that node's pod TERMINATED (not moved)
  Pod count always = number of eligible nodes
```

### Key Points to Remember

- A **DaemonSet runs exactly one copy of a Pod on every node** in the cluster.
- **No `replicas` field** — the count is determined by the number of nodes, automatically.
- **Node added → Pod auto-created; node removed → Pod terminated** (not rescheduled elsewhere).
- API version is **`apps/v1`**, `kind: DaemonSet` — manifest is otherwise like a Deployment/ReplicaSet.
- **`selector.matchLabels` must match `template.metadata.labels`** — same golden rule as ReplicaSet.
- **Use cases:** antivirus/malware agents, log collectors, monitoring/metrics agents, and core components like **`kube-proxy`** and CNI plugins (**`weave-net`**).
- **Compliance angle:** standards like **PCI DSS** ("anti-malware on every system") map naturally to a DaemonSet.
- **Scheduling:** modern DaemonSets (v1.12+) use the **default scheduler + node affinity**; older ones set `nodeName` directly.
- Inspect with `kubectl get daemonset` (`ds`), `kubectl describe ds <name>`, and `kubectl get pods -o wide` (to see per-node placement).
- Restrict to a subset of nodes by adding a **`nodeSelector`** / node affinity to the Pod template.
- **DaemonSet preserves coverage (one per node); a Deployment preserves a count.**
