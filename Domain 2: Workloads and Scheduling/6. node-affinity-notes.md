# Kubernetes Node Affinity — Domain 2: Workloads & Scheduling

> **Prerequisite:** Understand **[Node Selector](2.%20node-selector-notes.md)** first. Node Affinity is its more flexible, more expressive successor — everything here builds on the label/selector idea from there.

---

## 1. Foundation: The Limit of Node Selector

Node Selector schedules Pods using **strict equality** — the Pod's `nodeSelector` must exactly match a label on a worker node.

```
Node Selector = strict equality

  Node-1 has label:  size = medium
  Pod wants:         nodeSelector: { size: medium }
  → exact match → Pod scheduled on Node-1 ✓
```

This works, but it's a blunt instrument. You can only say *"run where the label equals exactly this value."* You **cannot** express anything more nuanced.

In production, where a cluster may have **hundreds or thousands** of worker nodes of many sizes, "exactly equals" isn't enough. You need to say things like *"anything except micro"* or *"large or medium"* or *"any node that has a GPU label at all."* For that, Kubernetes provides **Node Affinity**.

---

## 2. The Challenge — Requirements Node Selector Can't Express

Suppose you have three nodes — **micro**, **medium**, **large** — and this requirement:

> Run **App-A Pod** on **any node EXCEPT the micro node.**

```
   ┌──────────┐      ┌──────────┐      ┌──────────┐
   │  Node-1  │      │  Node-2  │      │  Node-3  │
   │size=medium│     │size=large│      │size=micro│
   │  AppA ✓  │      │  AppA ✓  │      │  AppA ✗  │ ◄── must be excluded
   └──────────┘      └──────────┘      └──────────┘
```

With Node Selector you'd have to know and hardcode the exact acceptable values — and there's no way to say "NOT micro" in a single rule. **Node Affinity solves this trivially** with a `NotIn` operator (`size NotIn [micro]`).

---

## 3. What is Node Affinity?

> **Node Affinity is a scheduling mechanism, similar to Node Selector, but more flexible and expressive.** It lets you define richer rules for which nodes a Pod may (or must) land on, using operators and match expressions instead of a single exact key=value.

It keeps the same underlying idea — **match Pods to nodes by node labels** — but adds:

- **Operators** (`In`, `NotIn`, `Exists`, `DoesNotExist`, `Gt`, `Lt`) instead of only equality.
- **Hard vs soft** rules (**Required** vs **Preferred**) — a Pod can *require* a node type or merely *prefer* it.

```
Node Selector:  size == medium              (one exact match, mandatory)
Node Affinity:  size In [medium, large]     (a set)
                size NotIn [micro]           (exclusion)
                disktype Exists              (key present, any value)
                ...and "required" OR "preferred"
```

---

## 4. Operators in Node Affinity

These operators are what make Node Affinity expressive:

| Operator | Meaning |
|---|---|
| **In** | Matches nodes whose label value is **in** the specified list (behaves like Node Selector) |
| **NotIn** | **Excludes** nodes whose label value is in the specified list |
| **Exists** | Matches nodes that **have the key** at all, regardless of its value |
| **DoesNotExist** | Matches nodes that **do not have** the specified key |
| **Gt** | Matches nodes whose **numeric** label value is **greater than** the given value |
| **Lt** | Matches nodes whose **numeric** label value is **less than** the given value |

```
Requirement                          Operator + expression
──────────────────────────────────   ───────────────────────────────
"run on medium or large"             size In [medium, large]
"run on anything except micro"       size NotIn [micro]
"run wherever a GPU label exists"    gpu Exists
"avoid any node tagged 'legacy'"     legacy DoesNotExist
"only nodes with cores > 8"          cores Gt 8
```

> 💡 `In` behaves just like a Node Selector. The real power comes from `NotIn`, `Exists`, `DoesNotExist`, and the numeric `Gt`/`Lt`.

---

## 5. Required vs Preferred — Hard vs Soft Rules

Node Affinity offers **two approaches**, and choosing between them is the core decision:

| Approach | Nature | If no node matches |
|---|---|---|
| **Required** | **Hard** requirement (mandatory) | Pod is **NOT scheduled** — stays `Pending` |
| **Preferred** | **Soft** preference (best-effort) | Pod is **still scheduled** on the best available node |

### Illustrative example

> Requirement: *Run App-A on an **Extra Large** node.* Cluster only has micro, medium, large — **no Extra Large exists.**

```
REQUIRED (hard):
  No Extra Large node → Pod stays PENDING (never scheduled) ✗

PREFERRED (soft):
  No Extra Large node → Kubernetes schedules Pod on the best
  available node anyway (e.g. Large) ✓
```

### The full field names

In the manifest these two approaches have deliberately long, self-describing names:

| Mode (YAML field) | Description |
|---|---|
| **`requiredDuringSchedulingIgnoredDuringExecution`** | Pods **must** be scheduled on nodes that match the criteria. If no node matches, the Pod won't be scheduled. **Strict requirement.** |
| **`preferredDuringSchedulingIgnoredDuringExecution`** | Pods **prefer** matching nodes but will still be scheduled elsewhere if none match. **A recommendation, not a strict rule.** |

---

## 6. What "IgnoredDuringExecution" Means

Both mode names end in **`IgnoredDuringExecution`**. This is important:

> Node Affinity rules are only evaluated **when the Pod is being scheduled**. Once the Pod is **already running**, any later changes to node labels are **ignored** — the Pod is **not** evicted or moved, even if its node no longer matches.

```
DuringScheduling → rule IS enforced when placing the Pod
IgnoredDuringExecution → after the Pod is running, label changes are ignored
                         (the running Pod stays put)
```

> 💡 The naming hints at a future mode (`RequiredDuringSchedulingRequiredDuringExecution`) that *would* evict a running Pod when labels stop matching — but as of now, execution-time is always "ignored."

---

## 7. Required Node Affinity — Manifest

The affinity block lives under `spec.affinity.nodeAffinity`. Here is the **Required** form (`nodeAffinity-required.yaml`):

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: disktype
                operator: In
                values:
                  - ssd
  containers:
    - name: nginx
      image: nginx
```

**Meaning:** the worker node **must** carry the label `disktype=ssd`. If no node has it, the Pod stays `Pending`.

> ⚠️ Note the required form uses **`nodeSelectorTerms`** → **`matchExpressions`**.

---

## 8. Preferred Node Affinity — Manifest

The **Preferred** form (`nodeAffinity-preferred.yaml`) is structurally a little different — it's a **list** of weighted preferences:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 1
          preference:
            matchExpressions:
              - key: disktype
                operator: In
                values:
                  - ssd
  containers:
    - name: nginx
      image: nginx
```

**Meaning:** Kubernetes **prefers** a node with `disktype=ssd`, but if none exists the Pod is **still scheduled** elsewhere.

### Two structural differences from Required

| | Required | Preferred |
|---|---|---|
| Top structure | `nodeSelectorTerms:` (a list of terms) | a **list of `- weight` + `preference`** items |
| Match block | `matchExpressions` under each term | `matchExpressions` under `preference` |
| `weight` | none | **required** (`1`–`100`) — higher weight = stronger preference |

> 💡 The `matchExpressions` (key / operator / values) is identical in both — only the wrapper (`nodeSelectorTerms` vs `weight`+`preference`) differs. When several preferred rules match, the scheduler sums their weights to rank nodes.

---

## 9. Manifest Structure — The Nesting Explained

The syntax looks intimidating because it's deeply nested. **You don't need to memorise it** — the Kubernetes docs have copy-paste examples. Just understand the hierarchy:

```
spec
└── affinity
    └── nodeAffinity
        ├── requiredDuringSchedulingIgnoredDuringExecution   (hard)
        │   └── nodeSelectorTerms
        │       └── matchExpressions
        │           ├── key:      disktype
        │           ├── operator: In
        │           └── values:   [ ssd ]
        │
        └── preferredDuringSchedulingIgnoredDuringExecution  (soft)
            └── - weight: 1
                └── preference
                    └── matchExpressions
                        ├── key:      disktype
                        ├── operator: In
                        └── values:   [ ssd ]
```

The scheduler reads the **key**, **operator**, and **values**, then finds a worker node whose labels satisfy the expression.

> 💡 **Exam tip:** Don't memorise — understand. Recall the hierarchy `affinity → nodeAffinity → required/preferred → …matchExpressions (key/operator/values)`, then pull the exact skeleton from the Kubernetes docs.

## 10. Behaviour Walkthrough (Demo)

On a single-node cluster whose node has **no** `disktype` label:

### Required → Pending until a match exists

```bash
kubectl apply -f nodeAffinity-required.yaml
kubectl get pods
# NAME    READY   STATUS    RESTARTS   AGE
# nginx   0/1     Pending   0          15s   ◄── no node has disktype=ssd
```

```bash
kubectl describe pod nginx
# Events:
#   Warning  FailedScheduling  ...
#   0/1 nodes are available: 1 node(s) didn't match
#   Pod's node affinity/selector.
```

Now label the node — the Pod schedules **immediately**:

```bash
kubectl label node <node-name> disktype=ssd
kubectl get pods
# NAME    READY   STATUS    RESTARTS   AGE
# nginx   1/1     Running   0          40s   ◄── match found → scheduled
```

### Preferred → runs even without a match

```bash
kubectl apply -f nodeAffinity-preferred.yaml
kubectl get pods
# nginx   1/1     Running   ◄── scheduled despite node lacking disktype=ssd
```

> 💡 **Waiting, not failing (Required):** if the matching node is temporarily down (network issue, node failure), the Pod stays `Pending` and Kubernetes **keeps waiting**. The moment a matching node becomes available, the Pod is scheduled automatically — you never get a hard error.

## 11. Node Selector vs Node Affinity

| Feature | Node Selector | Node Affinity |
|---|---|---|
| **Matching** | Strict equality only (`key=value`) | Operators: `In`, `NotIn`, `Exists`, `DoesNotExist`, `Gt`, `Lt` |
| **Exclusion (NOT)** | ❌ Not possible | ✅ `NotIn` / `DoesNotExist` |
| **Sets (OR of values)** | ❌ One value only | ✅ `In [a, b, c]` |
| **Hard vs soft** | Always hard (Pending if no match) | **Required** (hard) **or** **Preferred** (soft) |
| **YAML location** | `spec.nodeSelector` | `spec.affinity.nodeAffinity` |
| **Complexity** | Very simple | More verbose / nested |
| **Best for** | Simple, exact placement | Flexible, expressive, production-grade rules |

> 🎯 **Bottom line:** Node Selector is the quick tool for exact matches; Node Affinity is the expressive tool when you need OR, NOT, existence checks, numeric comparisons, or soft preferences.

## 12. Command Reference

| Task | Command |
|---|---|
| Label a node | `kubectl label node <node> disktype=ssd` |
| Remove a node label | `kubectl label node <node> disktype-` |
| Show node labels | `kubectl get nodes --show-labels` |
| Inspect one node | `kubectl describe node <node>` |
| Apply a manifest | `kubectl apply -f nodeAffinity-required.yaml` |
| See Pod status / node | `kubectl get pods -o wide` |
| Debug a Pending Pod | `kubectl describe pod <pod>` (read Events) |

> Node Affinity itself is defined entirely in the **Pod manifest** — there's no imperative `kubectl` flag for it. You only use `kubectl` to **label nodes** and to **apply/inspect** the Pod.

## 13. Hands-on Lab — Required and Preferred

**Goal:** Prove the hard vs soft behaviour on a single-node cluster.

### Step 1: Confirm the node has no `disktype` label

```bash
kubectl get nodes --show-labels     # no disktype=ssd present
```

### Step 2: Apply Required → expect Pending

```bash
kubectl apply -f nodeAffinity-required.yaml   # (manifest from Section 7)
kubectl get pods                              # STATUS = Pending
kubectl describe pod nginx                     # Events: didn't match node affinity
kubectl delete pod nginx
```

### Step 3: Apply Preferred → expect Running

```bash
kubectl apply -f nodeAffinity-preferred.yaml  # (manifest from Section 8)
kubectl get pods                              # STATUS = Running (no match needed)
kubectl delete pod nginx
```

### Step 4: Apply Required again, then add the label → watch it schedule

```bash
kubectl apply -f nodeAffinity-required.yaml
kubectl get pods                              # Pending
kubectl label node <node-name> disktype=ssd   # add the required label
kubectl get pods                              # Running — scheduled automatically
```

### Step 5: Cleanup

```bash
kubectl delete pod nginx
kubectl label node <node-name> disktype-       # remove the label
```

**Expected outcome:** Required blocks scheduling until a matching node exists; Preferred never blocks.

## 15. Summary

### The Full Picture

```
Node Selector (strict equality):
  nodeSelector: { size: medium }        ✗ no OR, no NOT, no preferences

Node Affinity (flexible + expressive):
  spec.affinity.nodeAffinity
    ├── requiredDuringSchedulingIgnoredDuringExecution   (HARD)
    │     → no match ⇒ Pod stays Pending
    └── preferredDuringSchedulingIgnoredDuringExecution  (SOFT)
          → no match ⇒ Pod still scheduled elsewhere

  Operators: In, NotIn, Exists, DoesNotExist, Gt, Lt
  IgnoredDuringExecution ⇒ running Pods are NOT moved when labels change
```

### Key Points to Remember

- **Node Affinity = a more flexible, more expressive Node Selector.**
- It fixes Node Selector's limits: it supports **OR** (`In` a set), **NOT** (`NotIn` / `DoesNotExist`), **existence** (`Exists`), and **numeric** comparisons (`Gt`, `Lt`).
- Two approaches: **Required** (hard — Pod `Pending` if no match) and **Preferred** (soft — Pod runs anyway).
- Full field names: **`requiredDuringSchedulingIgnoredDuringExecution`** and **`preferredDuringSchedulingIgnoredDuringExecution`**.
- **`IgnoredDuringExecution`** = rules apply only at **scheduling** time; a running Pod is **not evicted** when node labels later change.
- Manifest hierarchy: `spec → affinity → nodeAffinity → required/preferred → … → matchExpressions (key / operator / values)`.
- **Required** uses `nodeSelectorTerms → matchExpressions`; **Preferred** uses a list of `- weight` + `preference → matchExpressions`.
- **Don't memorise the syntax** — understand the hierarchy and copy the skeleton from the Kubernetes docs.
- Like Node Selector, a Required Pod with no matching node **waits** (`Pending`) rather than erroring, and schedules automatically once a match appears.
- Node Affinity is defined **entirely in the Pod manifest**; `kubectl` is only used to **label nodes** and apply/inspect.
