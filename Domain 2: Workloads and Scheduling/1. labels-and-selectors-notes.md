# Labels and Selectors — Domain 2: Workloads and Scheduling

---

## 1. What are Labels and Selectors?

> **Labels** are **key/value pairs** you attach to Kubernetes objects (Pods, Services, Deployments, ConfigMaps, etc.) to give them meaning — environment, app name, tier, owner, etc.
>
> **Selectors** are filters you use to **pick** objects based on their labels.

In plain English:
- A **label** is a sticker you put on an object that says something like `env=prod` or `app=payments`.
- A **selector** is the question *"Show me all objects whose sticker says X."*

```
       Pods with Labels                       Selector: env=dev
   ┌───────────────────────────┐             ┌────────────────────┐
   │  Pod-1  env: dev           │             │  Pod-1  env: dev    │
   │  Pod-2  env: prod          │   filter    │  Pod-3  env: dev    │
   │  Pod-3  env: dev           │  ───────►   │  Pod-5  env: dev    │
   │  Pod-4  env: prod          │             │                    │
   │  Pod-5  env: dev           │             │                    │
   │  Pod-6  env: prod          │             │                    │
   └───────────────────────────┘             └────────────────────┘
```

> Labels and selectors **always go together** — labels mean nothing without a way to query them, and selectors mean nothing without labels to match against.

---

## 2. Why Labels and Selectors — What Challenges Do They Solve?

### Challenge 1: You Cannot Tell What an Object Is by Looking at Its Name

In a real cluster you may have hundreds of pods (e.g., `pod-1`, `pod-2`, `payment-7d6f`, `gateway-abc`). Just from the name, it is impossible to tell which is dev, which is prod, which is a database, which is the front end.

**Labels solve this** by tagging each object with meaningful metadata (`env=prod`, `tier=db`).

> Real-world horror story from the transcript: a team member was asked to "delete the dev EC2 instance" — there were no labels, so they accidentally deleted the **staging** environment instead. Labels prevent this kind of mistake.

---

### Challenge 2: You Cannot Filter Hundreds of Objects Manually

Listing every pod and visually picking the dev ones is fine when you have 3 pods. With 1,000 pods, it is impossible.

**Selectors solve this** by letting you filter on the fly: *"show me all pods where env=dev."*

---

### Challenge 3: Higher-Level Objects Need to Group Pods

A Service does not talk to a specific pod by name — it talks to **any pod with this label**. A Deployment does not own specific pods by name — it owns **any pod whose labels match its selector**.

**Labels + selectors solve this** by being the **glue** that connects higher-level Kubernetes objects (Services, Deployments, ReplicaSets) to the right Pods.

---

## 3. Labels — Simple Definition and Examples

> A **label** is a key/value pair stored in an object's `metadata.labels` field.

A single object can have **many labels**:

```
   Pod: payments-7d6f
   ┌─────────────────────────────┐
   │  labels:                     │
   │    name: kplabs-gateway      │
   │    env:  production          │
   │    tier: frontend            │
   │    app:  payments            │
   └─────────────────────────────┘
```

Common labels you will see in production:

| Key | Example values | Meaning |
|---|---|---|
| `app` | `frontend`, `payments`, `redis` | What application this is |
| `env` | `dev`, `staging`, `prod` | Which environment |
| `tier` | `frontend`, `backend`, `db` | Architectural tier |
| `release` | `stable`, `canary` | Release channel |
| `version` | `v1`, `v2.3.1` | Version of the app |

> **Analogy from the transcript**: in AWS, you call these **tags**. In Kubernetes, they are **labels**. Same idea, different name.

---

## 4. Selectors — Simple Definition and Examples

> A **selector** is an expression that matches objects by their labels.

Two basic forms:

| Selector | Meaning |
|---|---|
| `env=dev` | Match where `env` equals `dev` |
| `env!=dev` | Match where `env` is **not** `dev` (also matches pods without the `env` label set to dev) |

You can combine multiple conditions with a comma — all must match (AND):

```
env=prod,tier=backend
```

---

## 5. Where Labels and Selectors Are Used in Kubernetes

| Object | How it uses labels/selectors |
|---|---|
| **Pod** | Carries labels in `metadata.labels` |
| **Service** | Routes traffic to pods that match `spec.selector` |
| **Deployment / ReplicaSet** | Owns pods that match `spec.selector.matchLabels` |
| **NetworkPolicy** | Selects pods to apply policy to via `podSelector` |
| **kubectl** | Uses `-l` / `--selector` to filter `get`, `delete`, etc. |

Without labels, none of these higher-level resources would work — they all rely on label matching.

## 6. Syntax — Quick Reference

### Labels in a Pod Manifest (YAML)

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
  labels:                    # labels go inside metadata
    env: dev
    app: nginx
spec:
  containers:
  - name: nginx
    image: nginx
```

> Labels always sit inside `metadata`, next to `name`.

### Add a Label via CLI

```bash
kubectl label pod <pod-name> <key>=<value>
# Example:
kubectl label pod pod-1 env=dev
```

### Add a Label to All Pods at Once

```bash
kubectl label pods --all status=running
```

### Remove a Label via CLI

```bash
kubectl label pod <pod-name> <key>-
# the trailing dash removes the label
# Example:
kubectl label pod pod-1 env-
```

### Overwrite an Existing Label

```bash
kubectl label pod <pod-name> <key>=<new-value> --overwrite
```

### View Labels

```bash
kubectl get pods --show-labels
kubectl describe pod <pod-name>            # see labels under metadata
```

### Filter Using a Selector

```bash
kubectl get pods -l env=dev                # equal
kubectl get pods -l env!=dev               # not equal
kubectl get pods -l 'env in (dev,stage)'   # set-based
kubectl get pods -l 'env notin (prod)'     # set-based negative
kubectl get pods -l env=prod,tier=backend  # AND
```

### Selectors in YAML (e.g., Service)

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  selector:                  # matches pods with these labels
    app: web
    env: prod
  ports:
  - port: 80
```

### matchLabels in a Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  selector:
    matchLabels:             # deployment owns pods with these labels
      app: web
  template:
    metadata:
      labels:                 # pod labels must match the selector above
        app: web
    spec:
      containers:
      - name: web
        image: nginx
```

## 7. Examples

### Example 1 — Create Pods and Add Labels via CLI

```bash
# Create 3 pods
kubectl run pod-1 --image=nginx
kubectl run pod-2 --image=nginx
kubectl run pod-3 --image=nginx

# Default labels Kubernetes adds: run=pod-1, run=pod-2, run=pod-3
kubectl get pods --show-labels

# Add meaningful labels
kubectl label pod pod-1 env=dev
kubectl label pod pod-2 env=stage
kubectl label pod pod-3 env=prod

kubectl get pods --show-labels
# pod-1  ...  env=dev,run=pod-1
# pod-2  ...  env=stage,run=pod-2
# pod-3  ...  env=prod,run=pod-3
```

### Example 2 — Filter Pods Using a Selector

```bash
kubectl get pods -l env=dev
# pod-1   1/1   Running

kubectl get pods -l env=prod
# pod-3   1/1   Running

kubectl get pods -l env!=dev
# pod-2   1/1   Running
# pod-3   1/1   Running
```

### Example 3 — Combine Multiple Labels

```bash
kubectl label pod pod-1 tier=frontend
kubectl label pod pod-3 tier=frontend

kubectl get pods -l env=prod,tier=frontend
# pod-3   1/1   Running
```

### Example 4 — Pod with Multiple Labels in YAML

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
  labels:
    run: nginx
    env: dev
    tier: frontend
spec:
  containers:
  - name: nginx
    image: nginx
```

```bash
kubectl apply -f nginx-pod.yaml
kubectl get pods --show-labels
# nginx   1/1   Running   ...   env=dev,run=nginx,tier=frontend
```

### Example 5 — Remove a Label

```bash
kubectl label pod pod-1 env-
kubectl get pods --show-labels
# pod-1   ...   run=pod-1     <-- env label is gone
```

### Example 6 — Label All Pods at Once

```bash
kubectl label pods --all status=running
kubectl get pods --show-labels
# All pods now have status=running
```

### Example 7 — Service Using a Selector

```yaml
# Pod
apiVersion: v1
kind: Pod
metadata:
  name: web
  labels:
    app: web
spec:
  containers:
  - name: web
    image: nginx

---
# Service that targets the pod via its label
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  selector:
    app: web              # routes to any pod with label app=web
  ports:
  - port: 80
    targetPort: 80
```

The Service automatically routes traffic to **every pod** with `app=web` — add another such pod and the Service picks it up.

1. Run `kubectl label pods --all status=running`.
2. Verify all pods now show `status=running`.

**Exercise 6 — Describe a Pod's Labels**

## 9. Important Points to Remember

- Labels live under **`metadata.labels`**, never inside `spec`.
- A single object can have **many labels** — there is no limit.
- Selectors are how **Services, Deployments, ReplicaSets, NetworkPolicies** find their target pods.
- The default `kubectl run` adds a label of the form `run=<pod-name>`.
- The trailing dash (`env-`) is the way to **remove** a label.
- Add `--overwrite` when you want to change an existing label's value.
- You can filter `kubectl get`, `kubectl delete`, `kubectl label` itself, and more, using `-l`.
- Labels and selectors are used **most heavily in YAML manifests** for Deployments and Services — get comfortable with them.

## 10. Summary

| Concept | Detail |
|---|---|
| **Label** | A key/value pair attached to an object's `metadata.labels` |
| **Selector** | An expression that filters objects by their labels |
| **Where labels live** | `metadata.labels` |
| **Add label (CLI)** | `kubectl label <object> <name> <key>=<value>` |
| **Remove label (CLI)** | `kubectl label <object> <name> <key>-` |
| **Overwrite label (CLI)** | Add `--overwrite` |
| **Apply to all** | `kubectl label pods --all <key>=<value>` |
| **View labels** | `kubectl get pods --show-labels` |
| **Filter (CLI)** | `kubectl get pods -l <selector>` |
| **Selector operators** | `=`, `!=`, `in (...)`, `notin (...)`, comma = AND |
| **Used by** | Services, Deployments, ReplicaSets, NetworkPolicies, etc. |
| **Default `run` label** | `run=<pod-name>` |
| **Real-world value** | Prevents mistakes (deleting wrong env), enables filtering at scale |
