# Horizontal Pod Autoscaler (HPA) — Domain 3: Services and Networking

---

## 1. What is the Horizontal Pod Autoscaler?

> The **Horizontal Pod Autoscaler (HPA)** is a Kubernetes object that **automatically increases or decreases the number of pods** in a Deployment, ReplicaSet, ReplicationController, or StatefulSet, based on observed **CPU utilization**, **memory usage**, or **custom metrics**.

- "Horizontal" scaling = **adding or removing pods**. (It is different from "Vertical" scaling, which would mean giving each pod more CPU or memory.)
- HPA keeps watching the metrics and adjusts the **replica count** of the workload up or down automatically.

```
                Horizontal Pod Autoscaler
                          │
                          │  watches CPU / memory metrics
                          ▼
                  ┌────────────────────┐
                  │     DEPLOYMENT     │
                  │    (php-apache)    │
                  └────────────────────┘
                          │
   Low load:   ──►  [ Pod-1 ]
   High load:  ──►  [ Pod-1 ] [ Pod-2 ] [ Pod-3 ]
```

---

## 2. Why HPA — What Challenges Does It Solve?

### Challenge 1: Workloads in Kubernetes are not static

Traffic to applications running in Kubernetes is **not constant**. It changes based on user demand, traffic spikes (e.g., weekends, holidays), or sudden computational needs.

- If you run **too few pods**, the application becomes slow or crashes when traffic spikes.
- If you run **too many pods all the time**, you waste CPU and memory.

**HPA solves this** by automatically adding pods when load goes up, and removing them when load comes back down.

---

### Challenge 2: Manual scaling is too slow

Without HPA, someone has to manually run `kubectl scale deployment ... --replicas=N` whenever the load changes. This is too slow for sudden spikes and impossible at odd hours.

**HPA solves this** by reacting automatically — no human action needed.

---

### Challenge 3: Cloud-style auto scaling, but inside Kubernetes

Cloud providers (AWS, GCP, Azure) provide auto scaling at the **VM/server** level. Kubernetes needs the same idea at the **pod** level, so applications can scale without provisioning new VMs.

**HPA solves this** by giving Kubernetes its own pod-level auto scaler that reacts to live metrics.

```
       1. Scale Out  → Add pods when resource usage goes up
       2. Scale In   → Remove pods when resource usage comes down
```

---

## 3. How HPA Works (in Simple Kubernetes Terms)

1. You create a **Deployment** that runs some pods.
2. You create an **HPA** object and point it at that Deployment using `scaleTargetRef`.
3. You tell the HPA:
   - **Minimum replicas** (e.g., 1)
   - **Maximum replicas** (e.g., 3)
   - **Target metric** (e.g., CPU utilization = 50%)
4. The HPA continuously asks the **Metrics Server** for current CPU/memory usage of the pods.
5. If actual usage > target → HPA **scales out** (adds pods, up to the max).
6. If actual usage < target → HPA **scales in** (removes pods, down to the min) — after a delay.

```
HPA → Metrics Server → Pod CPU/Memory → decision → Deployment.spec.replicas updated
```

---

## 4. Important Points to Remember

- **HPA requires the Metrics Server.** Without it, HPA cannot read CPU/memory data and the TARGETS column shows `<unknown>`.
- The Deployment's pod spec **must define `resources.requests`** for CPU (or memory). HPA uses requests to calculate utilization percentage. Without requests, HPA will not scale.
- HPA works **only with scalable workloads**: Deployment, ReplicaSet, ReplicationController, StatefulSet.
- **HPA does NOT work with DaemonSets** — DaemonSets cannot be scaled (they run one pod per node by design).
- **Scale Out is fast**, **Scale In is slow** by design:
  - When load spikes up → HPA adds pods almost immediately.
  - When load drops → HPA waits before removing pods. This wait is called the **stabilization window** (default **300 seconds / 5 minutes** for scale-down).
  - This delay prevents flapping (rapid up-down-up) which would cause service instability.
- New pods added by HPA may stay in `Pending` if the cluster does not have enough free CPU/memory — this is a cluster capacity issue, not an HPA problem.

---

## 5. Stabilization Window (Scale Down Delay)

Sometimes the metric drops only briefly (a "temporary dip"). If HPA reacted instantly, it would remove pods, and then the load could come back and overload the system. That is called **flapping** and causes **service instability**.

To prevent this, HPA uses a **stabilization window** — a waiting period before scaling down.

| Direction | Default Stabilization Window |
|---|---|
| **Scale Up** | `0` seconds (no delay — react immediately) |
| **Scale Down** | `300` seconds (5 minutes delay) |

You can override these defaults using the `behavior` field on the HPA:

```yaml
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300    # default
  scaleUp:
    stabilizationWindowSeconds: 0      # default
```

In the transcript, the value is changed to `60` seconds — and the deployment scales back from 5 → 1 in about a minute instead of five.

## 6. Syntax

### Create an HPA Imperatively

```bash
kubectl autoscale deployment <deployment-name> --cpu-percent=<target> --min=<min> --max=<max>
```

Example:

```bash
kubectl autoscale deployment php-apache --cpu-percent=50 --min=1 --max=3
```

### Inspect / Watch HPA

```bash
kubectl get hpa
kubectl get hpa <name> --watch
kubectl describe hpa <name>
```

### Delete HPA

```bash
kubectl delete hpa <name>
```

### HPA Manifest (Declarative)

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: php-apache
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: php-apache
  minReplicas: 1
  maxReplicas: 3
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
```

### Deployment Must Have Resource Requests

```yaml
spec:
  containers:
  - name: php-apache
    image: registry.k8s.io/hpa-example
    resources:
      requests:
        cpu: 200m       # required so HPA can calculate utilization %
```

### Custom Stabilization Window

```yaml
spec:
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 60    # custom — was 300 by default
    scaleUp:
      stabilizationWindowSeconds: 0
```

## 7. Examples

### Example 1: Create the HPA Imperatively

```bash
# 1. Deployment (must already exist with CPU requests defined)
kubectl get deployment php-apache

# 2. Create the HPA
kubectl autoscale deployment php-apache --cpu-percent=50 --min=1 --max=3

# 3. Verify
kubectl get hpa
# NAME         REFERENCE               TARGETS    MINPODS   MAXPODS   REPLICAS
# php-apache   Deployment/php-apache   2%/50%     1         3         1
```

It can take 20–30 seconds for the TARGETS column to update from `<unknown>/50%` to a real value.

---

### Example 2: Watch HPA Scale Out

In **terminal 1**:

```bash
kubectl get hpa php-apache --watch
```

In **terminal 2** — generate traffic from inside the cluster:

```bash
kubectl run load-generator --rm -it --image=busybox -- /bin/sh
# inside the pod:
while true; do wget -q -O- http://php-apache; done
```

Output in terminal 1:

```
NAME         TARGETS         REPLICAS   AGE
php-apache   2%/50%          1          59s
php-apache   380%/50%        1          90s
php-apache   380%/50%        3          106s    ◄── scaled out
php-apache   902%/50%        3          2m1s
```

Scale-out happens **fast** — within ~15 seconds of the spike.

---

### Example 3: Watch HPA Scale In (Default Window)

Stop the load with `Ctrl+C`, then keep watching:

```
TIME          TARGETS         REPLICAS
2m46s         7%/50%          3
3m1s          2%/50%          3
7m31s         2%/50%          3
7m46s         2%/50%          1       ◄── finally scaled in
```

It takes **about 5 minutes** for scale-in, even though CPU dropped immediately. This is the **default 300s stabilization window**.

---

### Example 4: HPA with Custom 60-Second Stabilization Window

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: cpu-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: php-apache
  minReplicas: 1
  maxReplicas: 5
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 60
```

After load drops from 712% → 2%, the replicas go from `5 → 1` in roughly **60 seconds** instead of five minutes:

```
TIME          TARGETS         REPLICAS
75s           840%/50%        1
90s           1700%/50%       5         ◄── scaled out
2m            712%/50%        5
2m30s         2%/50%          5
3m15s         2%/50%          5
3m30s         2%/50%          1         ◄── scaled in (60s after drop)
```

---

### Example 5: Pending Pods on a Small Cluster

After scaling out:

```bash
kubectl get pods
# NAME                          READY   STATUS    AGE
# php-apache-xxx-1              1/1     Running   10m
# php-apache-xxx-2              0/1     Pending   30s
# php-apache-xxx-3              0/1     Pending   30s
```

```bash
kubectl describe pod php-apache-xxx-2
# Events:  0/1 nodes are available: insufficient cpu
```

This is **not** a bug in HPA — the cluster simply has no free CPU to schedule new pods.

## 8. Exercises to Practice for the CKAD Exam

### Imperative (CLI-based) Exercises

**Exercise 1 — Confirm Prerequisites**
1. Run `kubectl top pods` and confirm the Metrics Server is installed and returning CPU/memory data.
2. If it returns `Metrics API not available`, install the Metrics Server before continuing.

**Exercise 2 — Create the Deployment + Service**
1. Create a Deployment called `php-apache` using `registry.k8s.io/hpa-example`, exposing port `80`, with CPU requests set to `200m` (you may need declarative for resource requests; see Exercise 7).
2. Expose it as a ClusterIP service called `php-apache` on port `80`.

**Exercise 3 — Create HPA via CLI**
1. Run `kubectl autoscale deployment php-apache --cpu-percent=50 --min=1 --max=3`.
2. Verify with `kubectl get hpa` — wait until TARGETS shows a CPU number (not `<unknown>`).

**Exercise 4 — Generate Load and Watch Scale-Out**
1. In one terminal, watch the HPA: `kubectl get hpa --watch`.
2. In another, start a load generator pod:
   ```bash
   kubectl run load-gen --rm -it --image=busybox -- /bin/sh -c "while true; do wget -q -O- http://php-apache; done"
   ```
3. Observe replicas growing from 1 up to 3.

**Exercise 5 — Watch Scale-In Delay**
1. Stop the load generator with `Ctrl+C`.
2. Watch how long it takes for the replicas to scale back down to 1.
3. Confirm the time is approximately **5 minutes** (default stabilization window).

**Exercise 6 — Cleanup**
1. Delete the HPA: `kubectl delete hpa php-apache`.
2. Delete the Deployment and Service.
3. Verify all pods are gone.

---

### Declarative (YAML-based) Exercises

**Exercise 7 — Deployment with Resource Requests**
1. Write a Deployment manifest for `php-apache`:
   - Image: `registry.k8s.io/hpa-example`
   - Replicas: `1`
   - `resources.requests.cpu: 200m`
2. Write a matching Service manifest of type `ClusterIP` on port `80`.
3. Apply both.

**Exercise 8 — Basic HPA Manifest**
1. Write an HPA manifest (`apiVersion: autoscaling/v2`) that targets the `php-apache` deployment.
2. Set `minReplicas: 1`, `maxReplicas: 5`, and target CPU utilization of `50%`.
3. Apply and verify with `kubectl get hpa`.

**Exercise 9 — Custom Stabilization Window**
1. Modify the HPA from Exercise 8 to add a **60-second** `scaleDown` stabilization window via the `behavior` field.
2. Apply the change.
3. Generate load, wait for scale-out to 5 replicas, then stop the load.
4. Verify the scale-in happens in ~60 seconds (instead of ~300 seconds).

**Exercise 10 — Negative Case: Missing CPU Requests**
1. Create a Deployment **without** any CPU resource requests.
2. Apply an HPA targeting that Deployment.
3. Run `kubectl get hpa` — observe TARGETS shows `<unknown>/50%`.
4. Add CPU requests back to the Deployment and verify metrics start showing up.

**Exercise 11 — Memory-Based HPA**
1. Write an HPA manifest that scales based on **memory utilization** instead of CPU (target `60%`).
2. Apply and verify the manifest is accepted and active.

**Exercise 12 — DaemonSet Cannot Be Scaled**
1. Try writing an HPA manifest with `scaleTargetRef.kind: DaemonSet`.
2. Apply it and observe the error.
3. Explain *why* HPA does not work with DaemonSets.

## 9. Summary

| Concept | Detail |
|---|---|
| **What it is** | A Kubernetes object that auto-scales the number of pods in a workload up or down |
| **Why it exists** | Traffic is dynamic — manual scaling is too slow and either over- or under-provisions |
| **Works with** | Deployment, ReplicaSet, ReplicationController, StatefulSet |
| **Does NOT work with** | DaemonSet (cannot be scaled) |
| **Requires** | Metrics Server installed + pods must define `resources.requests` |
| **Metric types** | CPU utilization, memory utilization, custom metrics |
| **Scale Out** | Immediate when metrics exceed target |
| **Scale In** | Delayed — default stabilization window is **300 seconds (5 minutes)** |
| **Default scaleUp delay** | `0` seconds |
| **Default scaleDown delay** | `300` seconds |
| **Imperative create** | `kubectl autoscale deployment <name> --cpu-percent=50 --min=1 --max=3` |
| **Declarative apiVersion** | `autoscaling/v2` (preferred) |
| **Inspect HPA** | `kubectl get hpa`, `kubectl describe hpa <name>`, `kubectl get hpa --watch` |
| **`<unknown>` in TARGETS** | Means either Metrics Server is missing or Deployment has no resource requests |
| **Pending new pods** | Means cluster does not have free CPU/memory — not an HPA bug |
