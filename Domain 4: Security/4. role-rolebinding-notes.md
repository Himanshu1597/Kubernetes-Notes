# Role and RoleBinding — Domain 4: Security

---

## 1. Recap: RBAC Building Blocks

| Concept | Scope | What it does |
|---|---|---|
| **Role** | Namespace | Defines a set of permissions inside **one namespace**. |
| **RoleBinding** | Namespace | Binds a Role to subjects (Users, Groups, ServiceAccounts) in **one namespace**. |
| **ClusterRole** | Cluster-wide | Defines permissions across **all namespaces** or for cluster-scoped resources. |
| **ClusterRoleBinding** | Cluster-wide | Binds a ClusterRole to subjects across the whole cluster. |

This note covers **Role** and **RoleBinding** — the namespace-scoped pair. For cluster-wide RBAC, see [clusterrole-clusterrolebinding-notes.md](clusterrole-clusterrolebinding-notes.md). For the overall RBAC overview, see [rbac-notes.md](rbac-notes.md).

---

## 2. What is a Role?

> A **Role** is a Kubernetes object that **defines a set of permissions** (`apiGroups` + `resources` + `verbs`) for a **single namespace**.

In plain English: *"In this namespace, allow these actions on these resources."*

```
   Role: pod-read-only
   namespace: default
   ┌──────────────────────────────────┐
   │  apiGroups:  [""]                 │
   │  resources:  ["pods"]             │
   │  verbs:      ["list", "get"]      │
   └──────────────────────────────────┘
                  ▲
                  │  (does nothing until bound)
```

> A Role on its own grants nothing. It must be attached to a Subject via a RoleBinding.

---

## 3. What is a RoleBinding?

> A **RoleBinding** is a Kubernetes object that **attaches a Role to one or more Subjects** (Users, Groups, ServiceAccounts) within a **single namespace**.

```
   RoleBinding: test-binding
   namespace: default
   ┌──────────────────────────────────┐
   │  subjects:                        │
   │   - kind: User                    │
   │     name: bob                     │
   │  roleRef:                         │
   │     kind: Role                    │
   │     name: pod-read-only           │
   └──────────────────────────────────┘
```

After this binding, `bob` can do whatever `pod-read-only` allows — but **only in the `default` namespace**.

---

## 4. Why Role + RoleBinding — What Challenges Do They Solve?

### Challenge 1: Different Namespaces Need Different Permissions

Team A works in the `team-a` namespace, Team B in `team-b`. They should not see each other's pods. A cluster-wide grant would be too broad.

**Role solves this** by being **namespace-scoped**. You create one Role in each namespace with the right permissions for that team.

---

### Challenge 2: Most Resources are Namespace-Scoped

Pods, ConfigMaps, Secrets, Services, Deployments — all live inside a namespace. Granting access to them only makes sense with a namespace scope.

**Role + RoleBinding solve this** by limiting access exactly to one namespace's worth of those resources.

---

## 5. Key Points to Remember

- A Role only grants permissions **inside its own namespace**. If you bind `bob` to a Role in `default`, he cannot use the same permission in `kube-system`.
- If you do not specify a namespace when creating a Role, it goes into the **default** namespace.
- A Role **cannot grant access to cluster-scoped resources** (nodes, persistent volumes, namespaces themselves) — use a ClusterRole for those.
- A RoleBinding's `roleRef` is **immutable** — to switch its Role you must delete and recreate the binding.
- A RoleBinding can reference a Role **in the same namespace**, OR a ClusterRole (which grants only that ClusterRole's permissions, but scoped to this binding's namespace).

## 6. Syntax — Imperative (CLI)

### Create a Role

```bash
kubectl create role <role-name> \
  --verb=<verb1>,<verb2> \
  --resource=<resource1>,<resource2> \
  [-n <namespace>]
```

Example:

```bash
kubectl create role pod-reader --verb=list,get --resource=pods
```

### Create a RoleBinding

```bash
# Bind a Role to a User
kubectl create rolebinding <name> --role=<role> --user=<user>

# Bind a Role to a ServiceAccount
kubectl create rolebinding <name> --role=<role> \
  --serviceaccount=<namespace>:<sa-name>

# Bind a Role to a Group
kubectl create rolebinding <name> --role=<role> --group=<group>
```

Example:

```bash
kubectl create rolebinding test-binding \
  --role=pod-reader \
  --user=bob
```

### Generate the YAML with Dry-Run

```bash
kubectl create role pod-reader --verb=list --resource=pods \
  --dry-run=client -o yaml

kubectl create rolebinding test-binding --role=pod-reader --user=bob \
  --dry-run=client -o yaml
```

> When you use the CLI, Kubernetes automatically figures out the correct `apiGroup`. With YAML you have to specify it yourself.

### Inspect / Delete

```bash
kubectl get roles -n <namespace>
kubectl get rolebindings -n <namespace>
kubectl describe role <role-name> -n <namespace>
kubectl describe rolebinding <rb-name> -n <namespace>
kubectl delete role <role-name> -n <namespace>
kubectl delete rolebinding <rb-name> -n <namespace>
```

## 7. Syntax — Declarative (YAML)

### Role

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-read-only
  namespace: default          # explicit namespace
rules:
- apiGroups: [""]             # "" = core API group
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
```

### RoleBinding

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: test-binding
  namespace: default
subjects:
- kind: User
  name: bob
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-read-only
  apiGroup: rbac.authorization.k8s.io
```

### Binding a ServiceAccount Instead of a User

```yaml
subjects:
- kind: ServiceAccount
  name: test-sa
  namespace: default
```

## 8. Examples

### Example 1 — Before: Bob Cannot List Pods

```bash
# As bob
kubectl get pods
# Error from server (Forbidden): pods is forbidden:
# User "bob" cannot list resource "pods" in API group "" in the namespace "default"
```

### Example 2 — Create a Role and RoleBinding for Bob

```bash
# Admin creates the Role
kubectl create role pod-read-only --verb=list --resource=pods

# Admin creates the RoleBinding
kubectl create rolebinding test-binding \
  --role=pod-read-only \
  --user=bob
```

Now Bob can list pods in the `default` namespace:

```bash
# As bob
kubectl get pods                  # ✓ works (default namespace)
kubectl get pods -n kube-system   # ✗ forbidden (different namespace)
kubectl delete pod test-pod       # ✗ forbidden (no delete verb)
kubectl get secrets               # ✗ forbidden (resource not in role)
```

### Example 3 — Test Using a ServiceAccount + Token + curl

```bash
# Setup the SA + token
kubectl create serviceaccount test-sa
TOKEN=$(kubectl create token test-sa --duration=100h)

# Without binding — forbidden
curl -k -H "Authorization: Bearer $TOKEN" \
  https://<api-server>:6443/api/v1/namespaces/default/pods
# 403 Forbidden

# Bind a Role to the SA
kubectl create role pod-reader --verb=list --resource=pods
kubectl create rolebinding test-binding \
  --role=pod-reader \
  --serviceaccount=default:test-sa

# Now the same curl succeeds
curl -k -H "Authorization: Bearer $TOKEN" \
  https://<api-server>:6443/api/v1/namespaces/default/pods
# 200 OK, returns pod list
```

### Example 4 — Generate Manifests from CLI

```bash
kubectl create role pod-reader --verb=list --resource=pods \
  --dry-run=client -o yaml > role.yaml

kubectl create rolebinding test-binding \
  --role=pod-reader --user=bob \
  --dry-run=client -o yaml > rolebinding.yaml
```

You can now version-control these YAML files.

### Example 5 — Multi-Rule Role

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: dev-role
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods", "configmaps"]
  verbs: ["get", "list", "watch"]
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "create", "update"]
```

This Role lets the subject read pods/configmaps and manage deployments — but **only in the `dev` namespace**.

## 9. Exercises to Practice for the CKAD Exam

### Imperative (CLI-based) Exercises

**Exercise 1 — Confirm No Permission**
1. As any unprivileged user (or via a token from a brand new SA), run `kubectl get pods`.
2. Confirm the response is `forbidden`.

**Exercise 2 — Create a Read-Only Role for Pods**
1. Run `kubectl create role pod-viewer --verb=get,list,watch --resource=pods -n default`.
2. Describe the role and confirm the resource and verbs.

**Exercise 3 — Bind the Role**
1. Run `kubectl create rolebinding view-pods --role=pod-viewer --user=alice -n default`.
2. Describe the binding and confirm the user is `alice` and `roleRef` points to `pod-viewer`.

**Exercise 4 — Test the Permission**
1. Run `kubectl auth can-i list pods --as=alice -n default` → expect **yes**.
2. Run `kubectl auth can-i delete pods --as=alice -n default` → expect **no**.
3. Run `kubectl auth can-i list pods --as=alice -n kube-system` → expect **no**.

**Exercise 5 — Bind a Role to a ServiceAccount**
1. Create `kubectl create serviceaccount app-sa -n default`.
2. Create a Role allowing `get,list` on `configmaps`.
3. Bind it: `kubectl create rolebinding app-binding --role=cm-reader --serviceaccount=default:app-sa`.
4. Verify with `kubectl auth can-i list configmaps --as=system:serviceaccount:default:app-sa -n default` → expect **yes**.

**Exercise 6 — Generate YAML from CLI**
1. Use `--dry-run=client -o yaml` to generate a Role YAML for `list/get` on pods.
2. Use the same trick to generate the RoleBinding YAML.
3. Save both files.

---

### Declarative (YAML-based) Exercises

**Exercise 7 — Write a Role from Scratch**
1. Write a Role manifest named `dev-role` in the `dev` namespace that allows `get,list,watch` on **pods** (core) and `get,list,create` on **deployments** (apps).
2. Apply and verify with `kubectl describe role dev-role -n dev`.

**Exercise 8 — Write a RoleBinding for a Group**
1. Write a RoleBinding manifest that binds `dev-role` to a Group named `developers` in the `dev` namespace.
2. Apply and verify with `kubectl describe rolebinding ... -n dev`.

**Exercise 9 — Bind to a ServiceAccount via YAML**
1. Modify the RoleBinding from Exercise 8 to bind to the ServiceAccount `dev-sa` in the `dev` namespace instead of the group.
2. Apply and confirm with `kubectl auth can-i ... --as=system:serviceaccount:dev:dev-sa -n dev`.

**Exercise 10 — Cross-Namespace Negative Test**
1. Create the same `pod-read-only` Role in `default` only.
2. Bind a ServiceAccount to it.
3. From a pod using that SA, try to list pods in `kube-system` via curl → confirm `403 forbidden`.

**Exercise 11 — Multi-Rule Role**
1. Write a Role manifest with **two** rule blocks: one for pods (`list`) and one for secrets (`get`).
2. Apply and verify with `kubectl describe role`.

**Exercise 12 — Cleanup**
1. Delete the RoleBinding.
2. Run `kubectl get pods` as the bound user — confirm `forbidden` again.
3. Delete the Role.

## 10. Summary

| Concept | Detail |
|---|---|
| **Role** | A namespace-scoped set of permissions (`apiGroups` + `resources` + `verbs`) |
| **RoleBinding** | Binds a Role to subjects (User / Group / ServiceAccount) in **the same namespace** |
| **Scope** | Strictly one namespace — cross-namespace access is denied |
| **Cannot grant** | Access to cluster-scoped resources (nodes, persistent volumes) — use ClusterRole |
| **Immutable field** | `roleRef` in a RoleBinding cannot be changed — delete + recreate |
| **Imperative create** | `kubectl create role <name> --verb=... --resource=...` |
| **Imperative bind** | `kubectl create rolebinding <name> --role=<role> --user=<user>` |
| **API version** | `rbac.authorization.k8s.io/v1` |
| **CLI auto-fills apiGroup** | Yes — declarative YAML requires you to write it |
| **Default namespace if omitted** | `default` |
