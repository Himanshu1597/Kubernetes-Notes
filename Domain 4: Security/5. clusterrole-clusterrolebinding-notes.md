# ClusterRole and ClusterRoleBinding — Domain 4: Security

---

## 1. Recap: RBAC Building Blocks

| Concept | Scope | What it does |
|---|---|---|
| **Role** | Namespace | Defines permissions in **one namespace**. |
| **RoleBinding** | Namespace | Binds a Role to subjects in **one namespace**. |
| **ClusterRole** | Cluster-wide | Defines permissions across **all namespaces**, or for **cluster-scoped resources**. |
| **ClusterRoleBinding** | Cluster-wide | Binds a ClusterRole to subjects across the entire cluster. |

This note covers **ClusterRole** and **ClusterRoleBinding** — the cluster-scoped pair. For namespace-scoped RBAC, see [role-rolebinding-notes.md](role-rolebinding-notes.md). For the overall RBAC overview, see [rbac-notes.md](rbac-notes.md).

---

## 2. What is a ClusterRole?

> A **ClusterRole** is a Kubernetes object that **defines a set of permissions** that apply **across the whole cluster** — every namespace, including cluster-scoped resources like nodes.

```
   ClusterRole: pod-read-only
   ┌──────────────────────────────────┐
   │  apiGroups:  [""]                 │
   │  resources:  ["pods"]             │
   │  verbs:      ["list", "get"]      │
   └──────────────────────────────────┘
                  ▲
                  │  (still does nothing until bound)
```

Same fields as a Role — but **no `namespace`**, because the scope is the whole cluster.

---

## 3. What is a ClusterRoleBinding?

> A **ClusterRoleBinding** is a Kubernetes object that **attaches a ClusterRole to one or more Subjects** (Users, Groups, ServiceAccounts) **across the whole cluster**.

```
   ClusterRoleBinding: cluster-pod-readers
   ┌──────────────────────────────────┐
   │  subjects:                        │
   │   - kind: User                    │
   │     name: bob                     │
   │  roleRef:                         │
   │     kind: ClusterRole             │
   │     name: pod-read-only           │
   └──────────────────────────────────┘
```

After this binding, `bob` can do whatever `pod-read-only` allows — **in every namespace**, not just one.

---

## 4. Why ClusterRole + ClusterRoleBinding — What Challenges Do They Solve?

### Challenge 1: Some Resources are Cluster-Scoped

Resources like **nodes**, **namespaces**, **persistentVolumes**, **storageclasses**, **clusterroles**, and **clusterrolebindings** themselves do not live inside a namespace — they are cluster-wide.

**Role cannot grant access to these** (a Role is namespace-bound). **ClusterRole solves this** by being the only way to grant permissions on cluster-scoped resources.

---

### Challenge 2: Some Users Need Access Across All Namespaces

A platform admin or a monitoring tool may need to read pods in **every** namespace. Creating a separate Role + RoleBinding in each namespace is tedious and error-prone.

**ClusterRole + ClusterRoleBinding solve this** by granting the permission once, cluster-wide.

---

### Challenge 3: Reusable Permission Templates

Sometimes you want the same permission (e.g., "read configmaps") to be available in many namespaces, but assigned to different users in each.

**ClusterRole solves this** because a **RoleBinding can also reference a ClusterRole** — the ClusterRole acts as a reusable permission template, while the RoleBinding scopes it to a single namespace.

---

## 5. Key Points to Remember

- A ClusterRole has **no namespace** in its metadata — it is cluster-scoped.
- A ClusterRoleBinding grants the bound ClusterRole's permissions **across all namespaces**.
- To grant access to **cluster-scoped resources** (nodes, persistentvolumes, namespaces), you **must** use a ClusterRole — a Role cannot do this.
- A **RoleBinding can reference a ClusterRole** — when it does, the permissions apply only inside the RoleBinding's namespace. This is the way to reuse a ClusterRole as a per-namespace template.
- Kubernetes ships many **built-in ClusterRoles** (e.g., `cluster-admin`, `admin`, `edit`, `view`). Use them for common patterns instead of writing your own.
- `roleRef` on a ClusterRoleBinding is **immutable** — delete and recreate to switch roles.

## 6. Syntax — Imperative (CLI)

### Create a ClusterRole

```bash
kubectl create clusterrole <name> \
  --verb=<verb1>,<verb2> \
  --resource=<resource1>,<resource2>
```

Example:

```bash
kubectl create clusterrole pod-read-only --verb=list,get --resource=pods
```

### Create a ClusterRoleBinding

```bash
# Bind to a User
kubectl create clusterrolebinding <name> \
  --clusterrole=<cr> \
  --user=<user>

# Bind to a ServiceAccount
kubectl create clusterrolebinding <name> \
  --clusterrole=<cr> \
  --serviceaccount=<namespace>:<sa-name>

# Bind to a Group
kubectl create clusterrolebinding <name> \
  --clusterrole=<cr> \
  --group=<group>
```

Example:

```bash
kubectl create clusterrolebinding bob-read-pods \
  --clusterrole=pod-read-only \
  --user=bob
```

### Generate YAML with Dry-Run

```bash
kubectl create clusterrole pod-read-only --verb=list --resource=pods \
  --dry-run=client -o yaml

kubectl create clusterrolebinding bob-read-pods \
  --clusterrole=pod-read-only --user=bob \
  --dry-run=client -o yaml
```

### Inspect / Delete

```bash
kubectl get clusterrole
kubectl get clusterrolebinding
kubectl describe clusterrole <name>
kubectl describe clusterrolebinding <name>
kubectl delete clusterrole <name>
kubectl delete clusterrolebinding <name>
```

## 7. Syntax — Declarative (YAML)

### ClusterRole

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: pod-read-only       # no namespace — it is cluster-scoped
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
```

### ClusterRoleBinding

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: cluster-pod-readers
subjects:
- kind: User
  name: bob
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: pod-read-only
  apiGroup: rbac.authorization.k8s.io
```

### Bind a ServiceAccount

```yaml
subjects:
- kind: ServiceAccount
  name: test-sa
  namespace: default
```

### Bind a ClusterRole *Inside a Single Namespace* via a RoleBinding

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding             # NOTE: RoleBinding, not ClusterRoleBinding
metadata:
  name: pod-readers-in-dev
  namespace: dev
subjects:
- kind: User
  name: alice
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole           # references a ClusterRole
  name: pod-read-only
  apiGroup: rbac.authorization.k8s.io
```

This grants `alice` the `pod-read-only` permissions **only inside the `dev` namespace**, even though `pod-read-only` is a ClusterRole.

## 8. Examples

### Example 1 — Bob Cannot List Pods Anywhere

```bash
# As bob
kubectl get pods                       # ✗ forbidden
kubectl get pods -n kube-system        # ✗ forbidden
```

### Example 2 — Create a ClusterRole + ClusterRoleBinding

```bash
# Admin
kubectl create clusterrole pod-read-only --verb=list --resource=pods
kubectl create clusterrolebinding bob-read \
  --clusterrole=pod-read-only \
  --user=bob
```

Now Bob can list pods **anywhere**:

```bash
# As bob
kubectl get pods                       # ✓ default
kubectl get pods -n kube-system        # ✓ kube-system
kubectl get pods --all-namespaces      # ✓ all namespaces
kubectl delete pod x                   # ✗ no delete verb
kubectl get secrets                    # ✗ resource not in role
```

### Example 3 — Grant Access to a Cluster-Scoped Resource (Nodes)

```bash
kubectl create clusterrole node-viewer --verb=get,list --resource=nodes
kubectl create clusterrolebinding view-nodes \
  --clusterrole=node-viewer \
  --user=alice
```

Now `alice` can run `kubectl get nodes` — a Role + RoleBinding could not have granted this, because `nodes` are cluster-scoped.

### Example 4 — Use a Built-In ClusterRole

```bash
# Make bob a cluster admin
kubectl create clusterrolebinding bob-admin \
  --clusterrole=cluster-admin \
  --user=bob
```

`cluster-admin` is a built-in ClusterRole that grants **all permissions on everything**. Use with extreme caution.

### Example 5 — Reuse a ClusterRole in a Single Namespace

```bash
# pod-read-only ClusterRole already exists
# Grant alice read access to pods ONLY in the dev namespace:
kubectl create rolebinding alice-dev-reader \
  --clusterrole=pod-read-only \
  --user=alice \
  -n dev
```

Even though the source role is a ClusterRole, this RoleBinding limits the effect to the `dev` namespace.

### Example 6 — Test with ServiceAccount + curl

```bash
kubectl create serviceaccount test-sa
TOKEN=$(kubectl create token test-sa --duration=100h)

kubectl create clusterrole pod-reader --verb=list --resource=pods
kubectl create clusterrolebinding test-cluster-binding \
  --clusterrole=pod-reader \
  --serviceaccount=default:test-sa

# Works in every namespace
curl -k -H "Authorization: Bearer $TOKEN" \
  https://<api>:6443/api/v1/namespaces/kube-system/pods
# 200 OK
```

## 9. Exercises to Practice for the CKAD Exam

### Imperative (CLI-based) Exercises

**Exercise 1 — List Existing ClusterRoles**
1. Run `kubectl get clusterrole`.
2. Pick `view` and `edit`; describe each and read their `rules` blocks.

**Exercise 2 — Read-Only Across All Namespaces**
1. Create a ClusterRole `pod-viewer` allowing `get,list,watch` on `pods`.
2. Bind it to user `alice` with a ClusterRoleBinding.
3. Verify: `kubectl auth can-i list pods --as=alice -n kube-system` → expect **yes**.

**Exercise 3 — Grant Access to Nodes**
1. Create a ClusterRole `node-viewer` allowing `get,list` on `nodes`.
2. Bind it to a ServiceAccount.
3. Verify with `kubectl auth can-i list nodes --as=system:serviceaccount:default:<sa>`.

**Exercise 4 — Reuse a ClusterRole in One Namespace (via RoleBinding)**
1. With `pod-viewer` ClusterRole already existing, create a RoleBinding in the `dev` namespace that references `pod-viewer` for user `alice`.
2. Verify: `kubectl auth can-i list pods --as=alice -n dev` → expect **yes**.
3. Verify: `kubectl auth can-i list pods --as=alice -n kube-system` → expect **no**.

**Exercise 5 — Use the Built-In `cluster-admin`**
1. Create a ClusterRoleBinding that binds `cluster-admin` to a test user.
2. Confirm the user can do almost anything (do not commit this in a real cluster).
3. Delete the binding when done.

**Exercise 6 — Generate YAML from CLI**
1. Use `--dry-run=client -o yaml` to generate ClusterRole and ClusterRoleBinding manifests.
2. Save them to files.

---

### Declarative (YAML-based) Exercises

**Exercise 7 — Write a ClusterRole**
1. Write a ClusterRole manifest `multi-resource-viewer` that grants `get,list,watch` on:
   - `pods` (core)
   - `deployments` (apps)
   - `nodes` (core)
2. Apply and describe.

**Exercise 8 — ClusterRoleBinding for a Group**
1. Write a ClusterRoleBinding that binds `multi-resource-viewer` to a Group named `platform-team`.
2. Apply and verify.

**Exercise 9 — ServiceAccount Cluster Binding**
1. Write a ClusterRoleBinding YAML that binds an existing ClusterRole to a ServiceAccount `audit-sa` in the `audit` namespace.
2. Apply.
3. From a pod using that SA, verify cluster-wide access via curl.

**Exercise 10 — RoleBinding References a ClusterRole**
1. Write a RoleBinding YAML in the `dev` namespace that references the **ClusterRole** `pod-read-only` and binds it to user `bob`.
2. Apply.
3. Confirm Bob can list pods in `dev` but not in `default`.

**Exercise 11 — Cluster-Scoped Resource Negative Test**
1. Write a Role (not ClusterRole) that tries to grant `get` on `nodes`.
2. Apply and bind it to a user.
3. Verify the user still **cannot** list nodes (because nodes are cluster-scoped — a Role cannot grant this).

**Exercise 12 — Cleanup**
1. Delete all ClusterRoles and ClusterRoleBindings you created.
2. Verify the user/SA you tested with loses access.

## 10. Summary

| Concept | Detail |
|---|---|
| **ClusterRole** | A cluster-scoped set of permissions (`apiGroups` + `resources` + `verbs`) |
| **ClusterRoleBinding** | Binds a ClusterRole to subjects across the whole cluster |
| **Scope** | All namespaces, including cluster-scoped resources |
| **Needed for** | Access to `nodes`, `persistentvolumes`, `namespaces`, `storageclasses`, etc. |
| **Reusable trick** | A RoleBinding can reference a ClusterRole — binding's namespace limits the effect |
| **Built-in ClusterRoles** | `cluster-admin`, `admin`, `edit`, `view` |
| **Immutable field** | `roleRef` on the binding |
| **Imperative create** | `kubectl create clusterrole <name> --verb=... --resource=...` |
| **Imperative bind** | `kubectl create clusterrolebinding <name> --clusterrole=<cr> --user=<user>` |
| **API version** | `rbac.authorization.k8s.io/v1` |
| **No namespace** | ClusterRole/ClusterRoleBinding have no `metadata.namespace` |
