# Kubernetes Authorization — Domain 4: Security

---

## 1. What is Authorization?

> **Authorization** is the process of deciding **what an already-authenticated user (or entity) is allowed to do** inside Kubernetes.

It is **not** about confirming "who you are" — that part is **authentication**. Authorization happens **after** authentication, and it answers the question: *"Now that I know who you are, are you allowed to perform this action on this resource?"*

```
   ┌──────────┐     ┌─────────────────┐     ┌─────────────────┐     ┌────────────────────┐
   │  Client  │ ──► │  Authentication │ ──► │  Authorization  │ ──► │ Kubernetes Resource │
   └──────────┘     └─────────────────┘     └─────────────────┘     └────────────────────┘
                       Who are you?           Are you allowed?         Pods, Secrets, etc.
```

If the user does not have permission, the request is **blocked at the authorization stage** — it never reaches the actual Kubernetes resources.

---

## 2. Why Authorization — What Challenges Does It Solve?

### Challenge 1: Authenticated ≠ Trusted

Once a user is logged in, should they be able to do *anything*? Delete all pods, read every secret, drain every node? Obviously not.

**Authorization solves this** by checking permissions for **every API request**, even after a successful login.

---

### Challenge 2: Multi-Team Clusters Need Fine-Grained Access

In a real cluster, different teams (developers, admins, CI/CD service accounts) need different levels of access. A developer should be able to `get` pods, but not delete them across the whole cluster.

**Authorization solves this** by providing fine-grained access control — different users get different permissions on different resources.

---

### Challenge 3: Misconfigured Clusters are Insecure

If a self-managed cluster is set up incorrectly, it may allow anyone authenticated to do anything — which is a major security risk.

**Authorization solves this** by giving cluster admins explicit control. (But beware: if **no authorization mode is set**, Kubernetes defaults to `AlwaysAllow` — which is the dangerous case to avoid.)

---

## 3. How Authorization Works in Kubernetes (Simple Flow)

1. A client sends a request to the **API server**.
2. The API server first runs **authentication** (using certificates, tokens, etc.) to verify identity.
3. Once authenticated, the API server runs **authorization** using the configured authorization mode.
4. Depending on the mode:
   - `AlwaysAllow` → request is always allowed.
   - `AlwaysDeny` → request is always blocked.
   - `RBAC` → permissions are checked against role policies.
5. If allowed, the request reaches the actual Kubernetes resource (Pod, Secret, ConfigMap, etc.).

```
User → API Server → Which Authorization Mode?
                      ├── AlwaysAllow ─► Request Always Allowed
                      ├── AlwaysDeny  ─► Request Always Denied
                      └── RBAC        ─► Check RBAC Policies
                                          ├── cluster-admin       ─► Allowed
                                          ├── developer with 'get' on pods ─► Allowed
                                          ├── User lacks role     ─► Denied
                                          ├── ServiceAccount has RoleBinding ─► Allowed
                                          └── Unknown user         ─► Denied
```

---

## 4. Authorization Modes in Kubernetes

The Kubernetes API server may authorize a request using one of several modes. Common ones:

| Authorization Mode | What it does | When to use |
|---|---|---|
| **AlwaysAllow** | Allows **all** requests. Brings security risks. | Testing only — never production. |
| **AlwaysDeny** | Blocks **all** requests. | Testing only — never production. |
| **RBAC** (Role-Based Access Control) | Defines a set of **permissions** based on roles; access is granted only if the request matches a policy. | **Recommended for production**. |
| **ABAC** | Attribute-Based Access Control — uses attribute policies. | Less common today. |
| **Node** | Authorizes kubelet requests for the node's own pods. | Always-on in real clusters. |
| **Webhook** | Sends authorization checks to an external HTTP service. | For external authz systems. |

> RBAC is what you will use **most of the time** in production. The other production-grade modes (Node, Webhook) work alongside RBAC, not instead of it.

---

## 5. Important Default Behavior (Remember This!)

> **If the authorization mode is NOT explicitly configured in the API server, Kubernetes defaults to `AlwaysAllow`.**

This means if you set up a Kubernetes cluster from scratch and forget to configure authorization, **any authenticated user can do anything** — which is a major security hole.

- **Self-managed clusters:** You must explicitly configure the authorization mode (usually RBAC).
- **Managed clusters (EKS / GKE / AKS / DOKS):** The cloud provider already configures RBAC for you, so this is not something you typically worry about.

---

## 6. Real-World Analogy (from the Slides)

Think of an **AWS user**:
- A brand new AWS user has **no permissions** by default. If they try to delete a server, AWS says "*You don't have permissions*".
- Once you attach the **AdministratorAccess** policy, the user can delete servers.
- Adding/removing those permissions is the **authorization** step.

Kubernetes RBAC works the same way — a `Role` (or `ClusterRole`) is the "policy", and a `RoleBinding` attaches it to a user or service account.

## 7. Syntax

### API Server Flag for Authorization Mode

When running the API server (self-managed cluster), authorization mode is set via the `--authorization-mode` flag:

```bash
# Single mode
--authorization-mode=RBAC

# Multiple modes (evaluated in order)
--authorization-mode=Node,RBAC
```

### Check Current Authorization Mode (Self-Managed Cluster)

```bash
# Look at the API server manifest or systemd unit:
cat /etc/kubernetes/manifests/kube-apiserver.yaml | grep authorization-mode
```

### Check Whether You Can Perform an Action

```bash
# Generic syntax
kubectl auth can-i <verb> <resource>

# Example: can I delete pods?
kubectl auth can-i delete pods

# Check on behalf of another user
kubectl auth can-i delete pods --as=jane

# Check in a specific namespace
kubectl auth can-i list secrets -n kube-system
```

## 8. Examples

### Example 1: Demo — `AlwaysAllow` Mode (Testing Only)

On a self-managed cluster, the API server is started with:

```
--authorization-mode=AlwaysAllow
--token-auth-file=/etc/kubernetes/root-token.csv
```

A request with a valid token:

```bash
kubectl get pods --token=<token> --insecure-skip-tls-verify
# returns the list of pods — no authorization check blocks it
```

Even a destructive command works:

```bash
kubectl delete pods --all --token=<token> --insecure-skip-tls-verify
# all pods get deleted — there is nothing stopping it
```

This is why **AlwaysAllow is never used in production**.

---

### Example 2: Demo — `AlwaysDeny` Mode

Change the API server flag:

```
--authorization-mode=AlwaysDeny
```

Restart the API server. Now any request returns:

```bash
kubectl get pods --token=<token> --insecure-skip-tls-verify
# Error: pods is forbidden
```

`AlwaysDeny` is also for testing only — nothing works.

---

### Example 3: Check Your Own Permissions

```bash
kubectl auth can-i create deployments
# yes

kubectl auth can-i delete nodes
# no
```

This is the simplest way to verify authorization rules without trying the action.

---

### Example 4: Check on Behalf of a Service Account

```bash
kubectl auth can-i list pods \
  --as=system:serviceaccount:dev:reader-sa \
  -n dev
# yes / no
```

This impersonates a service account to test what it can do.

## 9. Exercises to Practice for the CKAD Exam

### Imperative (CLI-based) Exercises

**Exercise 1 — Check Your Own Permissions**
1. Run `kubectl auth can-i get pods`.
2. Run `kubectl auth can-i delete nodes`.
3. Note which actions you can and cannot perform.

**Exercise 2 — Check a Namespace-Specific Permission**
1. Run `kubectl auth can-i list secrets -n kube-system`.
2. Compare the result with `kubectl auth can-i list secrets -n default`.

**Exercise 3 — Impersonate Another User**
1. Use `kubectl auth can-i list pods --as=alice`.
2. Use `kubectl auth can-i list pods --as=system:serviceaccount:default:my-sa`.
3. Note the results.

**Exercise 4 — Inspect the API Server Authorization Mode (Self-Managed)**
1. On a self-managed cluster (e.g., kubeadm), look inside `/etc/kubernetes/manifests/kube-apiserver.yaml`.
2. Find the `--authorization-mode` flag and record the modes in use.

**Exercise 5 — Practice Authorization Failures**
1. As an unprivileged user, run `kubectl delete namespace default`.
2. Observe the `forbidden` error message and identify which authorization mode produced it.

---

### Declarative (YAML-based) Exercises

> Most authorization is set on the API server itself (flags) or via RBAC objects (covered in a separate notes file). Below are declarative-style exercises that help cement how authorization decisions interact with manifests.

**Exercise 6 — Pod Creation Authorization Check**
1. Write a simple Pod manifest (`pod.yaml`) for an `nginx` pod.
2. Try `kubectl apply -f pod.yaml --as=alice` (a user with no permissions).
3. Observe the `forbidden` response — the authorization stage blocked the request, even though the manifest was valid.

**Exercise 7 — Service Account Authorization Test**
1. Create a ServiceAccount manifest called `reader-sa` in the `default` namespace.
2. Apply it.
3. Run `kubectl auth can-i get pods --as=system:serviceaccount:default:reader-sa`.
4. Confirm the answer is `no` — no Role is bound to this SA yet.

**Exercise 8 — Identify the Default Authorization Mode**
1. On a fresh kubeadm cluster, deliberately remove the `--authorization-mode` flag from the API server manifest.
2. After the API server restarts, verify (by attempting destructive actions) that the cluster is now in `AlwaysAllow`.
3. Restore the original flag to make the cluster secure again.

**Exercise 9 — Reading the Workflow Diagram**
1. Look at the workflow:
   ```
   User → Auth Mode? → AlwaysAllow / AlwaysDeny / RBAC → Allowed or Denied
   ```
2. For each of these scenarios, predict the outcome:
   - Mode = `AlwaysAllow`, user has no role → ?
   - Mode = `AlwaysDeny`, user is cluster-admin → ?
   - Mode = `RBAC`, user has `get pods` permission, tries `delete pods` → ?

## 10. Summary

| Concept | Detail |
|---|---|
| **What it is** | The stage that decides what an authenticated user is **allowed to do** |
| **Comes after** | Authentication — authentication is who, authorization is what |
| **API Server flag** | `--authorization-mode=...` |
| **Common modes** | `AlwaysAllow`, `AlwaysDeny`, `RBAC`, `ABAC`, `Node`, `Webhook` |
| **AlwaysAllow** | Allows all requests; testing only — insecure |
| **AlwaysDeny** | Blocks all requests; testing only |
| **RBAC** | Permissions are granted via Roles/ClusterRoles bound to users/SAs — **production standard** |
| **Default mode (if not set)** | **`AlwaysAllow`** — this is the dangerous default for self-managed clusters |
| **Managed clusters** | EKS/GKE/AKS/DOKS configure RBAC for you out of the box |
| **Quick permission check** | `kubectl auth can-i <verb> <resource>` (add `--as=<user>` to impersonate) |
| **Blocked at this stage** | A `forbidden` error from kubectl is the authorization layer rejecting your request |
