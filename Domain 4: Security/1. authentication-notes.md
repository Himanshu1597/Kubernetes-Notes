# Kubernetes Authentication — Domain 4: Security

---

## 1. What is Authentication?

> **Authentication** is the process of **verifying a user's identity** before granting them access to a system or resource.

It is the very first step — before Kubernetes lets anyone do anything, it asks: *"Who are you?"*

```
   ┌──────────┐       Create 10 pods        ┌────────────────┐
   │  Client  │ ───────────────────────────►│   Kubernetes   │
   │          │ ◄─────────────────────────── │                │
   └──────────┘   "Dude, who are you?         └────────────────┘
                   Authenticate first!"
```

Authentication is **different from authorization**:
- **Authentication** = "Who are you?" (identity check)
- **Authorization** = "What are you allowed to do?" (permission check)

Authentication **always comes first**. Only after Kubernetes confirms your identity does it move on to checking permissions.

---

## 2. Why Authentication — What Challenges Does It Solve?

### Challenge 1: Anyone Could Send Requests to the API Server

The Kubernetes API server listens for requests over the network. Without authentication, **anyone** who can reach the API server could create pods, read secrets, or destroy the cluster.

**Authentication solves this** by forcing every request to prove its identity before being processed.

---

### Challenge 2: Multiple Types of Clients Need to Connect

A cluster has many kinds of clients — human users on `kubectl`, CI/CD pipelines, applications running inside pods, cloud monitoring agents. They cannot all use the same login method.

**Authentication solves this** by supporting many different authentication methods so each client type can use what fits best.

---

### Challenge 3: Kubernetes Has No Built-In User Database

Kubernetes is not a user management system. It does not store usernames and passwords like AWS IAM does.

**Authentication solves this** by **referencing external identity sources** — certificates, token files, OIDC providers (Active Directory, Google, etc.) — instead of managing users itself.

---

## 3. How Authentication Works in Kubernetes (Simple Flow)

1. Client (kubectl, app, pipeline) sends a request to the API server.
2. The request includes some kind of **credential** — a certificate, a bearer token, etc.
3. The API server looks at the credential and tries to **match it against a configured authentication method**.
4. If a match is found, Kubernetes knows the username — the user is **authenticated**.
5. The request then moves on to the **authorization** stage (covered in separate notes).
6. If no method recognises the credential, the API returns `Unauthorized`.

---

## 4. Important Point — Kubernetes Does NOT Manage User Accounts Natively

> **You cannot run `kubectl create user alice`.** Kubernetes has no "user" object for human users.

```
   Client  ──── kubectl create user alice ────►  Kubernetes  ✗  (not supported)
```

Instead, "users" exist **only as identifiers inside the credential** (e.g., the Common Name of a certificate, or the username in a token file). Kubernetes simply trusts what is in that external credential.

**The exception:** Kubernetes does manage one type of identity natively — the **ServiceAccount** (used by apps inside pods).

---

## 5. Categories of Users in Kubernetes

There are **two categories** of users in a Kubernetes cluster:

| Category | Used By | Stored In Cluster? | Typical Auth Method |
|---|---|---|---|
| **Normal Users** | Human beings (developers, admins) | **No** — managed externally | X509 client certificates, OIDC tokens, static token file |
| **Service Accounts** | Applications / processes running inside pods | **Yes** — first-class Kubernetes objects | Service account tokens (JWT) |

> Why two categories? Generating client certificates for every application inside every pod is cumbersome. ServiceAccounts give apps a simple, Kubernetes-native way to authenticate.

```
                  ┌──────────────────────┐
                  │      Kubernetes       │
                  └──────────┬───────────┘
                             │
              ┌──────────────┴──────────────┐
              ▼                              ▼
      Normal Users (humans)        Service Accounts (apps)
```

---

## 6. Authentication Methods Supported by Kubernetes

Kubernetes supports **many** authentication methods. The common ones:

| Method | Description |
|---|---|
| **X509 Client Certificates** | Each user has their own certificate + private key. The API server validates the certificate against its CA. Default for kubeadm clusters. |
| **Static Token File** | A CSV file maps tokens to usernames. Simple but not recommended for production. |
| **Bootstrap Tokens** | Short-lived tokens used when nodes join the cluster. |
| **Service Account Tokens** | JWT tokens automatically mounted into pods. Used by apps inside the cluster. |
| **OpenID Connect (OIDC) Tokens** | Integrates with external identity providers (Active Directory, Google, Okta, etc.). |
| **Webhook Token Authentication** | API server calls an external service to validate the token. |

> In production, **X509 certificates** and **OIDC** are most common for human users; **Service Account tokens** are the standard for apps inside pods.

---

## 7. Method 1 — Static Token File

> The API server reads **bearer tokens from a CSV file** that you provide. Each line maps a token to a user.

The file is a CSV with at least 3 columns: `token, username, uid` (optional 4th column: `groups`).

### Example file (`/root/token.csv`):

```
Dem0Passw0rd#,bob,01,admins
```

### How the API server is told to use it:

```
[Service]
ExecStart=/usr/local/bin/kube-apiserver \
  --token-auth-file=/root/token.csv \
  ...
```

### How a client uses the token:

```bash
curl -k https://<api-server>:6443/api/v1/namespaces/default/pods \
     -H "Authorization: Bearer Dem0Passw0rd#"
```

- Right token → request is **authenticated** and returns the pods.
- Wrong token → API returns **`Unauthorized`**.

> Static tokens are not rotated, not encrypted, and end up in plain files — **not recommended for production**. Good for demos and learning.

---

## 8. Method 2 — X509 Client Certificates

> Each user has their **own certificate and private key**. The Common Name (CN) inside the certificate becomes the **username**. The group(s) come from the certificate's Organization (O) field.

This is the **default** for kubeadm-style clusters. The credentials are stored in the **kubeconfig** file (`~/.kube/config`).

### Snippet of a kubeconfig using client certificates:

```yaml
kind: Config
users:
- name: kubernetes-admin
  user:
    client-certificate-data: <base64-encoded cert>
    client-key-data:         <base64-encoded key>
```

- The `client-certificate-data` is base64-encoded — decode it to see the actual certificate.
- Inside the decoded certificate, the **Common Name (CN)** is the username (e.g., `kubernetes-admin`).
- The API server validates the certificate against its trusted CA.

> The certificate's CN is the user identity — no need for a user object in Kubernetes.

---

## 9. Managed Kubernetes — DigitalOcean Example

Cloud-managed clusters (EKS, GKE, AKS, DOKS) handle authentication for you. The method may even change over time:

- DigitalOcean used to use **client certificates**.
- DigitalOcean now uses **tokens** in the kubeconfig:

```yaml
users:
- name: do-user
  user:
    token: <long-token-string>
```

The takeaway: **the authentication method depends on the provider**, but the idea is always the same — the kubeconfig holds whatever credential the API server is set up to accept.

## 10. Syntax

### Inspect the Current kubeconfig Authentication

```bash
kubectl config view
kubectl config view --minify --raw       # shows full credentials including base64 cert
```

### Test Authentication Manually (Static Token Example)

```bash
curl -k https://<api-server>:6443/api/v1/pods \
     -H "Authorization: Bearer <token>"
```

### Decode a Base64 Client Certificate from kubeconfig

```bash
echo "<client-certificate-data>" | base64 -d
```

### Check Who You Are Authenticated As

```bash
kubectl auth whoami           # (newer kubectl)
# or
kubectl config current-context
```

### API Server Flags Related to Authentication (Self-Managed Cluster)

```
--client-ca-file=/etc/kubernetes/pki/ca.crt          # X509 client cert auth
--token-auth-file=/root/token.csv                    # static token auth
--service-account-key-file=/etc/kubernetes/pki/sa.pub  # SA token validation
```

## 11. Examples

### Example 1 — Static Token Authentication (Successful)

Server config:

```
--token-auth-file=/root/token.csv
```

File `/root/token.csv`:

```
Dem0Passw0rd#,bob,01,admins
```

Request from client:

```bash
curl -k https://<api-server>:6443/api/v1/pods \
     -H "Authorization: Bearer Dem0Passw0rd#"
# returns the list of pods (authenticated as 'bob')
```

---

### Example 2 — Static Token Authentication (Failed)

Wrong token:

```bash
curl -k https://<api-server>:6443/api/v1/pods \
     -H "Authorization: Bearer WrongToken123"
# {"kind":"Status","status":"Failure","message":"Unauthorized","code":401}
```

The API server did not recognise the token → **Unauthorized**.

---

### Example 3 — Inspect Client Certificate Auth in kubeconfig

```bash
kubectl config view --raw | grep client-certificate-data
# client-certificate-data: <base64>
```

Decode and look at the CN:

```bash
echo "<base64-cert>" | base64 -d | openssl x509 -text -noout | grep "Subject:"
# Subject: O = system:masters, CN = kubernetes-admin
```

So the user is `kubernetes-admin` and the group is `system:masters`.

---

### Example 4 — Token-Based Managed Cluster (DigitalOcean)

`~/.kube/config` snippet:

```yaml
clusters:
- cluster:
    server: https://abc-do-cluster.k8s.ondigitalocean.com
  name: do-cluster

users:
- name: do-user
  user:
    token: dop_v1_abc123...
```

When you run `kubectl get pods`, the token in this file is sent as a bearer token in the request header.

## 12. Exercises to Practice for the CKAD Exam

### Imperative (CLI-based) Exercises

**Exercise 1 — Inspect Your kubeconfig**
1. Run `kubectl config view`.
2. Identify which authentication method is in use (certificate, token, or exec plugin).
3. Run `kubectl config current-context` to see the current cluster/user.

**Exercise 2 — Identify Yourself**
1. Run `kubectl auth whoami` (if your kubectl supports it).
2. Otherwise, run `kubectl config view --minify -o jsonpath='{.users[0].name}'`.
3. Note the username — this is who the API server sees you as.

**Exercise 3 — Decode a Client Certificate**
1. Use `kubectl config view --raw` to extract `client-certificate-data`.
2. Decode it: `echo "<base64>" | base64 -d`.
3. Use `openssl x509 -text -noout` to read the CN (user) and O (group).

**Exercise 4 — Test Authentication with curl + Token**
1. Get a service account token (e.g., `kubectl create token <sa-name>`).
2. Use `curl -k -H "Authorization: Bearer <token>" https://<api>/api/v1/pods`.
3. Confirm the request succeeds.

**Exercise 5 — Force an Authentication Failure**
1. Send a `curl` request to the API server with an obviously bad token.
2. Confirm the response is `401 Unauthorized`.

---

### Declarative (YAML-based) Exercises

**Exercise 6 — Create a ServiceAccount**
1. Write a YAML manifest:
   ```yaml
   apiVersion: v1
   kind: ServiceAccount
   metadata:
     name: my-app-sa
   ```
2. Apply it.
3. Run `kubectl get sa my-app-sa` and confirm it exists.

**Exercise 7 — Use a ServiceAccount in a Pod**
1. Write a Pod manifest with `spec.serviceAccountName: my-app-sa`.
2. Apply it.
3. Inside the pod, look at `/var/run/secrets/kubernetes.io/serviceaccount/token` — this is the JWT the pod uses to authenticate to the API server.

**Exercise 8 — Generate a Token for a Service Account**
1. Run `kubectl create token my-app-sa --duration=1h`.
2. Note that this is a short-lived bearer token.
3. Use it in a `curl` request to the API server and confirm it works.

**Exercise 9 — Predict the Result of Different Credentials**
For each scenario, predict the outcome:
- Valid certificate, no token → ?
- Invalid certificate, valid token → ?
- No credentials at all → ?
- Token does not match any user → ?

**Exercise 10 — Identify the Auth Method on Different Clusters**
1. Look at `~/.kube/config` for any two clusters you have access to (e.g., a local kubeadm cluster and a managed cluster).
2. For each, identify if it uses client certificates, tokens, or an exec plugin.

## 13. Summary

| Concept | Detail |
|---|---|
| **What it is** | The stage where Kubernetes verifies **who** the requester is |
| **Comes before** | Authorization (which decides **what** they can do) |
| **Native user management?** | **No** — Kubernetes does not store normal users; they exist only in external credentials |
| **Two categories of users** | **Normal Users** (humans, external) and **Service Accounts** (apps, native objects) |
| **Common methods** | X509 client certificates, static token file, service account tokens, OIDC, bootstrap tokens, webhook |
| **kubeadm default** | X509 client certificate authentication |
| **Managed cluster default** | Often token-based (varies by provider) |
| **Static token file** | CSV `token,username,uid,groups`; pointed at by `--token-auth-file` |
| **X509 auth identity** | Common Name (CN) of the certificate = username; Organization (O) = group |
| **ServiceAccount token** | Mounted into pods at `/var/run/secrets/kubernetes.io/serviceaccount/token` |
| **Failure response** | `401 Unauthorized` |
| **Check identity** | `kubectl auth whoami`, `kubectl config view` |
