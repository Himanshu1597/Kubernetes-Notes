# Kubernetes RBAC — Domain 4: Security

---

## 1. What is RBAC?

> **RBAC (Role-Based Access Control)** is the authorization mode in Kubernetes where you **define a set of permissions** and then **bind those permissions to users, groups, or service accounts**. Only after binding does a subject get the listed permissions.

In simple plain English: *"Define what actions are allowed. Then attach those actions to someone."*

```
   ┌──────────┐   ┌─────────────────┐   ┌─────────────────┐
   │  Client  │──►│ Authentication  │──►│  Authorization  │──► Resource
   └──────────┘   │ (who are you?)  │   │  (RBAC: what    │
                  └─────────────────┘   │   can you do?)  │
                                        └─────────────────┘
```

RBAC happens **after authentication**. If the user is allowed by a Role, access is granted; otherwise the request is denied.

---

## 2. Why RBAC — What Challenges Does It Solve?

### Challenge 1: Authenticated Users Should NOT Have Full Access

Once a user successfully authenticates, the cluster needs to decide what they can actually do. Without RBAC (or with `AlwaysAllow`), every authenticated user could delete everything. That is a security disaster.

**RBAC solves this** by requiring explicit permission rules — no rule, no access.

---

### Challenge 2: Different Teams Need Different Permissions

A developer might need to view pods in their namespace; a security engineer might need to create secrets in a different namespace; a CI/CD service account might need to deploy apps. They cannot all use the same permissions.

**RBAC solves this** by letting you define many small **Roles** and bind them only to the right **subjects**.

---

### Challenge 3: Some Permissions Must Be Scoped to a Namespace, Others to the Whole Cluster

Some resources (pods, configmaps, secrets) are namespace-scoped. Other resources (nodes, persistent volumes) are cluster-scoped. Permissions need to match.

**RBAC solves this** by giving you two pairs:
- **Role + RoleBinding** → permissions for a **single namespace**.
- **ClusterRole + ClusterRoleBinding** → permissions across **the whole cluster**.

---

## 3. The Basic Workflow

Imagine two tables:

```
   ┌──────────────┐                       ┌──────────────────────┐
   │   Users       │       Bind            │   Permissions        │
   │              │ ◄───────────────────► │                      │
   │  Alice       │                       │  list pods           │
   │  Bob         │                       │  create/delete       │
   │              │                       │  secrets             │
   └──────────────┘                       └──────────────────────┘
```

The two tables are **independent**. To give Alice and Bob those permissions, you have to **bind** them together. That bind is what RBAC does in Kubernetes.

---

## 4. The 3 Important RBAC Concepts

| Concept | What it is |
|---|---|
| **Role** | Defines a **set of permissions**. (Or **ClusterRole** for cluster-wide permissions.) |
| **Subject** | The **who** — can be a **User**, **Group**, or **ServiceAccount**. |
| **RoleBinding** | **Ties** the Role's permissions to one or more Subjects. (Or **ClusterRoleBinding** for cluster-wide binding.) |

```
   ┌──────────────┐                          ┌──────────────┐
   │   Subjects    │       RoleBinding         │     Role     │
   │              │ ◄────────────────────────► │              │
   │  Users       │                          │  list pods   │
   │  Groups      │                          │  create/del  │
   │  Service     │                          │  secrets     │
   │  Accounts    │                          │              │
   └──────────────┘                          └──────────────┘
```

Without the binding, a Role does nothing. Without a Role, a Binding has nothing to grant. You need **all three**.

---

## 5. Namespace Scope vs Cluster Scope

This is the most important RBAC distinction.

| | Role / RoleBinding | ClusterRole / ClusterRoleBinding |
|---|---|---|
| **Scope** | Single namespace | Entire cluster (all namespaces) |
| **Used for** | Permissions on namespaced resources (pods, configmaps, secrets) in **one** namespace | Permissions across **all** namespaces, OR for **cluster-scoped** resources (nodes, persistent volumes) |
| **Detail file** | [role-rolebinding-notes.md](role-rolebinding-notes.md) | [clusterrole-clusterrolebinding-notes.md](clusterrole-clusterrolebinding-notes.md) |

> Resources like **nodes**, **namespaces**, and **persistentVolumes** are **cluster-scoped** — you cannot grant access to them with a Role; you must use a ClusterRole.

## 6. Anatomy of a Role / ClusterRole — apiGroups, resources, verbs

Every Role (and ClusterRole) is built from **three fields** under `rules`:

| Field | What it does |
|---|---|
| **`apiGroups`** | Which API group the rule applies to. |
| **`resources`** | Which resources inside that group the rule applies to. |
| **`verbs`** | Which actions are allowed on those resources. |

### 6.1 apiGroups

Kubernetes APIs are organised into groups. The most common ones:

| API Group | Description |
|---|---|
| `""` (empty string) | The **core** API group — `pods`, `services`, `configmaps`, `secrets`, `namespaces`, etc. |
| `apps` | `deployments`, `daemonsets`, `replicasets`, `statefulsets` |
| `batch` | `jobs`, `cronjobs` |
| `networking.k8s.io` | `ingresses`, `networkpolicies` |

```bash
# See which resources are in a given API group:
kubectl api-resources --api-group=apps
kubectl api-resources --api-group=""        # core group
```

### 6.2 resources

The kind of resource you want to grant access to, e.g., `pods`, `deployments`, `secrets`, `configmaps`. The resource must belong to the apiGroup you specified.

### 6.3 verbs

The actions allowed on those resources. Common verbs:

| Verb | What it does |
|---|---|
| `get` | Read a specific resource by name. |
| `list` | List all resources of that type. |
| `create` | Create a new resource. |
| `update` | Modify an existing resource. |
| `patch` | Partially modify a resource. |
| `delete` | Remove a resource. |
| `watch` | Observe changes to a resource. |

### Example `rules` block

```yaml
rules:
- apiGroups: [""]                # core
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "create"]
```

This rule grants read access on pods (core) and limited access on deployments (apps).

## 7. Anatomy of a RoleBinding / ClusterRoleBinding — subjects + roleRef

Every Binding has **two parts**:

| Field | What it does |
|---|---|
| **`subjects`** | Who gets the permission — Users, Groups, or ServiceAccounts. |
| **`roleRef`** | Which Role (or ClusterRole) is being attached. |

```yaml
subjects:
- kind: User
  name: bob
  apiGroup: rbac.authorization.k8s.io

roleRef:
  kind: Role                   # or ClusterRole
  name: pod-read-only
  apiGroup: rbac.authorization.k8s.io
```

> The `roleRef` cannot be changed once the binding is created — you must delete and recreate the binding to switch its Role.

## 8. Preparing a Subject — ServiceAccount + Token

To **test** RBAC rules quickly without juggling X509 certificates, the common trick is to create a **ServiceAccount**, generate a token for it, then use the token as the Subject in your binding.

### Step 1 — Create a ServiceAccount

```bash
kubectl create serviceaccount test-sa
kubectl get sa
# default    1   1m
# test-sa    1   5s
```

### Step 2 — Generate a Token

```bash
# Default: ~1 hour expiry
kubectl create token test-sa

# Longer expiry (e.g., 100 hours)
kubectl create token test-sa --duration=100h
```

> The output is a JWT (JSON Web Token). You can paste it into a JWT decoder to see the expiry, subject, etc.

### Step 3 — Store the Token in an Environment Variable

```bash
# Linux / Mac
export TOKEN="<paste-token-here>"
echo $TOKEN

# Windows
set TOKEN=<paste-token-here>
echo %TOKEN%
```

### Step 4 — Use the Token in a curl Request

```bash
# Get the API server URL
kubectl cluster-info

# Send a request with the token as Bearer auth
curl -k -H "Authorization: Bearer $TOKEN" \
     https://<api-server>:6443/api/v1/namespaces/default/pods
```

If the ServiceAccount is bound to a Role with `list` on `pods` in `default`, this succeeds. Otherwise it returns `forbidden`.

> The **subject name** for a ServiceAccount in a RoleBinding looks like:
> `system:serviceaccount:<namespace>:<sa-name>`
> e.g., `system:serviceaccount:default:test-sa`

## 9. Generic Syntax

### Imperative — Create a Role / RoleBinding / ClusterRole / ClusterRoleBinding

```bash
# Role (namespace-scoped)
kubectl create role <role-name> --verb=<verb> --resource=<resource>

# RoleBinding
kubectl create rolebinding <name> --role=<role> --user=<user>           # bind a user
kubectl create rolebinding <name> --role=<role> --serviceaccount=<ns>:<sa>

# ClusterRole (cluster-scoped)
kubectl create clusterrole <name> --verb=<verb> --resource=<resource>

# ClusterRoleBinding
kubectl create clusterrolebinding <name> --clusterrole=<role> --user=<user>
```

### Inspect

```bash
kubectl get role,rolebinding -n <namespace>
kubectl get clusterrole,clusterrolebinding
kubectl describe role <name> -n <namespace>
kubectl describe rolebinding <name> -n <namespace>
```

### Generate YAML with dry-run

```bash
kubectl create role pod-reader --verb=list --resource=pods --dry-run=client -o yaml
kubectl create rolebinding test-binding --role=pod-reader --user=bob --dry-run=client -o yaml
```

> When you create a Role via CLI, Kubernetes automatically figures out the correct `apiGroup` for you. You only need to pick the resource.

### Check What You Can Do

```bash
kubectl auth can-i list pods
kubectl auth can-i create secrets --as=bob -n default
kubectl auth can-i get nodes --as=system:serviceaccount:default:test-sa
```

## 10. End-to-End Example (Conceptual)

```
1. Bob tries:  kubectl get pods       →  forbidden (no role bound)

2. Admin creates a Role:
     pod-read-only:  resource=pods, verbs=[list], namespace=default

3. Admin creates a RoleBinding:
     test-binding:  binds Role 'pod-read-only' to user 'bob'

4. Bob tries again:  kubectl get pods           →  ✓ works (default namespace)
   Bob tries:        kubectl get pods -n kube-system  →  ✗ forbidden
   Bob tries:        kubectl delete pod x       →  ✗ forbidden (no delete verb)
   Bob tries:        kubectl get secrets        →  ✗ forbidden (resource not in role)
```

## 11. Exercises to Practice for the CKAD Exam

> Type-specific exercises live in the Role/RoleBinding and ClusterRole/ClusterRoleBinding notes. Below are concept-level exercises.

### Imperative (CLI-based) Exercises

**Exercise 1 — Confirm RBAC is Active**
1. Run `kubectl auth can-i create pods` as yourself. Note the response.
2. Run `kubectl auth can-i delete nodes --as=bob`. Note the response.

**Exercise 2 — Inspect Default Roles**
1. List all roles across all namespaces: `kubectl get roles --all-namespaces`.
2. List all cluster roles: `kubectl get clusterroles`.
3. Pick one cluster role (e.g., `cluster-admin`) and describe it: `kubectl describe clusterrole cluster-admin`.

**Exercise 3 — API Group Discovery**
1. Run `kubectl api-resources --api-group=""` and list the core resources.
2. Run `kubectl api-resources --api-group=apps`.
3. Run `kubectl api-resources --api-group=batch`.

**Exercise 4 — Service Account + Token for Testing**
1. Create a ServiceAccount called `test-sa`.
2. Generate a 24-hour token: `kubectl create token test-sa --duration=24h`.
3. Set it as `TOKEN` env var.
4. Use curl with the token against the API server — observe `forbidden` until you bind a role.

---

### Declarative (YAML-based) Exercises

**Exercise 5 — Write Your Own Rules Block**
1. Write a `rules:` block that grants `get`, `list`, `watch` on **pods** (core group) and **deployments** (apps group).
2. Save it inside a Role manifest (do not apply yet — we'll cover this in the next file).

**Exercise 6 — Decode a JWT Token**
1. Generate a token: `kubectl create token test-sa`.
2. Paste it into any online JWT decoder.
3. Identify the `exp` (expiry) field and the `sub` (subject) field.

**Exercise 7 — Predict Outcomes**
For each scenario, predict whether the action will be allowed or denied:
- User `alice` has a Role with `list` on `pods` in `default`. She runs `kubectl get pods -n default`. → ?
- Same Alice runs `kubectl get pods -n kube-system`. → ?
- Same Alice runs `kubectl delete pod x -n default`. → ?
- Same Alice runs `kubectl get secrets -n default`. → ?
- User `bob` has a ClusterRole with `list` on `pods`. He runs `kubectl get pods -n kube-system`. → ?

## 12. Summary

| Concept | Detail |
|---|---|
| **What it is** | The authorization mode that grants access based on bound roles |
| **Comes after** | Authentication |
| **3 building blocks** | Role (permissions), Subject (who), RoleBinding (the link) |
| **Two scopes** | Role/RoleBinding = namespace; ClusterRole/ClusterRoleBinding = cluster |
| **Role fields** | `apiGroups`, `resources`, `verbs` |
| **Binding fields** | `subjects` and `roleRef` |
| **Subjects** | User, Group, ServiceAccount |
| **Cluster-scoped resources** | Need ClusterRole — e.g., nodes, persistentVolumes |
| **CLI for testing** | `kubectl auth can-i ...` and `kubectl create token <sa>` |
| **Manifest from CLI** | `kubectl create role ... --dry-run=client -o yaml` |
| **Detail files** | [role-rolebinding-notes.md](role-rolebinding-notes.md), [clusterrole-clusterrolebinding-notes.md](clusterrole-clusterrolebinding-notes.md) |
